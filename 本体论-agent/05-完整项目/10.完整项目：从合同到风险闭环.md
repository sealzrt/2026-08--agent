# 10. 完整项目：从合同到风险闭环

## 先看一个扎心的对比

> 传统信息化系统：核心是**记录、流程**——数据躺着等人查，流程按部就班跑。
>
> AI-Native 系统：核心是**认知、演化**——系统自己理解业务、推理风险、触发动作，还在不断长出新的理解。
>
> 从"记录"到"认知"，差的就是一条**能自己跑通的业务闭环**。这一章我们把前面 9 章串起来，做一整个"从合同到风险"的完整项目。

## 一句话说清

**完整项目 = 上传合同 → 自动建模 → 规则扫描 → 风险确认 → 人工审核 → 结果展示，一整套端到端闭环。** 前面学的每样东西，都在这里面各就各位。

## 1. 先看整条链路长什么样

```
① 上传合同（docx/pdf）
   ↓ 文档解析（RDF/SPARQL 不直接参与，先转纯文本）
② 自动建模（本体当模板）
   ↓ 按"合同"类的属性去认：金额、编号、验收条款、功能清单
③ 数据落库（第 05 章：数据装进图谱）
   ↓ 实体、关系、带来源和置信度
④ 规则扫描（第 06 章：怎么推）
   ↓ 沿本体关系推演：延期>7天→进度风险；变更>3次→需求蔓延
⑤ 风险确认（人机协作）
   ↓ 每条建议可编辑、可勾选采纳，不盲目写入
⑥ 人工审核（第 09 章：管住 AI）
   ↓ 高风险动作 interrupt，等项目经理批准
⑦ 结果展示（图谱 + 仪表盘）
   ↓ 合同→需求→方案→风险 的关系一目了然
```

> 这就是"本体论 + Agent"的最朴素落地形态。你不用等一个万能大模型，把这一条链先跑通，就已经比"只会搜文档的 AI"强一个量级。

## 2. 完整案例一：合同风险管控（你熟悉的那套）

**业务判断**：这份合同有没有坑？实施会不会延期？

| 环节 | 干什么 | 用到的章节能力 |
|---|---|---|
| 合同要素抽取 | 金额/关键节点/交付物/功能清单/维保/指标 | 第 06 章查询 + 规则 |
| 功能清单 | 10 个模块成为对齐锚点 | 第 05 章数据映射 |
| 需求对齐 | 功能 ↔ 需求覆盖矩阵，缺的=风险 | 第 07 章检索 |
| 规则引擎 | 延期/变更/未评审/无验收条款 自动触发风险 | 第 06 章推理 |
| 风险审批 | 高风险挂起，项目经理确认 | 第 09 章 HITL |

**效果**：上传一份合同，几分钟内得到 60+ 条结构化建议（要素/功能/风险），人工确认后落库，后续所有模块都能沿着这张图查。

## 3. 完整案例二：供应商合作价值评估（视频里的经典案例）

**业务判断**：这个供应商还值不值得继续合作？

**判断依赖的关系链**：

```
供应商 ─签订→ 合同 ─包含→ 交付节点
供应商 ─发生→ 交付记录 ─产生→ 质量异常
合同 ─约定→ 付款条款 ─对应→ 付款记录
供应商 ─关联→ 风险标记 ─触发→ 审批升级
```

**跑起来的效果**：

- 采购成本异常 → 自动调供应商清单 → 和**历史合同**比价 → 发现超标 → **自动升级给主管批**
- 评估"是否继续合作"：聚合交付记录、延期条款、投诉、替代供应商、区域风险、未来项目依赖——**不是看一份合同，是看一整条关系链**

> 这就是"同一套模型 4 天 → 2 小时"的秘密：模型不是在碎片里检索猜测，是直接沿结构化业务世界推理。

## 4. 回答凭什么可信？（证据链）

AI 说"合同 HT-001 缺验收条款，影响里程碑 M1"——凭什么信它？因为每个结论都带**证据链**：

```
结论：验收条款缺失风险（风险R1）
  ├─ 事实来源：合同 HT-001 第 4 节未出现"验收"（文档证据，第 3 页）
  ├─ 规则依据：规则 R6"合同无验收条款 → 验收风险（高）"
  ├─ 关系路径：合同 HT-001 →约束→ 项目AAA →包含→ 里程碑M1
  └─ 置信度：0.9（规则触发）｜ 采纳人：张经理（审计记录）
```

**结论可追溯、可审计**——这正是纯大模型黑盒给不了的。

## 5. 怎么保证它一直不出错？（测试与评估）

三层测试，由底向上：

| 层 | 测什么 | 例子 |
|---|---|---|
| **单元** | 单个规则/函数 | "延期>7天"的规则单测 |
| **图级** | 本体查询、节点路由 | 沿关系链查询是否正确 |
| **端到端** | 完整任务、HITL、恢复 | 上传合同→建模→审核→落库全流程 |

再加一个**评估集**：收集 20 个真实合同问题（标准实体、期望答案），每次改版跑一遍，看成功率有没有掉。

## 6. 别忘了：它会长大（认知演化）

传统系统改一次功能要发一次版；本体系统是**可演化的**：

```
系统运行 → 发现新实体（如"变更单"）→ 补进本体 → 验证 → 升版本
→ 长期记忆沉淀 → 异常模式识别 → 系统对世界的理解越来越准
```

**这就是"认知演化"**：不是自动化（自动化是写好的脚本在跑），是系统根据规则自己组织自己、自己长出新理解。

## 7. 回头看：四步落地路径用上了吗

| 第一步 | 定位业务判断 | 合同风险管控 / 供应商合作价值 |
| 第二步 | 梳理依赖实体关系 | 合同/项目/交付/付款/风险标记… |
| 第三步 | 盘点信息载体 | 数据库+PDF+工单+老员工经验 |
| 第四步 | 才接 AI | 先问答，再预警，再自动执行 |

先有底盘（本体），再装发动机（大模型）和驾驶系统（Agent）——**第一性原理想清楚去哪，本体论搭底盘**。

## 一句话总结

**本体论让 AI 从"会搜索"变成"懂业务"，从"懂业务"变成"能跑通闭环"，从"跑通闭环"变成"会演化"。这一章的项目，就是这三步的合体。**
