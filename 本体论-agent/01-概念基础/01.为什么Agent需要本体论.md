# 01. 为什么 Agent 需要本体论

## 本章目标

- 理解 Agent 只依赖自然语言和向量检索时的边界。
- 理解本体论提供的概念、关系和约束。
- 建立“本体论是语义基础层”的整体认识。

## 一个常见误区

很多 Agent 的链路是：

```text
用户问题 -> 向量检索 -> 拼接上下文 -> LLM 生成回答
```

这条链路适合查找相似文本，但不一定能稳定回答结构化问题：

- 产品属于哪个模块？
- 哪些问题会影响这个功能？
- 哪个角色有权限执行这个动作？
- 这个工具是否适用于当前实体？

这些问题不只是“找相似文本”，还需要理解实体类型、关系和业务约束。

## 本体论增强 Agent

```mermaid
flowchart LR
    U[用户问题] --> A[Agent]
    A --> E[实体与意图识别]
    E --> O[本体论约束]
    O --> Q[结构化查询或工具计划]
    Q --> K[知识图谱 / 文档 / 工具]
    K --> R[带证据的回答]
```

本体论的作用不是替代 Agent，而是让 Agent 的理解和行动有更稳定的语义边界。

## 对比：没有本体论和有本体论

| 场景 | 只使用文本/RAG | 使用本体论增强 |
|---|---|---|
| 实体识别 | 依赖模型猜测 | 根据类、别名和关系归一化 |
| 查询关系 | 可能只召回相似段落 | 可沿明确关系做多跳查询 |
| 工具调用 | 主要依赖 Prompt | 可校验工具能力、参数类型和前置条件 |
| 权限判断 | 容易遗漏隐含关系 | 角色、资源、动作关系更明确 |
| 解释回答 | 只能引用文本 | 可以同时给出事实路径和文档证据 |

## 贯穿案例

企业知识助手需要回答：

```text
产品 A -> 属于 -> 模块 B
模块 B -> 包含 -> 功能 C
问题 D -> 影响 -> 功能 C
问题 D -> 有解决方案 -> 方案 E
```

Agent 可以沿着这条关系路径回答问题，而不是只找包含“问题 D”的文档。

## 练习

分别判断下面的问题更需要“文本相似度”还是“概念关系”：

1. “登录失败怎么处理？”
2. “登录失败会影响哪些模块？”
3. “谁有权限修改登录策略？”
4. “给我找一篇登录失败排查文档。”

## 本章小结

- RAG 解决“相关内容在哪里”。
- 本体论解决“概念是什么、彼此如何关联、哪些行为允许”。
- Agent 需要同时使用文本证据、结构化事实和语义约束。
