# 04. 怎么从业务里抽出本体

## 先看一个扎心的问题

> 决定做本体了。然后呢？
>
> "要不要把整个系统的代码都扒一遍？""要不要把公司所有业务都建模？""先建哪个模块？"
>
> 别急。**先想清楚一个问题：你到底想让 AI 帮你做什么业务判断？**
>
> 是"这个供应商还值不值得继续合作"？是"这个客户是不是高价值客户"？还是"这个需求该不该排期"？
>
> 想清楚这个，才知道本体该从哪开始建、建多大。

## 一句话说清

**建本体不是把公司所有业务都梳理一遍，而是"目标驱动、局部先行"——先挑一个最值钱的业务判断，圈最小范围，跑通一个闭环，再往外扩。**

## 第一步：先想"要解决什么业务判断"（第一性原理）

很多人做 AI 的顺序是反的：先采购模型、搭知识库、做聊天助手，再找业务价值——**就像先买了发动机，再想造什么车**。

正确顺序是先回答本质问题：**要把人的经验、组织规则、业务关系，变成系统能持续理解、能执行的能力。**

挑判断的时候，选那种"**依赖多维业务关系**"的，因为这才是本体能发力的地方：

| 业务判断 | 只看一条信息不行，要看 |
|---|---|
| 供应商能否继续合作 | 交付记录、延期条款、投诉、替代供应商、区域风险、未来项目依赖 |
| 客户是否高价值 | 毛利、回款、复购、服务成本、投诉、增长潜力、组织关系、行业周期 |
| 需求是否值得排期 | 需求价值、技术风险、交付成本、关联模块、依赖关系 |

> 反过来，如果只是"查个制度、写封邮件、总结会议"，那是高级搜索框，不需要本体。

## 第二步：梳理这个判断依赖哪些"实体和关系"

以"供应商合作价值评估"为例：

```
供应商 ─签订→ 合同 ─包含→ 交付节点
供应商 ─发生→ 交付记录 ─产生→ 质量异常
合同   ─约定→ 付款条款 ─对应→ 付款记录
供应商 ─关联→ 风险标记 ─触发→ 审批升级
```

把判断需要的实体列出来（供应商、合同、交付记录、付款记录、质量异常、风险标记），**再画它们之间的关系**——这就是本体的骨架。

### 附：从一句业务话里认概念（五类候选词）

梳理依赖时，常要面对一段业务描述（比如一段合同条款、一句需求）。里面冒出来的词怎么认？分五类：

| 候选词 | 判断标准 | 在本体里当什么 |
|---|---|---|
| **实体** | 能独立引用 | 类 + 实例（合同HT-001、项目A） |
| **事件** | 发生的业务事实 | 关系 或 类（看要不要单独查"延期过几次"） |
| **角色** | 谁参与 | 角色类（审批人王工） |
| **状态** | 现在什么阶段 | 枚举属性值（验收 pending / approved） |
| **动作** | 要执行什么 | 动作类（供权限/工具用：查询、触发验收） |

> **关键判断**：同一个词可能身兼多职——"验收"既是名词（实体）也可能是动作。分类的目的**不是贴标签，而是决定它在本体里当"类、属性还是关系"**。规则就一条：**你将来要不要单独查它？要，就当类或关系；只是贴个字段，就当属性。查询决定建模深度。**

## 第三步：盘点这些东西现在散在哪

实体和关系通常散落在五个地方：

| 载体 | 例子 | 处理方式 |
|---|---|---|
| 数据库 | 合同表、供应商表 | 直接读表结构，反推实体和字段 |
| 文档 | 合同 PDF、需求文档 | 从文档里抽概念（用上面的"五类候选词"方法） |
| **代码** | 一堆 if-else 的业务规则 | **代码是线索，不是本体本身** |
| 表格/Excel | 报价单、评审表 | 反推字段 |
| 员工脑子 | 特殊审批、隐性规则 | 业务访谈，把隐性知识问出来 |

### 关于代码，有个常见疑问：要不要把前后端代码全扒一遍？

**不需要全盘通读。** 记住三条：

1. **代码是线索，不是本体**——本体是业务抽象层，和用什么语言、什么框架无关。
2. **重点看后端**：前端大多是展示逻辑，业务规则主要埋在后端代码里（状态流转、判断条件）。
3. **两条路线**：
   - **轻量路线（推荐先走）**：先做业务访谈 + 读数据库表结构，搭出本体骨架，暂时不深扒代码；后期遇到规则对不上的再补。
   - **完整路线**：要把系统真实行为完全对齐，才需要解析后端逻辑，把硬编码的 if-else 提取成本体里的显式约束和行为。

> 长期目标：**业务规则沉淀到本体层，代码只负责执行**。这样以后改规则改本体就行，不用到处翻代码加 if。

## 第四步：最后才想"AI 怎么接"

本体骨架有了，数据映射有了，这时候才考虑 AI 形态：

```
问答（回答"这合同约束哪个项目"）
→ 分析预警（"供应商风险分超 80 自动告警"）
→ 流程建议（"这个风险该升级给谁"）
→ 自动执行（"自动发起比价→超标→升级审批"）
→ Agent 任务链（多步自主跑通）
```

**顺序别搞反**：先有业务判断和本体，再选 AI 形态。而不是先买模型再找场景。

## 落地五步法（把上面四步落成行动）

```
① 选目标：挑一个最值钱的业务判断（如供应商合作价值评估）
② 划边界：只保留 供应商/合同/交付/付款/质量异常/风险标记，人事、仓储、总账暂时不管
③ 建局部本体：定义实体、属性、关系、规则（五大件）
④ 数据映射 + 单点闭环：先把一个场景跑通，验证效果
⑤ 拿到收益再扩张：其他模块逐步加进来
```

**两条设计底线（避免后期返工）**：

- 实体定义尽量**标准化**（命名规范、字段通用），方便后续其他场景复用
- Schema 预留**扩展空间**（版本号、可新增实体/关系），别把结构写死

## 真实例子：供应商合作价值评估（完整走一遍）

1. **业务判断**：这个供应商还值不值得继续合作？
2. **依赖实体**：供应商、合同、交付记录、付款记录、质量异常、风险标记
3. **信息载体盘点**：合同在数据库+PDF、交付记录在交付系统、投诉在客服工单、特殊规则在老员工脑子里 → 业务访谈补齐
4. **AI 形态**：先做"风险分计算+告警"，跑通后升级"自动比价→超标→升级审批"任务链

> 这就是为什么同一套模型，在数据中台上跑 4 天、在本体架构上跑 2 小时——因为系统能直接沿"供应商→合同→交付→风险"这条关系链推理，而不是在海量碎片里检索。

## 动手试试

选一个你手头的业务，回答：

1. 你最想让 AI 帮你做的**一个**业务判断是什么？（一句话说清）
2. 这个判断依赖哪些实体？它们之间什么关系？
3. 这些信息现在散在哪？（数据库/文档/代码/人脑）
4. 最小范围跑通闭环，先圈哪几个模块？

## 一句话总结

**建本体的正确姿势：先想"要解决什么判断"，再圈最小范围建局部本体，数据映射跑通闭环，最后才接 AI。别一上来就扒全量代码、建全公司本体——那是自讨苦吃。**
