# 16. 本体论与权限、安全边界和异常处理

## 一分钟看懂本章

> **一句话**：权限不是写在 Prompt 里的"请小心"——本体定义"项目经理─能确认→合同风险"，PDP 统一决策、PEP 强制拦截，高风险动作必须人工审核并全程留审计。

```mermaid
flowchart LR
    U[项目经理] --> R[角色：project_manager]
    R --> A[动作：确认风险 confirm_risk]
    A --> X[资源：合同HT-001的风险R1]
    PDP[PDP 策略决策] --> D{allow / deny / approval}
    R --> PDP
    X --> PDP
    A --> PDP
    D -->|approval| H[人工审核]
    D -->|allow| PEP[PEP 执行确认]
    H -->|批准| PEP
    H -->|驳回| E[拒绝并审计]
```

**读图要点**：整条链路里没有人是"因为看起来像管理员就被放行"——谁（项目经理）、对什么资源（合同HT-001的风险R1）、做什么动作（确认风险），三个要素缺一不可，最后由 PDP 决策、PEP 强制拦截。

## 本章目标

- 用主体、角色、资源和动作描述权限关系。
- 区分本体语义判断、策略决策和业务执行。
- 识别类型错误、事实冲突、权限拒绝和工具失败。
- 设计重试、降级、人工接管和审计闭环。

## 1. 权限模型的四个核心对象

## 1.1 真实例子：只有项目经理才能确认风险

同样的动作，不同的人结果完全不同：

```text
普通用户（contract_clerk）："帮我确认风险 R1"
  → PDP 判定 deny，reason=role_missing（缺 project_manager 角色）

项目经理（project_manager）："我来确认风险 R1"
  → PDP 判定 requires_approval，创建审核请求
  → 审核人批准后，PEP 才执行 confirm_risk 工具
```

PDP 决策逻辑的骨架：

```python
def decide(user: User, action: str, resource: Resource) -> Decision:
    roles = ontology.roles_of(user)                    # [contract_clerk] 或 [project_manager]
    req = policy.required_roles(action, resource)      # confirm_risk 需要 project_manager
    if not req.issubset(roles):
        return Decision.DENY("role_missing")           # 结构化拒绝原因
    if policy.risk_level(action) == "high":
        return Decision.APPROVAL_REQUIRED              # 高风险 → 人工审核
    return Decision.ALLOW
```

**图 16-1：本体论、权限策略和执行边界**

**读图要点**：本体在底部给 PDP 提供**语义**——"project_manager─能确认→Risk"这种关系从哪来？本体定义的。PDP 根据当前主体、资源、动作和上下文做决策，PEP 在工具/API 入口强制执行。**三者不能混成一个 Prompt**，也不能让模型自己判断权限。

## 2. 权限决策树

```mermaid
flowchart TD
    R[收到动作请求<br/>用户要确认风险R1] --> T{主体和资源类型有效?<br/>用户是Human? R1是Risk?}
    T -->|否| E1[拒绝: semantic_invalid]
    T -->|是| P{主体拥有所需角色?<br/>project_manager?}
    P -->|否| E2[拒绝: role_missing<br/>普通用户不能确认风险]

    C -->|是| H{风险是否需要审核?<br/>risk_level=high?}
    H -->|是| A[创建审核请求<br/>项目经理审核]
    H -->|否| D[允许执行]
    A -->|approved| D
    A -->|rejected| E4[拒绝: human_rejected]
    D --> X[由 PEP 执行 confirm_risk]
```

**图 16-2：权限判断和拒绝路径**

**读图要点**：每层判断都对应一个**结构化拒绝原因**——`semantic_invalid`（类型错）、`role_missing`（没角色）、`prerequisite_missing`（前置条件缺）、`human_rejected`（人被驳回）。这些原因不能都返回"无权限"，要分别返回给前端展示、Agent 澄清和审计分析。

## 3. 异常分类

| 异常类别 | 示例 | 默认处理 |
|---|---|---|
| `semantic_invalid` | 输入实体不是 `Contract` | 不重试，要求修正或澄清 |
| `data_conflict` | 两个来源给出不同的风险等级 | 标记冲突，降低结论置信度 |
| `permission_denied` | 普通用户不能确认风险 | 拒绝并记录审计 |
| `approval_required` | 高风险动作 confirm_risk 需要审核 | 创建审核请求并暂停任务 |
| `tool_timeout` | 合同 API 超时 | 有界重试，超过上限后降级 |
| `tool_failed` | 工具返回业务错误（合同已归档） | 根据错误码决定重试或人工接管 |
| `evidence_insufficient` | 证据不足以确认风险 | 澄清、拒答或给出不确定性 |

## 4. 异常处理和人工接管

```mermaid

    C -->|语义错误| S[返回可修复字段<br/>risk_id 类型错误]
    C -->|权限拒绝| P[拒绝并审计<br/>role_missing]
    C -->|需要审核| H[项目经理看到等待审核]

    T --> Q{达到上限?}

    C -->|证据不足| A[澄清或拒答]
```

**图 16-3：异常分类、重试、降级和人工接管**

**读图要点**：恢复动作**取决于异常类别**——语义错误要补充输入（改 `risk_id` 类型）、权限拒绝直接拒绝不重试、工具超时可以有限重试、高风险走人工审核、证据不足用澄清而不是用重试掩盖知识缺口。右边红色分支是"降级为草稿"——降级结果不能泄露原本无权访问的证据。

## 5. 审计记录

关键动作至少记录以下字段：

```json
{
  "event_type": "tool_call_denied",
  "user_id": "user-001",
  "task_id": "task-001",
  "thread_id": "thread-001",
  "tool_id": "confirm_risk",
  "resource_id": "contract_ht001#risk_r1",
  "decision": "requires_approval",
  "reason_code": "high_risk_action",
  "policy_version": "policy-v3",
  "created_at": "2026-08-23T10:05:00+08:00"
}
```

审计记录的作用是回答"谁在什么任务中，基于哪个策略，对哪个资源提出了什么动作，结果如何"。它不应只保存最终答案。

## 6. 安全边界原则

1. Agent 不能自行提升角色或修改权限。（普通用户不能把自己"变成"项目经理）
2. 模型输出不能绕过 PEP、PDP 和业务 API 的校验。
3. 审核人批准的是明确的动作、资源和参数（批准"确认风险R1"），不是整个任务的无限授权。
4. 高风险动作默认使用 `dry_run`，正式执行必须有显式授权。
5. 失败降级不能泄露原本无权访问的证据。（降级回答不能暴露其他项目的合同内容）

## 7. 常见错误和排查

- **只在 Prompt 中说明权限**：Prompt 不是安全边界，必须在服务端强制执行。
- **所有拒绝都自动重试**：权限拒绝和语义错误通常重试无效。
- **审核人和普通用户混用身份**：审核动作必须有独立主体、角色和审计记录。
- **异常信息过于详细**：向普通用户返回可行动原因，但不要泄露内部策略和敏感资源。

## 8. 练习和自查

1. 为“发布解决方案文档”定义普通用户、审核人和服务账号的权限。
2. 设计 `requires_approval` 到 `approved` 的状态迁移条件。
3. 为工具超时、权限拒绝和证据不足分别设计响应结构。

## 本章小结

本体论提供权限和异常处理所需的语义对象，但不直接承担安全执行职责。真正可靠的系统必须把本体校验、策略决策、执行拦截、人工审核和审计记录连成闭环。
