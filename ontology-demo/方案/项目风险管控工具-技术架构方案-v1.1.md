## 1. 架构总览

### 1.1 Agent 认知架构全景

将需求文档 v1.1 的五阶段 Agent 能力（感知 → 推理 → 行动 → 报告 → 学习）映射为技术架构的四层一基座：

```mermaid
flowchart TB
    subgraph PRESENTATION[展示层 — Agent 表达]
        P1[仪表盘<br/>风险统计与趋势] --> P2[决策链回放<br/>时间线展示]
        P2 --> P3["关系图谱<br/>@xyflow/react"]
    end

    subgraph CORE[核心引擎层 — Agent 思考与行动]
        subgraph REASON[推理引擎]
            R1[规则匹配<br/>L1-L4 推理]
            R2[风险量化<br/>概率 × 影响]
            R3[闸门逻辑<br/>G01-G04]
        end
        subgraph LEARN[学习引擎]
            L1[驳回分析<br/>原因入库]
            L2[共进化<br/>模板优化提示]
        end
        subgraph ACT[行动引擎]
            A1[状态机<br/>待确认→已关闭]
            A2[决策记录<br/>五要素写入]
        end
    end

    subgraph PERCEPTION[感知层 — Agent 感知文档]
        S1[文档解析<br/>PDF/Word/Excel]
        S2[模板抽取<br/>规则式 + LLM]
        S3[审核队列<br/>人工确认/驳回]
    end

    subgraph KNOWLEDGE[知识基座]
        K1[本体引擎<br/>类·关系·属性]

        I1[项目隔离<br/>project_id]

    end

    PERCEPTION -->|要素候选| CORE
    CORE -->|风险信号| PRESENTATION
    CORE -.->|反馈| LEARN
    LEARN -.->|优化| PERCEPTION
    KNOWLEDGE -.->|查询/写入| CORE
```

## 2. 感知层（Perception Layer）

### 2.1 文档解析流水线

Agent 获取输入的第一步：将五类文档（PDF/Word/Excel）解析为结构化文本块。

```mermaid
flowchart TB
    subgraph INPUT[输入]
        IN1[合同 PDF]
        IN2[项目范围 Word]
        IN3[功能清单 Excel]
        IN4[原型文档 PDF]
        IN5[技术方案 Word]
    end
    subgraph PARSE[解析引擎]
        P1[文件类型识别]
        P2[pdfplumber<br/>PDF 按段落]
        P3[python-docx<br/>Word 按章节]
        P4[openpyxl<br/>Excel 按单元格/行]
        P5[编号生成<br/>D1-v1-12.2]
    end
    subgraph OUTPUT[输出]
        O1[文本块表<br/>doc_blocks]
        O2[文档版本表<br/>documents]
    end

    IN1 --> P1
    IN2 --> P1
    IN3 --> P1
    IN4 --> P1
    IN5 --> P1
    P1 --> P2
    P1 --> P3
    P1 --> P4
    P2 --> P5
    P3 --> P5
    P4 --> P5
    P5 --> O1
    P1 --> O2
```

**关键设计**：文本块编号格式 `文档ID-版本-段落号`（如 `D1-v1-12.2`），与 v1.1 需求 FR-10 的证据编号体系一致。

### 2.2 模板抽取引擎

Agent 的核心感知能力：按模板将文本块中的自然语言映射为本体要素。

```mermaid
flowchart TD
    IN[文本块<br/>D1-v1-12.2: SLA 30 分钟响应] --> T{选择模板}
    T -->|合同模板| CON[合同模板 ContractExtractor]
    
    subgraph CONTRACTOR[合同模板抽取流程]
        direction TB
        C1[字段定义<br/>交付范围/付款节点/验收条款/SLA/质保期/范围外]
        C2{LLM 是否可用?}
        C2 -->|是| C3[ontogpt LLM 抽取<br/>输出: 要素 + 置信度]
        C2 -->|否| C4[规则式兜底<br/>正则: 编号/金额/比例/日期<br/>关键词: 交付范围/验收等]
        C3 --> C5[要素候选<br/>含置信度 + 来源段落]
        C4 --> C5
    end
    
    CON --> CONTRACTOR
    C5 --> AUDIT[审核队列<br/>待用户确认]
```

**抽取引擎的内部结构**：

```mermaid
flowchart LR
    subgraph RULE[规则式抽取器 — 兜底]
        RE1[正则引擎<br/>合同编号 / 金额 / 日期]
        RE2[关键词匹配<br/>交付范围 / 验收条款 / 范围外]
        RE3[低置信度标记<br/>留空由人工补]
    end
    subgraph LLM[LLM 抽取器 — ontogpt]
        LE1[模板 Schema<br/>字段锚定本体属性]
        LE2[LLM 推理<br/>理解语义映射]
        LE3[置信度评分<br/>0-1 输出]
    end
    subgraph MERGE[合并器]
        M1[优先级: LLM > 规则式]
        M2[取高置信度结果]
        M3[无结果时标记空缺]
    end

    RULE --> MERGE
    LLM --> MERGE
    MERGE --> OUTPUT[要素候选列表]
```

### 2.3 审核队列

Agent 提交要素候选后，用户审核确认的交互流程：

```mermaid
flowchart LR
    AUDIT_IN[要素候选列表] --> A1{逐条审核}
    A1 -->|确认| A2[要素入库<br/>进入推理层]
    A1 -->|驳回| A3[记录驳回原因<br/>进入学习层]
    A1 -->|修改后确认| A4[修改值入库<br/>记录原始值]
    A2 --> NEXT[下一条]
    A3 --> NEXT
    A4 --> NEXT
```

## 3. 知识层（Knowledge Layer）

### 3.1 本体引擎

Agent 的知识基座：存储和查询本体模型（15 核心类 + 16 关系 + 18 属性 + 4 支撑类）。

```mermaid
flowchart TB
    subgraph STORE[本体存储]
        K1[classes<br/>JSON: 类名+属性列表+关系列表]
        K2[relations<br/>JSON: 源类+目标类+关系名]
        K3[versions<br/>版本快照 + 发布状态]
    end
    
    subgraph API[本体 API]
        Q1[查询: 类详情 / 关系 / 属性]
        Q2[CRUD: 类增删改查]
        Q3[发布: 草案→审核→发布→回滚]
    end
    
    subgraph VIZ[可视化]
        V1["@xyflow/react<br/>图谱渲染"]
        V2[点击节点跳转详情]
    end

    Q1 --> STORE
    Q2 --> STORE
    Q3 --> STORE
    V1 -->|读取| Q1
```

**本体变更发布流**的数据状态演变：

```mermaid
stateDiagram-v2
    [*] --> 草案: 新增/修改
    草案 --> 已提交: 提交审核
    已提交 --> 已发布: 审核通过
    已提交 --> 草案: 审核驳回
    已发布 --> 已回滚: 回滚到历史版本
    已发布 --> 草案: 再次修改
```

### 3.2 规则库

10 条预置规则以 DSL 形式存储，支持启停控制：

```
规则存储格式（SQLite rules 表）：
{
  "id": "R05",
  "name": "SLA 响应资源不足",
  "dsl": "sla.response_time <= 120",
  "type": "threshold",
  "risk_type": "运维资源风险",
  "default_level": "高",
  "enabled": true,
  "hit_count": 3
}
```

## 4. 推理层（Reasoning Layer）

### 4.1 L1-L4 推理架构

Agent 从要素到风险的推理分四个层次，逐层递进：

```mermaid
flowchart TB
    subgraph L1[L1 规则匹配 — 确定性推理]
        L1A[要素值 vs 规则阈值<br/>R01-R09 逐条检查]
        L1B[命中 = 条件成立<br/>输出: 风险信号 + 证据]
    end
    subgraph L2[L2 关系推演 — 关联推理]
        L2A[风险关联里程碑/需求<br/>检查多里程碑影响]
        L2B[R10 联动升级<br/>影响 ≥ 2 里程碑 → 上调]
    end
    subgraph L3[L3 阈值判定 — 等级计算]
        L3A[概率 × 影响 → 矩阵]
        L3B[红/黄/绿 三级输出]
    end
    subgraph L4[L4 LLM 辅助 — 深度分析]
        L4A[LLM 分析复杂风险<br/>MVP 关闭, P1 可启用]
    end

    INPUT[已确认要素集] --> L1A
    L1A -->|命中| L1B
    L1A -->|未命中| END[无风险]
    L1B --> L2A
    L2A --> L2B
    L2B --> L3A
    L3A --> L3B
    L3B -.->|可选| L4A
    L3B --> OUTPUT[风险信号 + 等级 + 证据链]
```

### 4.2 规则匹配流程（以 R05 为例）

```mermaid
sequenceDiagram
    participant E as 要素库
    participant R as 规则引擎
    participant R05 as R05 SLA规则
    participant MAT as 矩阵计算器
    participant O as 风险台账

    E->>R: 提交已确认要素集
    R->>R05: 检查 sla.response_time
    R05-->>R: sla.response_time=30, 阈值<=120 ✅ 命中
    R->>R: 记录命中规则+字段值+证据段落
    R->>MAT: 请求计算等级
    MAT-->>R: 初始等级: 高（规则预设）
    R->>O: 输出风险信号: 运维资源风险·高
    Note over R,O: 含证据引用: D1-v1-12.2
```

### 4.3 闸门逻辑执行

闸门是 Agent 的自我约束机制，在关键动作前拦截检查：

```mermaid
flowchart TD
    subgraph TRIGGER[触发 — 4 类关键动作]
        G1[关闭风险]
        G2[确认里程碑完成]
        G3[提交进度]
        G4[发布本体]
    end
    subgraph CHECK[检查子流程]
        C1[查询风险状态 / 缓解措施 / 关联里程碑]
        C2[查询延期登记 / 草案审核状态]
        C3{与闸门规则<br/>G01-G04 逐条比对}
    end
    subgraph RESULT[结果]
        PASS[✅ 放行]
        BLOCK[⛔ 拦截 + 提示]
        EXEMPT[⚠️ 可申请豁免]
    end

    TRIGGER --> CHECK
    CHECK -->|未命中任何规则| PASS
    CHECK -->|命中拦截规则| BLOCK
    BLOCK -->|用户裁决| EXEMPT
```

## 5. 行动层（Action Layer）

### 5.1 风险状态机实现

Agent 管理风险的全生命周期，每次状态变更自动记录决策五要素：

```mermaid
flowchart LR
    subgraph STATE[状态流转]
        S0[待确认] -->|PM 确认| S1[已确认]
        S0 -->|PM 驳回| S7[已忽略]
        S1 -->|指派+缓解措施| S2[处置中]
        S2 -->|措施完成| S3[已缓解]
        S3 -->|验证通过| S4[已关闭]
        S3 -->|验证未通过| S2
        S4 -->|风险复发| S2
    end
    subgraph DECISION[决策记录 — 每次状态变更]
        D1[决策人: PM]
        D2[时间: 自动]
        D3[依据证据: 段落引用]
        D4[决策内容: 状态变化原因]
        D5[结果: 新状态]
    end
    STATE -->|触发| DECISION
```

### 5.2 决策链数据流

Agent 记录完整的追溯链：文档段落 → 要素 → 规则 → 风险 → 处置：

```mermaid
sequenceDiagram
    participant DOC as 文档段落
    participant EL as 要素
    participant R05 as 规则R05
    participant RSK as 风险
    participant DEC as 决策记录

    Note over DOC: D1-v1-12.2
    DOC->>EL: 抽取: SLA 响应时限=30分钟
    EL->>R05: 检查: response_time <= 120
    R05->>RSK: 命中 → 生成风险信号
    RSK->>DEC: PM 确认风险 → 记录决策
    DEC-->>RSK: 决策写入 (五要素)
    Note over RSK,DEC: 决策链可回放: DOC→EL→R05→RSK→DEC
```

**决策记录表结构**：

```
字段        类型        说明
───        ────        ───
id          text        UUID
risk_id     text        关联风险
actor       text        决策人
timestamp   datetime    决策时间
evidence_ref text       证据段落ID
action      text        决策内容 (确认/指派/关闭等)
result      text        结果状态
```

### 5.3 MCP 接口层（预留架构）

Agent 的核心能力对外暴露为 MCP 工具，供其他 Agent 调用。MVP 先以 REST 接口实现，后续包装为标准 MCP Server：

| MCP 工具名 | 功能 | REST 路径（MVP） |
|---|---|---|
| `query_ontology` | 查询本体类/关系/属性 | `GET /api/v1/ontology/classes` |
| `get_risk_feed` | 获取某项目风险清单 | `GET /api/v1/projects/{id}/risks` |
| `create_risk` | 登记风险 | `POST /api/v1/projects/{id}/risks` |
| `check_rule` | 检查某要素是否命中规则 | `POST /api/v1/rules/check` |

## 6. 学习层（Learning Layer）

### 6.1 共进化闭环

Agent 从用户的审核反馈中持续优化感知和推理能力：

```mermaid
flowchart TB
    subgraph FEEDBACK[用户反馈]
        F1[要素确认 ✅]
        F2[要素驳回 ⛔<br/>含驳回原因]
        F3[修改后确认 🔄<br/>含原始值和修正值]
    end
    subgraph ANALYZE[Agent 分析]
        A1[统计驳回率<br/>模板维度 / 字段维度]
        A2["识别模式<br/>某字段经常被驳回 → 模板需优化"]
        A3["关联规则命中率<br/>某规则从未命中 → 可调整"]
    end
    subgraph OPTIMIZE[优化提示]
        O1[标记待优化模板]
        O2["生成优化建议<br/>付款节点字段匹配率仅 60%"]
        O3[规则调优建议<br/>MVP 仅记录, P1 自动提示]
    end

    FEEDBACK -->|数据入库| ANALYZE
    ANALYZE --> OPTIMIZE
    OPTIMIZE -.->|人工确认后同步| PERCEPTION[感知层模板]
    OPTIMIZE -.->|人工确认后同步| REASONING[推理层规则]
```

**共进化数据流**：

| 数据 | 来源 | 用途 |
|---|---|---|
| 驳回原因 | 审核队列（FR-14） | 模板字段精度分析 |
| 原始值 vs 修正值 | 修改后确认 | 模板抽取误差分析 |
| 规则命中统计 | 规则引擎 | 规则有效性评估 |
| 审核耗时 | 审核队列 | 感知效率评估 |

```mermaid

    participant ACT as 行动服务
    participant DB as SQLite

    FE->>API: POST /api/upload

    PER->>DB: 写入文本块 doc_blocks
    
    U->>FE: 触发抽取
    FE->>API: POST /api/extract
    API->>PER: 调用模板抽取引擎
    PER->>DB: 写入要素候选
```

## 附录：关键技术决策

| 决策 | 方案 | 理由 |
|---|---|---|
| 前端框架 | React 19 + Vite + AntD | 10 个参考项目中 6 个用 React 生态，图谱库 @xyflow/react 也在 React 侧 |
| 后端框架 | Python FastAPI | 9/10 参考项目用 Python：ontogpt/ontocast/semantica 等成熟组件全在 Python 生态 |
| 数据存储 | SQLite 单文件 | MVP 单机模式，避免 Postgres/Redis 运维开销（P2 升级） |
| LLM 集成 | ontogpt（直接 import） | 同进程调用免服务间网络开销，LLM 默认关闭不影响核心流程 |
| 文档解析 | pdfplumber + python-docx + openpyxl | Python 生态成熟库，合同/Word/Excel 全覆盖 |
| 规则推理 | semantica Rete 参考实现 | 10 条预置规则轻量化，无需引入复杂规则引擎 |
| 图谱可视化 | @xyflow/react | 参考项目 jonex/trustgraph/semantica 同款，交互体验好 |
| 架构模式 | 后端一体化（非微服务） | 单一写入者避免锁冲突，MVP 阶段不需要横向扩展 |
