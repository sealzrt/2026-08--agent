### 0.2 术语小词典（⭐ 重点，随时回来查）

按"咱们方案里会出现、且比较难懂"排序：

| 术语 | 白话解释 | 类比 |
|------|---------|------|
| **本体（Ontology）** | 对某个领域"有哪些东西、分几类、互相什么关系"的正式定义。咱们方案里的 15 个类（合同/项目/风险/需求…）、16 条关系（合同约束项目、需求变更导致风险…）就是一个领域本体 | 公司的**组织架构图 + 规章制度** |
| **OWL** | 本体的国际标准语言（W3C 制定），能表达"类是啥、谁是谁的子类、属性有啥限制"，还支持机器推理 | 本体的"官方公文格式" |
| **RDF** | 描述数据的国际标准：一切知识都写成"主语-谓语-宾语"三条腿（叫**三元组**）。例：`合同A --约束--> 项目B` | 知识的最小积木（主谓宾） |
| **RDFS** | RDF 的简单扩展，能定义类和属性（比 OWL 弱，但简单） | 本体的"简化版" |
| **Turtle（.ttl）** | RDF/OWL 本体的一种**文本文件格式**，人比较容易读和写 | 本体的"txt 文件" |
| **TBox / ABox** | 本体的两个层次：**TBox** = 概念层（"风险"类、"延期导致"关系，即**模板**）；**ABox** = 实例层（"合同A 的验收风险"这个具体记录，即**填好的内容**） | 模板（TBox） vs 填好的表格（ABox） |
| **SKOS** | 管"术语表/词表"的标准：概念、同义词、上下位词。适合管理"合同术语表"这类受控词汇 | 公司统一的**术语字典** |
| **三元组（Triple）** | RDF 知识的基本单位：主语-谓语-宾语。知识图谱就是海量三元组 | 一句话：谁-做了什么-对谁 |
| **知识图谱（KG）** | 用"点（实体）+ 边（关系）"组织起来的知识网络 | 从"Excel 表格"升级成"带箭头的思维导图" |
| **SPARQL** | 知识图谱的**查询语言**，相当于"图数据库的 SQL"。想查"所有受合同约束的项目"就写一条 SPARQL | 数据库的 SQL 语句 |
| **推理（Reasoning）** | 机器根据本体里已有的规则自动"想出新结论"。例：合同约束项目、项目包含计划 → 机器自动推出"合同间接影响计划"；HermiT/ELK 是两种推理引擎 | 数学里的**三段论推导** |
| **Datalog / Rete** | 两种推理/规则引擎的算法：Datalog 偏逻辑规则推导，Rete 是高效规则匹配算法（经典专家系统用） | 不同的"自动推导引擎" |
| **SHACL** | 检查"数据是否符合规定形状"的标准：比如"每个风险必须有等级，等级只能是高/中/低"。不合规直接报错 | Excel 里的**数据有效性校验** |
| **PROV-O** | W3C 溯源标准：记录"这条数据是哪来的、谁生成的、什么时候"。审计时能回答"为什么这么判" | 食品的**溯源二维码** |
| **MCP（Model Context Protocol）** | 让 AI 模型调用外部工具/数据的**标准接口协议**。装了 MCP 服务的程序，任何支持 MCP 的 Agent 都能即插即用 | 电脑的 **USB 接口**（插上就能用） |
| **Extractor 模式** | OntoGPT 的核心理念：为每个领域预先定义一个**"抽取模板"**（要抽哪些类、哪些属性、哪些关系），LLM 照着模板从文本里抓信息、填格子。模板=本体，输出=结构化数据 | 给 LLM 一张**答题卡**，让它从文章里找答案填进去 |
| **Grounding（接地/锚定）** | 让 LLM 的输出"锚定"在标准词汇上——比如模型说"延期"，自动对齐到本体里的"里程碑延期"概念，保证说法统一 | 翻译时**对照官方词典**，不许自由发挥 |
| **本体学习（Ontology Learning）** | 用算法/LLM 从一堆文档里**自动提炼本体**（哪些概念、什么关系） | 从海量文件里自动归纳出**分类体系** |
| **本体对齐/匹配（OM）** | 两套本体（比如公司 A 和公司 B 的术语体系）要合并时，自动找到"哪个概念和哪个概念是同一个意思" | 两个部门术语表的**对照映射** |
| **GraphRAG** | 传统 RAG（检索增强）只做"相似度找文章片段"；GraphRAG 先建知识图谱，再沿着关系找答案，能回答"跨了 3 层关系"的问题 | 从"查目录"升级成"顺着关系网找人" |
| **超图（Hypergraph）** | 普通图的一条边只能连 2 个点；超图的一条边能连**任意多个点**（一条边就是一个小集合）。适合描述"一份合同 + 项目经理 + 客户 + 验收标准 + 时间"这种**多方关系** | 群聊 vs 一对一私聊 |
| **N-Quads** | RDF 的扩展格式：三元组加第 4 个字段（所属图/上下文），能表达"这条知识属于哪个场景" | 每条知识贴一张**便签注明出处** |
| **语义差距** | 同一个词在不同系统里意思不一样（比如 A 系统的"验收"和 B 系统的"验收"），导致数据对不上 | 方言差异：都是"番茄"，有人叫西红柿 |
| **L1-L4（识别架构）** | 咱们方案的风险识别四层：**L1** 规则引擎（确定条件→触发）、**L2** 关系推演（沿本体传导）、**L3** 阈值信号（数据偏差预警）、**L4** LLM 辅助（大模型读文档） | 风险识别的"四道防线" |
| **M1-M5（里程碑）** | 咱们方案的开发节奏：**M1** 工程骨架（已在进行）→ **M2** 本体建模工作台 → **M3** 业务数据管理 → **M4** 自动识别流水线（核心价值）→ **M5** 仪表盘+图谱展示 | 盖楼的"打地基→砌墙→装水电→精装→验收" |
| **Nitro server** | Nuxt 3 自带的**后端服务层**（Node.js），`server/api/*.ts` 写接口。咱们工具的 REST API 都跑在这里 | 房子的"管道间"，前端和数据库都通过它连接 |
| **可嵌入 Nitro server 直接复用** | 这句原意是"Python 写的 ontocast 可以当库直接嵌进 Nuxt 后端用"。⚠️ **实际情况要澄清**：Nitro 是 Node.js 运行时，**不能直接 import Python 库**。真正可行的接入方式是：① 把 ontocast 跑成独立 REST 服务（`ontocast serve`），Nitro 用 HTTP 调它；② 用 Node 的 `child_process` 调它的 Python 命令行。效果上"能复用"，方式上"走网络/子进程" | 电饭煲不能塞进微波炉里，但可以插同一个插座 |
| **VKG（Virtual Knowledge Graph）** | 不把数据搬进图数据库，而是"虚拟地"用 SPARQL 直接查询原有数据库（关系型/SQL），让老数据看起来像知识图谱 | 不搬家，但给你一把"万能钥匙"能翻任何抽屉 |

## 2. ontopilot（DeepLethe，437★，39 分，第 1 名）

### 2.1 一句话白话

一个"**本体工厂**"：把政策文件、产品说明书、操作手册等文档，加工成"分类体系（TBox）+ 术语表（SKOS）+ 实例数据（ABox）"，全程有人审核、有版本管理、能发布、能回滚，还能让 Agent 通过 MCP 直接用。

> 📜 **开源协议**：**Apache 2.0**：可商用、可修改、可闭源，保留版权声明即可；非传染性

### 2.2 它是干什么的（白话）

大多数"让 LLM 生成本体"的工具是一次性玩具——模型吐一坨东西，没人审核，错了也不知道。OntoPilot 的思路是**把本体生产变成一条正规流水线**：

1. **文档进来**：支持 PDF/Word/Excel/Markdown/CSV 批量解析（结构化分块）
2. **AI 起草**：LLM 从文档块里抽取类、属性、关系、实例
3. **人审核**（这是它的灵魂）：4 个审查队列——冲突审查（两个说法矛盾）、实体消歧（"Ocean Explorer One"和"OE-1"是不是同一个？）、术语审查、实例验证；审核结果**沉淀为记忆**，下次同样的歧义自动解决
4. **版本发布**：草稿→已审查→已发布三级状态，发布前有质量门禁（有冲突/未决项就不许过），支持语义 Diff（两个版本差在哪）和回滚
5. **对外服务**：REST API、只读 SPARQL、MCP——下游系统和 Agent 按版本拉取本体

它的一个亮点：**每条结论都能溯源**——这条本体是从哪个文档块、用哪个模型、哪版 prompt、谁审核的，全部有记录。这正是咱们风险管控要的"审计追溯"。

### 2.3 架构要点

```
React Web UI → FastAPI 后端 → PostgreSQL（人/角色/审核状态/审计记录）
                           → Oxigraph（RDF 图存储：TBox/SKOS/ABox 分图层）
                           → 工件存储（原始文档、不可变发布快照）
                           → 模型端点（OpenAI 兼容的 chat/embedding）
MCP Agent → /mcp 接口（读/提案/编辑/审核/发布工具，带权限分级）
```

- 分层清晰：**TBox / SKOS / ABox 放在命名图（Named Graphs）里分开管理**，发布时只投影已发布版本
- 本地开发可用 SQLite（正好咱们也是 SQLite），生产用 PostgreSQL
- 内置一个"浮动 Agent"：感知当前页面和选中的本体节点，自动调用只读 MCP 工具查看结构，**变更必须经人工确认**（语义预览 → 人工点确认 → 原子提交，Agent 从不直接写）

### 2.4 对咱们工具的价值

| 借鉴点 | 白话说明 | 落到哪个里程碑 |
|--------|---------|--------------|
| **文档→本体→审核→发布流水线** | 咱们 M4 的五类输入文档（合同/范围/功能清单/原型/技术方案）正是"文档→本体"的输入；它的"AI 起草+人工确认"和方案 4.2 的"⑥人工确认"完全同构 | M4 |
| **审查队列设计** | 冲突/消歧/术语/验证四类队列，咱们的风险识别结果确认流程（方案 4.2 第 6 步）可以照抄交互 | M4 |
| **审核记忆沉淀** | "这次确认过的消歧，下次自动处理"——咱们的"风险规则自动演进"可以借鉴 | M4 之后 |
| **语义 Diff + 版本发布** | 本体改了啥、谁批准的、能不能回滚——风险台账版本管理的好模板 | M2 |
| **中文支持** | 官方支持简体中文界面和中文 prompt，咱们是中文团队，学习成本低 | — |

### 2.5 落地注意点

- ⚠️ **面向本体工程师而非业务用户**：交互偏专业（TBox/ABox/SKOS 术语），咱们的 PM/总监用户需要做"翻译层"
- ⚠️ 社区规模还小（437★），版本未到 1.0（README 明确写"reach 1.0"在 roadmap 上），生产依赖需谨慎
- 抽取效果依赖模型配置（默认 deepseek-chat + bge-m3，恰好国产模型可接入）

## 3. ontocast（growgraph，228★，39 分，第 2 名）

### 3.1 一句话白话

一条把"**文章变成知识卡片**"的流水线：它一边从文档里抽取事实（三元组），一边**顺手升级自己的抽取模板（本体）**——模板和内容共同进化，最后输出可查询的 RDF 知识图谱。

> 📜 **开源协议**：**Apache 2.0**：可商用、可修改、可闭源，保留版权声明即可；非传染性

### 3.2 它是干什么的（白话）

很多抽取工具把文本变成三元组就完事了，本体（模板）要你另找人维护。OntoCast 的核心特点是**本体与事实并行共进化**：

- **两条并行流水线**：一条跑"本体循环"（ontology loop：根据文档片段生成/更新本体），一条跑"事实循环"（facts loop：按当前本体抽取事实），用 map/reduce 方式并行处理文档块
- **增量更新**：抽完一批不重新生成整个图，而是产出 **GraphUpdate 补丁**（插入/删除操作），省 token 也省算力
- **实体消歧**：同一个实体在多段文本里出现（"张总"和"张伟"），用向量相似度+符号规则对齐
- **数据校验**：内置 SHACL 形状校验 + 不变量检查，**发现不合规可以不调 LLM 自动修复**（省钱）
- **溯源**：RDF 1.2 provenance，每条事实知道来自哪段文本（可关闭）
- **引导种子本体**：你提供自己的本体（.ttl 格式）作为"种子"，它抽取时就严格按你的类/关系来——这点对咱们特别重要，因为咱们已经有 15 类 16 关系的领域本体草案

### 3.3 架构与接入方式

- 三种运行形态：**REST 服务**（`ontocast serve`，POST /process 传文件）、**批处理 CLI**、**嵌入式**（作为 Python 库：`ontocast_tools` 挂进 LangChain Agent、`make_ontocast_node` 挂进 LangGraph、`run_unit_pipeline` 单段处理）
- 存储：默认内存 pyoxigraph；配 Fuseki 可持久化；支持租户/项目隔离（tenant/project 参数——跟咱们的 projectId 多项目隔离思路一致）
- LLM 缓存：磁盘缓存、并发限制、批量预热，控成本的设计到位

⚠️ **关于"可嵌入 Nitro server 直接复用"的澄清**：Nitro 是 Node.js 运行时，**没法直接 import 这个 Python 库**。实际可行的两种接法：
1. `ontocast serve` 起独立服务（端口 8999），Nuxt 的 `server/api/` 里用 `fetch` 调它——**推荐，解耦干净**
2. Node 用 `child_process` 调 `ontocast process` 命令行

### 2.4 对咱们工具的价值

| 借鉴点 | 白话说明 | 落到哪个里程碑 |
|--------|---------|--------------|
| **要素抽取+本体入库一体化** | 方案 4.2 流水线第②③步（要素抽取→规则匹配）的现成实现参考；用咱们的本体做种子，抽取结果直接对齐 15 类 16 关系 | M4 核心 |

## 4. semantica（semantica-agi，10619★，38 分，第 3 名）

### 4.1 一句话白话

### 4.2 它是干什么的（白话）

金融、医疗这类监管严格的行业，AI 批了贷款、调了药量，监管问"**为什么？**"——传统 RAG 答不上来（只有向量相似度，没有记录）。Semantica 的回答是：所有决策都变成**一等公民对象**（decision record），带完整因果链：

```
add_causal_relationship(决策A, 决策B)           → 连因果边
trace_decision_chain(决策B)                    → 回溯整条因果链
check_decision_rules(规则集)                   → 策略合规门禁
export(审计轨迹)                               → 导出 W3C PROV-O 格式交给监管
```

翻译成咱们的场景：**每个风险的识别/确认/驳回都是一条"决策记录"**——谁在什么时候、依据哪份文档、按哪条规则判的，全部可查。这就是方案里"决策有据可查、审计追溯"的现成底座。

### 4.3 核心能力与架构

```
Sources → Ingest → Parse → Normalize → Split → Extract → 冲突检测 → 去重

→ 多语言图存储（RDF 与 LPG） → 导出 / 可视化 / REST · MCP · CLI
```

关键能力：
- **确定性推理**：Forward chaining、Rete 网络、Datalog、SPARQL——推理路径完全可解释（不是黑盒）
- **本体治理**：SHACL 约束、冲突检测、合规规则、**OWL 生成**、SKOS 词汇管理 + 可视化编辑器

- **多语言图存储**：RDF 系（Oxigraph/Blazegraph/Jena/RDF4J）+ 属性图系（Neo4j/FalkorDB/AGE/Neptune）+ 向量库，可切换不锁死

- **接入方式**：`pip install semantica`、MCP server、REST、CLI、Agno/CrewAI 原生支持

## 6. ontogpt（Monarch Initiative，978★，37 分，第 5 名）

### 6.1 一句话白话

给 LLM 发"**答题卡**"：你预先定义好模板（要抽哪些类、属性、关系），它照着模板从文章里抓信息、填格子，输出结构化的、和标准本体对齐的数据。

> 📜 **开源协议**：**BSD-3-Clause**：宽松（同 MIT 级别），保留版权声明、禁止用 Monarch 机构名义做背书

### 6.2 它是干什么的（白话）

生物医学领域权威机构（Monarch Initiative）出品。核心方法是 **SPIRES**（发表于 Bioinformatics 2024）：**结构化提示词 + 递归语义抽取**。

它的工作方式：

1. 选一个**模板（extractor）**：比如 `drug` 模板定义了"药物（名称、适应症、副作用、相互作用…）"要抽什么
2. LLM 读文本，按模板输出结构化对象（JSON 格式的类实例）
3. 结果自动**对齐（grounding）**到标准本体词汇（比如"carvedilol"这种药物名对齐到权威药物本体）——保证"说的是同一个东西"
4. 输出就是"填好的答题卡"，直接入库

它跟"直接让 LLM 总结"的区别：**有模板约束 → 输出稳定、可校验、可批量入库**；**本体锚定 → 术语统一，不会今天叫"延期"明天叫"延误"**。

模型支持很广：LiteLLM 接 OpenAI/Anthropic/Mistral/Groq/Cohere/Vertex 等，也支持 **Ollama 本地模型**（`ollama/llama3` 这种前缀）——跟咱们方案"OpenAI 兼容 / Ollama 可插拔"完全对路。

### 6.3 架构要点

- 轻量 Python 包：`pip install ontogpt`，命令行为主（`ontogpt extract -i 文本 -t 模板`），附带极简 Web 应用
- 依赖 oaklib（生物医学本体工具库）做 grounding，用 runoak 管理模型凭据
- extractor（模板）是 Python 类，可以自己定义——**这是它最有迁移价值的部分**

### 6.4 对咱们工具的价值

| 借鉴点 | 白话说明 | 落到哪个里程碑 |
|--------|---------|--------------|
| **Extractor 模式**（用户点名的词） | 为每个领域定义"抽取模板"（类/属性/关系），LLM 照模板填格子。咱们可以给"合同条款抽取"定义模板（验收条款、付款节点、交付范围、违约条款…），给"需求描述"定义模板（编号、优先级、状态、变更次数…） | M4 L4 |

## 7. trustgraph（TrustGraph AI，2597★，36 分，第 6 名）

### 7.1 一句话白话

多系统之间的"**公共语境层**"：用一张**超图**把各系统（销售、财务、工单…）的数据连起来统一语义，AI 问什么都有据可查，Agent 的行为不只是可追溯，而是**可加密验证**。

### 7.2 它是干什么的（白话）

它用一个经典相声解释问题：棒球场上有个队员叫"Who"（谁），主持人问"Who is on first?"（谁在一垒？），AI 把"Who"当成疑问词就答错了——**两个系统（或人与 AI）对同一个词理解不一致，就会出乱子**。企业里也一样：销售的"验收"和财务的"验收"可能不是一回事。

TrustGraph 的解法：用 **RDF/OWL 标准把语义钉死**（"Who"是一个球员类的实例，playsPosition 指向一垒），再用 **超图** 表达复杂关系——普通图一条边只能连 2 个点，它的图一条边能连"文档+作者+审批经理+合规政策+时间"整个事件。

关键能力：
- **BYOO（自带本体）**：把自己的 OWL 本体加载进去，所有摄入数据自动按本体做语义合规——**这条对咱们最有用**：把咱们的 15 类 16 关系本体导进去，数据自动对齐
- **LLM 抽取入图**：PDF/API/数据库等原始数据，用 LLM 抽实体关系直接进超图
- **Hyperflows**：Agent 工作流，每一步可以配不同的 LLM 和不同的图访问权限（轻模型分类→重模型推理，按规则路由）

- **上下文管理**：Workspaces（隔离）/ Collections（知识库分区）/ Context Cores（可插拔的知识包）
- **自带开源 LLM 推理栈**：vLLM/TGI/Ollama 等，数据不出内网（离线部署都行）
- 全套基础设施自己带：Cassandra（图数据）+ Qdrant（向量）+ Garage（文件）+ Pulsar/RabbitMQ（消息），**不依赖外部 API key**

### 7.3 架构要点

- 部署：`npx @trustgraph/config` 生成 docker-compose/K8s 配置，一键起（本地 Docker/Podman/Minikube 都行）
- UI 全家桶：Agent Console（流式问答+实时解释追踪）、GraphRAG View（可视化解释 DAG）、Context Explorer（3D 图浏览）、**Ontology Workbench（本体编辑器：类/属性树、OWL/XML 与 Turtle 双向导入导出、循环依赖检测、安全删除确认）**——这个本体编辑器交互可以做咱们 M2 的参考

## 10. OpenCrab（AlexAI-MCP，102★，36 分，第 9 名）

### 10.1 一句话白话

一个"**本体操作系统**"：把世界万物分成 **9 个语义空间**（主体、资源、证据、概念、主张、社区、成果、杠杆、政策），所有数据都能归位进格子，Agent 通过 **MCP 插件**即插即用地读写——本体的能力变成"插座"。

> 📜 **开源协议**：**MIT**：最宽松，商用/闭源随意，保留版权声明即可

### 10.2 它是干什么的（白话）

OpenCrab 由两部分组成：**LocalCrab**（本地本体工厂：爬取/解析/OCR/证据索引/Neo4j 校验，纯本地跑）+ **OpenCrab SaaS**（托管生态，闭源）。开源部分核心是 **MetaOntology OS**：

- **9 个语义空间**是它的世界模型：
  - `subject`（人/角色）、`resource`（文档/工具/API）、`evidence`（原始观察/日志）、`concept`（概念/类）、`claim`（有证据支撑的断言）、`community`（相关概念的聚类）、`outcome`（KPI/风险/影响）、`lever`（可调的控制开关）、`policy`（权限/治理规则）
  
  对照咱们方案：风险（Risk）≈ `outcome`，文档（Document）≈ `resource`，干系人 ≈ `subject`，识别规则 ≈ `policy`——思路很接近，但它是通用 9 格，咱们是 15 类专用本体
- **MCP 工具全家桶**：`ontology_add_node`/`add_edge`（写图）、`ontology_query`（混合查询：向量+BM25+图）、`ontology_impact`（影响分析 I1-I7）、`ontology_rebac_check`（权限检查）、`ontology_ingest`（文本入库）——本体能力全部 MCP 化
- **CrabHarness 控制平面**：爬什么、谁执行、证据够不够、能不能晋升发布，全程留痕
- **Pack v1 打包**：本体交付物打成标准 ZIP（图+证据+质量报告+Neo4j 导入脚本），可复现、可分发

### 10.3 架构要点

- 本地运行：`pip install -e .` + `opencrab serve`，数据用 SQLite + JSON + Chroma（本地向量），**默认纯本地**
- 存储适配器：Neo4j / Chroma / Mongo / SQL 多后端可换
- 接入 Agent：`claude mcp add opencrab -- opencrab serve` 一行挂载
- 许可证 MIT（最宽松）

### 10.4 对咱们工具的价值

| 借鉴点 | 白话说明 | 落到哪个里程碑 |
|--------|---------|--------------|
| **本体能力 MCP 化** | 将来咱们工具做完，把"风险查询/本体浏览/规则查询"做成 MCP server，外部 Agent（Claude Code 等）即插即用——工具从"Web 应用"升级为"Agent 可调用的服务" | M5 之后 |
| **9 语义空间设计** | 它的 outcome（风险/KPI/影响）+ policy（治理规则）+ evidence（证据）三格联动，正好对应咱们"风险 + 规则 + 审计追溯" | 架构参考 |
| **Impact 分析（I1-I7）** | 本体操作的影响预评估——咱们 M2 建模时改一个类会牵连哪些数据，可以先算影响再动手 | M2 |
| **本地优先 + 多存储适配** | SQLite 起步、可换图库——与咱们的数据架构策略一致 | M3 |

### 10.5 落地注意点

- ⚠️ 102★ 社区极小，概念超前（"MetaOntology OS"这种宏大叙事），落地验证少
- ⚠️ SaaS 部分闭源，只有本地引擎开源；项目形态还在快速变化期
- 价值主要在"MCP 暴露本体"这个**模式**，而不是它的 9 格本体本身（咱们有自己的领域本体）

## 11. PRD-driven-context-engineering（mattgierhart，184★，35 分，第 10 名）

### 11.1 一句话白话

一个"**文档即记忆库**"的方法论：给产品文档里的每条重要决策发一个**唯一编号**（比如 BR-004 业务规则、UJ-101 用户旅程），人和 AI 都靠编号引用，AI 干活前先查编号，再也不"失忆"；文档没通过门禁就不许进入下一阶段，从机制上**防住需求蔓延**。

> 📜 **开源协议**：**MIT**：最宽松，商用/闭源随意，保留版权声明即可

### 11.2 它是干什么的（白话）

作者观察到 AI 编程的三大记忆问题：瀑布式"写死文档"、敏捷"记忆碎片化"、AI 时代"模型隔夜失忆"。解法是把文档当成**基础设施**（Memory as Infrastructure）：

- **Source of Truth（SoT）文件**：14 个事实文件（业务规则 BR-、用户旅程 UJ-、API 契约 API-、风险 RISK- 等 21 种 ID 类型），**零数据库、纯 Markdown、放 git 里**，每条决策一个编号
- **渐进式 PRD**：PRD 是带门禁的工作流（v0.1 问题定义 → v0.5 红队评审 → v0.7 开发 → v1.0 增长），**每个阶段有 Definition of Done，不达标不许前进**——AI 不可能一口气把架构拍完，需求蔓延在机制上被挡住
- **就绪度评分**：`readiness.py` 给仓库打分（SoT 文件质量 → EPIC 依赖 → 阶段门禁三层），分数不够就列出"先修哪个文件"，PASS/WARN/BLOCK 三种退出码
- **开发图**：代码里写 `@implements BR-004` 标签，AST 扫描生成 devgraph.json，能检测"规格写了但代码没做""代码做了但规格漂了"
- **Agent 小队**：4 个角色 Agent（战略/设计/开发/运维）各有 MEMORY.md，跨 EPIC 沉淀经验
- 47 个 Skills + hooks（SessionStart 注入阅读顺序、PreToolUse 校验 EPIC 等），**纯文件驱动、离线可用、fork 即用**

### 11.3 对咱们工具的价值

| 借鉴点 | 白话说明 | 落到哪个里程碑 |
|--------|---------|--------------|
| **编号化决策 + 门禁** | 需求/范围管控的直接对应：合同条款编号化，需求变更必须引用条款编号，无编号的变更视为蔓延风险——拦截需求蔓延的机制性方案 | M3/M4 |
| **就绪度评分** | 类似咱们的"风险就绪度"：文档齐不齐、确认没确认，先量化再干活 | M4 |
| **规格与代码一致性检测** | 相当于"合同条款 vs 实际交付"的自动对账（@implements 标签思路），L3 信号的轻量实现 | M4 之后 |
| **文档即知识图谱** | 纯 Markdown + 编号交叉引用就是知识图谱——对咱们"五类输入文档→本体"是极低成本的起步形态 | M4 |

### 11.4 落地注意点

- ⚠️ 184★ 个人项目，方法论价值 > 代码价值；hooks/skills 绑定 Claude Code（.claude/ 目录）
- ⚠️ 它是"产品研发上下文工程"，不是"项目风险管控"——编号门禁机制可以直接抄，但领域本体（合同/里程碑/SLA）不在它的范围内
- 没有服务端、没有数据库，纯文件体系——正好适合作为咱们 M4 文档中心的**交互设计参考**

## 12. 综合对比：怎么把 10 个项目用到咱们工具上

### 12.1 一张图看懂 10 个项目在风险识别架构（L1-L4）里的位置

```
L1 规则引擎（确定规则）     ← 自研规则 DSL（方案 4.4 预置规则）、sofagent（规则审计，第二梯队）
L2 关系推演（本体推理传导） ← HugAgentOS（控制平面闸门）
L3 阈值信号（数据偏差）     ← trustgraph（跨系统对账）、semantica（冲突检测）、PRD（就绪度评分）
L4 LLM 辅助（文档抽取）     ← ontogpt（extractor 模板抽取）、ontocast（本体+事实共进化）
审计追溯（贯穿全链路）      ← semantica（PROV-O + 决策链）、ontopilot（审查溯源）、jonex（引用+推理轨迹）
```

### 12.2 按"抄什么"分类

| 用法 | 项目 | 说明 |
|------|------|------|
| **抄代码（轻量集成）** | ontocast | Python 库 + REST 服务形态，跑独立服务后 Nuxt 用 HTTP 调；抽取+建本体一体化，价值密度最高 |
| **抄流程/交互（不引代码）** | ontopilot、trustgraph、PRD、HugAgentOS | 文档→本体→审核→发布流水线、本体编辑器交互、编号门禁、执行闸门——这些是**设计蓝图**，照着在 Nuxt 里实现 |
| **抄范式（方法论）** | ontogpt、fusion-jena | extractor 模板抽取范式、CQ 驱动建模方法论——不集成，写进自己的实现 |
| **抄理念（长期演进）** | semantica、jonex、OpenCrab | 决策留痕审计、本体编译前置、本体能力 MCP 化——工具成熟后对标的方向 |

### 12.3 结合咱们里程碑（M1-M5）的落地路线

| 里程碑 | 参考谁 | 具体做什么 |
|--------|--------|-----------|
| **M1 骨架（进行中）** | 无新增 | 先把 Nuxt 3 + SQLite + 本体/实体 API 跑通（方案 6.2 的 REST API 采用"契约先行"思路：先定接口模型再实现） |
| **M2 本体建模** | trustgraph 的 Ontology Workbench、ontopilot 的语义 Diff | 类/属性/关系可视化编辑 + 循环依赖检测 + 安全删除 + 修改历史；建模方法用 fusion-jena 的 **CQ 驱动**（先列风险管控要回答的问题） |
| **M3 业务数据** | ontocast 的 tenant/project 隔离、jonex 的多模态导入 | 全链路实体 CRUD + Excel 导入；文档可粘贴/上传（为 M4 铺路） |
| **M4 自动识别（核心）** | **ontocast（抽取+建本体，独立 REST 服务接入）+ ontogpt（extractor 模板范式，自研模板）+ PRD（编号门禁）** | ① 五类文档录入 → ② 要素抽取（模板化，LLM 可插拔）→ ③ L1 规则匹配 → ④ L2 关系传导 → ⑤ 落库 → ⑥ 人工确认；识别结果带"依据文档/条款"引用（学 jonex）；审计记录用 semantica 的决策链思路 |
| **M5 展示** | semantica（时间快照）、HugAgentOS（风险分级处置） | 双角色仪表盘 + 关系图谱 + 演示模式；风险看板支持"回看历史时点" |
| **M5 之后** | OpenCrab（MCP 化） | 把工具的本体/风险查询做成 MCP server，外部 Agent 可调用 |

### 12.4 最重要的三个结论

1. **没有一个项目能直接拿来当"风险管控工具"**——它们提供的是**抽取、推理、存储、校验、审计**这些能力组件；风险规则（L1）、领域本体（15 类 16 关系）、业务流程必须自研。这与评分报告的"落地提醒"一致。
2. **M4 是核心价值闭环，参考组合最清晰**：ontocast（抽取流水线，REST 接入）+ ontogpt（模板抽取范式）双件套 + 自研规则引擎（L1）与关系传导（L2），正好覆盖方案 4.2 的六步流水线。
3. **审计追溯不是事后补的，是设计出来的**：semantica 和 ontopilot 的共同点是把"谁、何时、依据什么、判了什么"作为**一等公民**记录。咱们工具从 M4 起就应在数据模型里预留 provenance 字段（识别来源、依据文档、规则编号、确认人），否则后期补审计成本极高。
