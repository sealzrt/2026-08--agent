# LangGraph 入门教程方案

## 1. 教程定位

本教程基于《LangGraph 入门大纲》展开，面向有多年服务端和前端开发经验、但 Python 基础较弱的开发者。

教程不按“纯概念文档”组织，而采用“工程实践主线 + 贯穿项目实战”的方式：每章先讲清最小必要概念，再立刻把概念应用到同一个项目中，逐步完成一个可运行、可调试、可扩展的 LangGraph Agent。

贯穿项目为：资料检索与总结 Agent。

最终教程应让读者完成以下结果：

- 能独立搭建 Python + LangGraph 开发环境。
- 能理解并实现 `State`、`Node`、`Edge`、条件分支和循环。
- 能把 LLM 调用、工具调用、人工确认、持久化和流式输出接入图工作流。
- 能把示例代码整理成接近生产项目的目录结构。
- 能理解 LangGraph 工程落地中的测试、日志、配置、部署和成本控制问题。

## 2. 教程总体结构

教程建议分为 4 个部分，共 15 章。

### 第一部分：建立最小认知

覆盖章节：

- 01. LangGraph 是什么
- 02. Python 最小基础
- 03. 第一个 LangGraph Hello World

目标：

- 让读者知道 LangGraph 解决什么问题。
- 让读者具备运行示例所需的 Python 最小基础。
- 让读者第一次跑通一个 LangGraph。

写作重点：

- 少讲抽象理论，多用服务端和前端开发者熟悉的类比解释。
- 把 LangGraph 类比为“有状态的业务流程编排”，而不是神秘的 AI 框架。
- Python 内容只讲本教程马上要用的部分。

阶段交付：

- 一个最小 Python 项目。
- 一个单节点 LangGraph 示例。

### 第二部分：完成核心图工作流

覆盖章节：

- 04. State：让工作流拥有共享上下文
- 05. Node：把业务步骤拆成可测试函数
- 06. Edge：控制流程、分支和结束条件
- 07. 工具调用：让 Agent 连接外部能力
- 08. LLM 调用与提示词组织
- 09. 循环、重试与递归限制

目标：

- 让读者掌握 LangGraph 的核心开发模型。
- 完成一个有分支、有循环、有工具调用、有 LLM 调用的工作流。

写作重点：

- 每章都要把代码接回贯穿项目。
- 每个节点都保持小函数形态，强调可测试性。
- 每次引入新概念，都要说明它解决了前一章的什么问题。

阶段交付：

- 一个能完成资料检索、总结、质量检查和循环补充的 Agent。

### 第三部分：加入真实应用能力

覆盖章节：

- 10. 持久化与会话恢复
- 11. Human-in-the-loop：人工确认与人工修改
- 12. 流式输出与前端集成

目标：

- 让 Agent 从“脚本示例”变成“可以被产品调用的后端能力”。
- 让读者理解长任务、人工介入和前端进度展示。

写作重点：

- 强调 `thread_id`、checkpointer、暂停恢复和人工反馈的关系。
- 明确 `interrupt()` 用于暂停，`Command(resume=...)` 用于恢复。
- 明确恢复执行时会从触发 `interrupt()` 的节点开头重新运行。
- 明确 `interrupt()` 前的副作用必须幂等，或放到恢复之后执行。
- 明确不要把 `interrupt()` 包在 `try/except` 中捕获。
- 明确 `checkpointer` 保存线程级执行状态，`store` 承担跨线程长期记忆。
- 明确内存型 checkpointer 只适合教程和本地实验，生产环境需要持久化存储。
- 用前端开发者熟悉的任务状态解释节点执行过程。
- 不过早引入复杂 UI，先设计稳定的后端接口和流式事件结构。

阶段交付：

- 一个支持会话恢复和人工确认的 Agent。
- 一个最小 API 设计。
- 一个前端状态展示方案。

### 第四部分：工程化收尾

覆盖章节：

- 13. 调试、观测与测试
- 14. 项目化目录结构
- 15. 部署与生产化注意事项

目标：

- 把教程代码整理成可维护项目。
- 帮读者建立上线前的工程检查清单。

写作重点：

- 重点讲可维护性，不做过度架构。
- 让每个目录、配置、测试都有明确目的。
- 区分“教程示例”和“生产系统还需要补的能力”。

阶段交付：

- 一个结构完整的 LangGraph 入门项目。
- 一份 README。
- 一份生产化注意事项清单。

## 3. 每章固定模板

每章建议统一采用以下写法，降低读者理解成本。

```text
1. 本章目标
2. 为什么需要这一章
3. 核心概念
4. 最小代码示例
5. 贯穿项目改造
6. 代码运行方式
7. 常见错误
8. 练习任务
9. 本章小结
```

各部分写作要求：

- 本章目标：用 3 到 5 条列出可验证结果。
- 为什么需要这一章：说明它解决前一章遗留的什么问题。
- 核心概念：只讲本章代码会用到的概念。
- 最小代码示例：代码尽量短，先保证能跑。
- 贯穿项目改造：展示本章如何推进资料检索与总结 Agent。
- 代码运行方式：必须给出明确命令。
- 常见错误：列出初学者容易遇到的异常和排查方式。
- 练习任务：至少包含一个必做任务和一个扩展任务。
- 本章小结：总结本章新增能力，以及下一章要解决的问题。

## 4. 贯穿项目演进方案

贯穿项目不要一次性给出完整代码，而应按章节逐步演进。

### 第 1 版：普通函数流程

对应章节：

- 02. Python 最小基础

能力：

- 接收一个主题。
- 返回一段固定总结。

目的：

- 让 Python 初学者先理解项目结构、函数和配置。

### 第 2 版：单节点图

对应章节：

- 03. 第一个 LangGraph Hello World

能力：

- 使用 `StateGraph` 包装一个简单节点。
- 通过 `invoke()` 执行图。

目的：

- 让读者看到普通函数如何变成图节点。

### 第 3 版：多节点顺序图

对应章节：

- 04. State
- 05. Node

能力：

- 拆分主题分析、检索计划、总结生成等节点。
- 通过共享状态传递数据。

目的：

- 建立“业务步骤 = 节点，业务上下文 = 状态”的模型。

### 第 4 版：分支与循环图

对应章节：

- 06. Edge
- 09. 循环、重试与递归限制

能力：

- 根据主题复杂度决定是否检索。
- 根据总结质量决定是否补充检索。
- 设置最大循环次数。

目的：

- 让读者理解 LangGraph 和普通链式调用的核心区别。

### 第 5 版：工具与 LLM 接入

对应章节：

- 07. 工具调用
- 08. LLM 调用与提示词组织

能力：

- 调用模拟检索工具。
- 调用 LLM 生成结构化分析、总结和评估结果。

目的：

- 让示例从固定逻辑变成真正的 Agent 工作流。

### 第 6 版：持久化与人工介入

对应章节：

- 10. 持久化与会话恢复
- 11. Human-in-the-loop

能力：

- 保存会话状态。
- 在生成报告前暂停。
- 接收人工反馈后继续执行。
- 使用 `interrupt()` 暂停图执行。
- 使用 `Command(resume=...)` 恢复图执行。
- 说明恢复执行会重新进入触发 `interrupt()` 的节点。
- 说明同一节点内多个 `interrupt()` 不要随意增删或重排。
- 对比 `checkpointer` 和 `store` 的职责边界。

目的：

- 覆盖真实业务中常见的审批、确认和恢复场景。

### 第 7 版：服务化与可观测

对应章节：

- 12. 流式输出与前端集成
- 13. 调试、观测与测试
- 14. 项目化目录结构
- 15. 部署与生产化注意事项

能力：

- 提供最小 API。
- 展示节点执行状态。
- 使用 `stream()` 或事件流输出节点更新、模型 token 和中断事件。
- 区分 `graph.stream(..., stream_mode=...)` 和 `graph.stream_events(..., version="v3")` 的适用场景。
- 增加日志、测试和配置。
- 整理项目目录。

目的：

- 让教程最终产物具备真实工程形态。

## 5. 代码组织方案

教程前期可以使用单文件示例，后期必须迁移到项目结构。

### 前期单文件结构

适用章节：

- 02 到 06 章

示例：

```text
examples/
  01_basic_function.py
  02_first_graph.py
  03_state_graph.py
  04_conditional_edges.py
```

优点：

- 读者容易复制运行。
- 每章关注点清晰。

限制：

- 不适合展示真实项目边界。

### 后期项目结构

适用章节：

- 07 到 15 章

推荐结构：

```text
langgraph_intro_project/
  app/
    __init__.py
    config.py
    graph.py
    state.py
    nodes/
      analyze.py
      search.py
      summarize.py
      evaluate.py
      report.py
    tools/
      search_tool.py
    prompts/
      analyze.md
      summarize.md
      report.md
    api/
      main.py
      schemas.py
  tests/
    test_nodes.py
    test_graph.py
  examples/
    run_graph.py
  .env.example
  pyproject.toml
  README.md
```

迁移规则：

- 第 01 到 06 章使用单文件示例，降低初学者运行门槛。
- 第 07 章开始出现工具调用和 LLM 调用，迁移到项目结构。
- 第 14 章不再首次引入项目结构，而是对前面已经形成的结构做最终整理和解释。

## 6. 每章代码交付要求

每章代码必须满足以下要求：

- 可以从零运行。
- 依赖安装命令明确。
- 入口命令明确。
- 示例输入明确。
- 预期输出明确。
- 不依赖读者猜测隐藏配置。
- 如果需要 API Key，必须提供 `.env.example`。
- 如果使用模拟工具，必须明确说明它和真实工具的差异。
- 如果章节修改了示例代码，必须在生成后运行对应命令校验。
- 如果章节只生成 Markdown，也必须检查代码块和文件路径是否与现有项目一致。

代码风格要求：

- 优先使用类型标注。
- 节点函数保持短小。
- 业务函数和节点函数分开。
- Prompt 放到独立文件或独立常量中。
- 不在节点里硬编码环境变量读取逻辑。
- 错误处理先简单明确，再逐步工程化。
- 循环章节必须同时展示业务层 `iteration_count` 和运行时 `recursion_limit`，并说明 `recursion_limit` 在调用图时通过 config 传入。
- 人工介入章节必须展示 `interrupt()`、`Command(resume=...)` 和 `thread_id` 的配合。
- 人工介入章节必须说明节点恢复重跑、副作用幂等、不要捕获 `interrupt()`、不要重排同节点内多个 `interrupt()`。
- 流式输出章节必须明确 stream mode 的用途，至少覆盖 `updates`、`values` 和 `messages`。
- 流式输出章节必须区分 `stream()` 的图执行输出和 `stream_events(..., version="v3")` 的类型化事件输出。

## 7. 练习设计方案

每章练习分为两类。

### 必做练习

目标：

- 验证读者掌握本章核心概念。

示例：

- 修改 `State`，增加一个字段。
- 新增一个节点。
- 修改条件边的判断逻辑。
- 为节点增加一个单元测试。

### 扩展练习

目标：

- 让有工程经验的读者进一步连接真实项目经验。

示例：

- 把模拟检索替换成本地文件检索。
- 把内存 checkpointer 替换为数据库持久化。
- 增加前端任务进度展示。
- 增加结构化日志和请求 ID。

## 8. 教程写作口径

### 面向 Python 初学者

需要解释：

- Python 文件如何运行。
- 包和模块如何导入。
- 虚拟环境是什么。
- 字典和类型标注怎么读。
- `async` 和 `await` 的最低必要概念。

不需要展开：

- Python 元类。
- 装饰器高级用法。
- 复杂异步并发模型。
- 过深的包管理生态比较。

### 面向有工程经验的开发者

需要类比：

- `State` 类似一次业务流程的上下文对象。
- `Node` 类似一个明确输入输出的 service function。
- `Edge` 类似流程编排和路由规则。
- checkpointer 类似流程状态持久化。
- human-in-the-loop 类似审批流或人工复核点。

需要强调：

- LangGraph 不是替代业务系统的全部架构。
- Agent 节点仍然要遵守普通工程代码的可测试性和可观测性要求。
- LLM 输出要当成不稳定外部依赖处理。

## 9. 阶段验收标准

### 第一阶段验收

读者应能：

- 创建 Python 虚拟环境。
- 安装并导入 LangGraph。
- 定义一个 `StateGraph`。
- 运行一个单节点图。
- 解释 `State`、`Node`、`Edge`。

### 第二阶段验收

读者应能：

- 拆分多个节点。
- 使用共享状态传递数据。
- 编写条件边。
- 实现循环和最大次数限制。
- 接入一个模拟工具。
- 调用 LLM 并解析结构化输出。

### 第三阶段验收

读者应能：

- 使用 checkpointer 保存会话状态。
- 通过 `thread_id` 恢复同一会话。
- 解释 checkpointer 和 store 的区别。
- 使用 `interrupt()` 暂停图执行。
- 使用 `Command(resume=...)` 继续执行。
- 解释恢复执行为什么会重新运行触发中断的节点，以及这对副作用代码的影响。
- 在关键节点暂停并等待人工反馈。
- 为前端设计任务状态接口。
- 为前端设计流式事件消费方式。

### 第四阶段验收

读者应能：

- 把代码拆成项目目录。
- 编写基础单元测试和集成测试。
- 增加日志和基础观测。
- 用 FastAPI 封装图执行入口。
- 说明生产环境还需要补齐的能力。

## 11. 后续生成顺序

建议不要一次性生成全部章节正文。更稳妥的顺序是：

1. 先生成第 01 到 03 章，验证写作风格和代码难度。
2. 再生成第 04 到 09 章，完成核心工作流。
3. 再生成第 10 到 12 章，补齐应用能力。
4. 最后生成第 13 到 15 章，完成工程化收尾。

每个批次生成后应检查：

- 章节之间是否前后衔接。
- 代码是否能运行。
- 概念是否重复或跳跃。
- 是否符合 Python 初学者但有工程经验的读者定位。
- Markdown 中的命令、路径和代码文件是否真实存在。
- 本批次新增或修改的示例代码是否已执行验证。
- 官方 API 名称是否和当前 LangGraph 文档一致。

每个批次建议生成的产物：

- 对应章节 Markdown。
- 对应示例代码或项目代码变更。
- 一条可复制运行的验证命令。
- 本批次完成后的读者验收清单。

## 12. 风险与控制

### 风险一：Python 内容讲得太浅

控制方式：

- 每个 Python 概念都配一个马上用到的例子。
- 避免只给代码不解释运行方式。

### 风险二：LangGraph 概念讲得太抽象

控制方式：

- 每个概念都绑定贯穿项目中的一个问题。
- 先给图示或流程描述，再给代码。

### 风险三：教程代码过早复杂化

控制方式：

- 第 01-13 章坚持单文件示例，保证每章都有可独立运行的最小代码。
- 第 07 章起逐步引入项目结构，第 14 章做最终收束，避免读者到最后才第一次看到完整项目形态。

### 风险四：LLM 输出导致教程不可复现

控制方式：

- 先使用模拟 LLM 或固定返回值。
- 再切换到真实模型调用。
- 对结构化输出增加校验和兜底说明。
- 对依赖真实模型的示例提供“模拟模式”和“真实模式”两套运行方式。

### 风险五：读者只会复制代码，不理解工程边界

控制方式：

- 每章都解释当前代码为什么这样拆。
- 在后期章节明确哪些写法只是教程简化，哪些写法适合生产。

## 13. 完整教程完成标准

- 15 篇 Markdown 正文章节。

- 每章对应的练习任务。
- 最后一章的生产化检查清单。
