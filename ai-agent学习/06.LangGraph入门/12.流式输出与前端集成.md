# 12. 流式输出与前端集成

> 版本说明：本教程基于 **Python 3.10+，推荐 3.13；LangGraph 1.x**。

## 本章导读

Agent 工作流可能运行几十秒甚至更久。前端不能只显示一个"转圈加载"——用户需要知道：当前执行到哪个节点了、模型在说什么、是不是在等人确认。

这一章讲两件事：

1. 后端如何用 `graph.stream()` 逐步输出执行过程。
2. 如何把流式输出包装成前端能消费的事件结构 + 最小 API。

涉及代码：`code/step_by_step/12_stream_output.py`、`code/step_by_step/12_api.py`、`code/langgraph_intro_project/app/api/`

---

## 本章目标

- 理解"流式输出"和"最终状态"的区别。
- 掌握 `graph.stream(..., stream_mode=...)` 的常见 mode。
- 区分 `stream()` 与 `stream_events(version="v3")` 的适用场景。
- 设计前端可消费的统一事件结构。
- 用 FastAPI 包装最小接口。

## 为什么需要这一章

前 11 章我们一直用 `graph.invoke()`：一次性执行，最后返回完整结果。但长任务场景下，这个体验是灾难——用户盯着加载圈几十秒，不知道发生了什么。

真实产品的需求：

- **节点进度**：`analyze_topic` 在跑、`search_documents` 完成了、`evaluate_summary` 失败了。
- **模型消息**：LLM 正在逐 token 生成总结。
- **中断状态**：图停在 `human_review`，等人提交反馈。
- **最终结果**：完整报告。

`invoke()` 只能给最后一种。流式输出负责前三种。

### 两类场景

这一章里的“流式输出”，实际会落到两类产品里：

| 场景 | 典型形态 | 用户看到什么 | 状态怎么管 |
|---|---|---|---|
| 工具型本地 agent | 命令行工具、桌面软件、安装在本机的自动化助手 | 终端进度、桌面提示、当前步骤 | 往往直接在本地进程里跑，状态管理更轻 |
| 服务 API 型 agent | 面向用户的后端服务、Web 产品、SaaS 接口 | 页面进度条、任务状态、事件流、审批卡片 | 需要 `user_id/task_id/thread_id`、任务存储、事件查询或 SSE |

本章重点讲的是**服务 API 型**，因为它更能体现：

- 后端如何把 `stream()` 的结果整理成统一事件结构。
- 前端如何消费事件并刷新页面状态。
- 人工确认、长任务、任务恢复这些工程问题怎么串起来。

工具型本地 agent 也会用到 `stream()`，但它通常直接把进度打印到终端或本地 UI，不一定需要独立的 `/tasks`、`/events` 接口。

### 多用户并发时，后端如何区分

服务 API 型 agent 可能同时服务很多用户。区分用户和任务，主要由**后端 API + 认证信息 + 任务存储**完成，不是靠创建多个 `graph` 对象来区分。

最常见的是三种标识各司其职：

| 标识 | 表示什么 | 例子 | 用在哪里 |
|---|---|---|---|
| `user_id` | 当前登录用户是谁 | `user-001` | 认证、权限校验、查询用户自己的任务 |
| `task_id` | 用户提交的某一次任务 | `task-001` | API 路径、前端订阅、任务状态和事件 |
| `thread_id` | LangGraph 要读取的状态链 | `thread-user-001-001` | `configurable.thread_id`、checkpoint、恢复执行 |

可以把它们理解成：

```text
一个用户可以有多个任务
一个任务对应一条 LangGraph 状态链

user_id
  ├── task_id=task-001  -> thread_id=thread-user-001-001
  └── task_id=task-002  -> thread_id=thread-user-001-002
```

多用户同时调用时，后端为每个任务生成自己的上下文：

```text
用户 A -> API -> user_id=A -> task_id=task-001 -> thread_id=thread-A-001
用户 B -> API -> user_id=B -> task_id=task-002 -> thread_id=thread-B-001
```

调用 LangGraph 时，真正传入的是当前任务自己的 `thread_id`：

```python
from langgraph.types import Command

config = {
    "configurable": {
        "thread_id": task["thread_id"],
    }
}

result = graph.invoke(input_state, config)
```

这里不需要为每个用户重新 `compile()`。通常应用启动时编译一次图，多个请求共享这个已编译的图；每次调用通过不同的 `thread_id` 读取不同的 checkpoint。

人工反馈恢复时，仍然必须使用原任务的 `thread_id`：

```python
result = graph.invoke(
    Command(resume=feedback),
    {
        "configurable": {
            "thread_id": task["thread_id"],
        }
    },
)
```

后端的基本职责是：

1. 从登录态或令牌中得到 `user_id`。
2. 创建任务时生成 `task_id` 和 `thread_id`，并把三者保存到任务记录。
3. 查询任务、事件、报告或提交反馈时，校验任务属于当前 `user_id`。
4. 调用图时使用任务记录中的 `thread_id`，不能让前端随意指定别人的线程。

> 教程 demo 中可以直接让 `task_id == thread_id`，这样代码简单；生产系统通常把两者分开。`task_id` 是 API 的业务任务编号，`thread_id` 是 LangGraph 的状态编号。

还要注意：不同任务可以并发执行，但**同一条 `thread_id` 不应该被多个请求同时恢复**。例如用户连续点击两次“提交审批”，后端需要通过任务状态、幂等键、队列或锁，保证同一个中断只被处理一次。

### `thread_id` 保存在哪里

生产环境通常要保存两类数据，不要把它们混为一谈：

| 数据 | 通常保存在哪里 | 作用 |
|---|---|---|
| `user_id`、`task_id`、`thread_id`、任务状态、任务归属 | 业务数据库 | 后端根据 `task_id` 找到任务，并校验当前用户是否有权限访问 |
| `thread_id` 对应的图状态、checkpoint、暂停位置 | LangGraph checkpointer | `invoke()` 或 `Command(resume=...)` 时恢复图执行 |

业务数据库里可以有类似这样的任务记录：

```text
task_id=task-001
user_id=user-001
thread_id=thread-user-001-001
status=interrupted
```

前端提交反馈时只需要传业务任务编号：

```http
POST /tasks/task-001/feedback
```

后端先根据 `task_id` 查询任务，再取出内部的 `thread_id` 调用 LangGraph：

```python
task = task_store.get("task-001")

result = graph.invoke(
    Command(resume=feedback),
    {
        "configurable": {
            "thread_id": task["thread_id"],
        }
    },
)
```

`thread_id` 本身只是 checkpoint 的查询 key，不等于完整的图状态。真正需要恢复的内容，例如已生成的草稿、当前节点和中断位置，由 checkpointer 保存。

当前教程项目为了简单，使用 `InMemorySaver`，并直接设置：

```text
task_id == thread_id
```

这只适合单进程演示：服务重启后内存状态会丢失，多实例部署时不同实例之间也无法共享状态。生产环境应使用持久化、可共享的 checkpointer，并把业务数据库和 checkpointer 的职责分开管理。

## 核心概念

### 节点级状态展示

前端展示的每个节点，应该有明确的状态机：

```text
analyze_topic:      waiting | running | done | error
search_documents:   waiting | running | done | error
summarize_documents: waiting | running | done | error
evaluate_summary:   waiting | running | done | error
human_review:       waiting | interrupted | done
generate_report:    waiting | running | done | error
```

普通节点的状态流转：

```mermaid
stateDiagram-v2
    [*] --> waiting
    waiting --> running: 节点开始执行
    running --> done: 节点正常返回
    running --> error: 节点抛异常
```

而 `human_review` 这类有人工介入的节点多一个特殊状态：

```mermaid
stateDiagram-v2
    [*] --> waiting
    waiting --> running
    running --> interrupted: interrupt() 触发
    interrupted --> running: Command(resume=...) 恢复
    running --> done: 正常完成
```

前端对 `interrupted` 的处理很关键：它不是一个"结束状态"，而是**等待外部输入的中途状态**——看到它就该弹审批卡片，而不是把任务标记成失败。

任务级别的状态（跨节点）：

```text
created -> running -> interrupted -> completed
                        |--> failed
                        |--> cancelled
```

前端的本质工作，就是把后端事件流**翻译成这棵状态树**。

### 流式输出 vs 最终状态

| 对比维度 | `invoke()` | `stream()` |
|---|---|---|
| 返回什么 | 最终完整状态 | 执行过程的每个片段 |
| 时机 | 全部执行完 | 每步执行完立即返回 |
| 前端体验 | 转圈等结果 | 实时看进度 |
| 适用场景 | 批处理、测试 | 交互式产品 |

### graph.stream() 与 stream_mode

`stream()` 的核心参数是 `stream_mode`，决定每个片段里装什么：

| mode | 输出内容 | 适合谁消费 |
|---|---|---|
| `values` | 每步之后的**完整状态** | 调试、状态还原 |
| `updates` | 每个节点的**局部状态更新** | 展示"哪个节点干了什么" |
| `messages` | 模型消息和 token | 聊天式逐字输出 |
| `custom` | 自定义事件 | 业务事件 |
| `debug` | 完整调试信息 | 排障 |

```python
for chunk in graph.stream(input, config, stream_mode="updates"):
    print(chunk)
    # {'analyze_topic': {'documents': [...]}}
    # {'summarize_documents': {'summary': '...'}}
```

`updates` 格式是 `{节点名: 该节点返回的局部更新}`，天然适合"节点进度"展示。

### updates 的 chunk 到底怎么读

`stream_mode="updates"` 返回的是一个迭代器。每次循环拿到的 `chunk`，表示**某个节点刚刚执行完，并把局部更新写回了状态**。

最小示例里第一个 chunk 类似：

```python
{
    "analyze_topic": {
        "documents": ["资料：《LangGraph 流式输出》的入门资料"]
    }
}
```

读取方式：

```python
for chunk in graph.stream(input_state, config, stream_mode="updates"):
    for node_name, update in chunk.items():
        print("刚完成的节点:", node_name)
        print("这个节点写回的状态:", update)
```

这里要分清楚两层：

- 外层 key：节点名，例如 `analyze_topic`。
- 内层 value：这个节点返回的局部状态，例如 `{"documents": [...]}`。

所以前端适配层通常这样做：

```python
def to_frontend_events(task_id: str, chunk: dict) -> list[dict]:
    events = []
    for node_name, update in chunk.items():
        events.append({
            "task_id": task_id,
            "node": node_name,
            "status": "done",
            "event_type": "node_update",
            "payload": update,
        })
    return events
```

注意：`updates` 是**节点完成后**才产出，因此这里的 `status` 更适合标成 `done`。如果你想精确展示"节点开始执行 → running"，需要使用更细粒度的 `stream_events(...)`，或者在业务层自己补一个 `node_start` 事件。

### stream() vs stream_events()

| 对比维度 | `graph.stream(...)` | `graph.stream_events(..., version="v3")` |
|---|---|---|
| 关注点 | 图执行过程的状态 | 类型化的事件流 |
| 输出粒度 | 节点级 | 更细（含 LLM token、工具调用） |
| 版本 | 无 | 需指定 `version="v3"` |
| 适合场景 | 后端调试、节点进度 | 前端消费、可观测系统 |

**入门建议**：后端内部调试优先用 `stream(stream_mode="updates")`；真正给前端做事件流时，再对接 `stream_events(version="v3")`。

### 统一事件结构

后端无论用哪种方式，给前端的事件应该**统一结构**，避免前端写死解析逻辑：

```json
{
  "task_id": "stream-001",
  "node": "summarize_documents",
  "status": "done",
  "event_type": "node_update",
  "payload": {"summary": "基于 1 份资料总结：..."}
}
```

前端只需要处理几种 `event_type`：

| event_type | 含义 | 前端动作 |
|---|---|---|
| `node_update` | 节点返回了状态更新 | 标记该节点 done，刷新数据 |
| `node_start` | 节点开始执行（需要额外埋点） | 标记该节点 running |
| `token` | 模型 token（来自 messages mode） | 追加到输出框 |
| `interrupt` | 图在等人 | 弹出审批卡片 |

### SSE：前端怎么收事件

服务端把事件写成 SSE（Server-Sent Events）格式，前端用 `EventSource` 直接订阅：

```text
data: {"task_id": "task-001", "node": "analyze_topic", "status": "done", ...}

data: {"task_id": "task-001", "node": "human_review", "event_type": "interrupt", ...}
```

```javascript
const es = new EventSource("/tasks/task-001/events");
es.onmessage = (e) => {
  const evt = JSON.parse(e.data);
  updateNodeState(evt.node, evt.status, evt.payload);
};
```

注意：上面的 `EventSource` 是**生产版写法**。本章的 `12_api.py` 还是教程版，只返回普通 JSON，不是真正的 `text/event-stream`。也就是说：

- 教程版：`GET /tasks/{task_id}/events` 返回一个 JSON 对象，适合先理解事件结构。
- 生产版：同一个接口改成持续 `yield`，才可以被 `EventSource` 实时订阅。

### 时序图：两类场景

#### 本地工具型 agent

```mermaid
sequenceDiagram
    participant U as 用户
    participant UI as 本地界面/终端
    participant APP as 本地工具/桌面应用
    participant G as graph.stream(...)

    U->>UI: 输入任务
    UI->>APP: 触发执行
    APP->>G: 触发图执行
    loop 每个节点完成后
        G-->>APP: chunk = {node_name: update}
        APP-->>UI: 显示进度 / 当前步骤
    end
    G-->>APP: 最终结果
    APP-->>UI: 展示完成状态
```

#### 服务 API 型 agent

```mermaid
sequenceDiagram
    participant U as 用户
    participant FE as 前端
    participant API as 后端 API
    participant G as graph.stream(...)
    participant A as to_frontend_event()
    participant T as 任务存储

    U->>FE: 提交任务
    FE->>API: POST /tasks
    API->>G: 触发图执行
    loop 每个节点完成后
        G-->>API: chunk = {node_name: update}
        API->>A: 转成统一事件
        A-->>API: {task_id, node, status, event_type, payload}
        API->>T: 保存当前事件/状态
    end
    FE->>API: GET /tasks/{task_id}/events
    API-->>FE: 返回事件列表（教程版）
    Note over API,FE: 生产版这里会改成 SSE 持续推送
```

前者更像“本机工具在跑”，后者更像“后端服务在给前端喂事件”。

## 最小代码示例

创建 `code/step_by_step/12_stream_output.py`：

```python
from typing import TypedDict

from langgraph.graph import END, START, StateGraph


class ResearchState(TypedDict):
    topic: str
    documents: list[str]
    summary: str


def analyze_topic(state: ResearchState) -> dict[str, list[str]]:
    return {"documents": [f"资料：《{state['topic']}》的入门资料"]}


def summarize_documents(state: ResearchState) -> dict[str, str]:
    return {"summary": f"基于 {len(state['documents'])} 份资料总结：{state['topic']}"}


builder = StateGraph(ResearchState)
builder.add_node("analyze_topic", analyze_topic)
builder.add_node("summarize_documents", summarize_documents)
builder.add_edge(START, "analyze_topic")
builder.add_edge("analyze_topic", "summarize_documents")
builder.add_edge("summarize_documents", END)

graph = builder.compile()


def to_frontend_event(task_id: str, chunk: dict, status: str = "done") -> dict:
    """把 stream 输出整理成前端可消费的统一事件格式。"""
    if chunk:
        node = list(chunk.keys())[0]
        payload = chunk[node]
    else:
        node = ""
        payload = {}

    return {
        "task_id": task_id,
        "node": node,
        "status": status,
        "event_type": "node_update",
        "payload": payload,
    }


if __name__ == "__main__":
    config = {"configurable": {"thread_id": "stream-001"}}

    for chunk in graph.stream(
        {
            "topic": "LangGraph 流式输出",
            "documents": [],
            "summary": "",
        },
        config,
        stream_mode="updates",
    ):
        print(to_frontend_event("stream-001", chunk))
```

运行：

```powershell
cd code/step_by_step
python 12_stream_output.py
```

预期输出：

```text
{'task_id': 'stream-001', 'node': 'analyze_topic', 'status': 'done', 'event_type': 'node_update', 'payload': {'documents': ['资料：《LangGraph 流式输出》的入门资料']}}
{'task_id': 'stream-001', 'node': 'summarize_documents', 'status': 'done', 'event_type': 'node_update', 'payload': {'summary': '基于 1 份资料总结：LangGraph 流式输出'}}
```

## 执行过程拆解

`graph.stream(...)` 的执行与 `invoke()` 相同，只是**每个节点完成后立即产出**：

1. `analyze_topic` 执行完 → 产出第一个 chunk：`{'analyze_topic': {'documents': [...]}}`。
2. `summarize_documents` 执行完 → 产出第二个 chunk：`{'summarize_documents': {'summary': '...'}}`。
3. 遍历结束，流关闭。

`to_frontend_event` 做的事情：

- 从 chunk 里取出节点名（chunk 唯一的 key）。
- 取出该节点的局部更新作为 `payload`。
- 包装成统一事件结构。

**关键点**：`to_frontend_event` 是"适配层"——它把 LangGraph 的原始输出翻译成产品约定的格式。前端永远不直接碰 LangGraph 的数据结构，只依赖这个约定。

事件从图到前端的链路：

```mermaid
flowchart LR
    G["graph.stream(...)<br/>stream_mode=updates"] -->|"原始 chunk"| A["to_frontend_event()<br/>适配层"]
    A -->|"统一事件结构"| EV["事件通道<br/>GET /tasks/{id}/events"]
    EV -->|"data: {...}"| FE["前端 EventSource"]
    FE -->|"解析 event_type"| UI["更新节点状态树<br/>running / done / interrupt"]
```

`stream()` 产出 → 适配层翻译 → 事件通道 → 前端渲染，每一跳都有明确职责。改动任何一跳，其他层不需要跟着改。

## 贯穿项目改造

贯穿项目的节点较多，前端节点状态机：

```text
analyze_topic -> plan_search -> search_documents -> summarize_documents
  -> evaluate_summary -> human_review -> generate_report
```

**最小 API 设计**：

```text
POST /tasks                       创建任务，返回 task_id
GET  /tasks/{task_id}             查询任务状态
POST /tasks/{task_id}/feedback    提交人工反馈（对接第 11 章 Command）
GET  /tasks/{task_id}/events      获取事件（教程版返回列表，生产可扩展为 SSE）
GET  /tasks/{task_id}/report      获取最终报告
```

其中 `code/step_by_step/12_api.py` 只实现前四个接口，用来演示任务状态和事件入口；`GET /tasks/{task_id}/report` 在完整项目的 `code/langgraph_intro_project/app/api/` 中实现。

`task_id` 在教程 demo 里直接映射为 `thread_id`。如果升级为生产形态，整个后端会围绕它组织：

```text
创建任务（生成 thread_id）
  -> 触发图执行（后台任务，前端订阅 /events）
  -> 图运行，事件通道传递节点事件
  -> 到达 human_review，推送 interrupt 事件
  -> 前端弹审批卡片，POST /feedback
  -> 后端 Command(resume=...) 恢复，继续推送
  -> 完成，GET /report 取结果
```

这是一种面向产品化的 Agent 后端形态雏形。当前项目代码仍是教程版同步执行，`/events` 只是返回当前可见事件列表；第 15 章会进一步把长任务、队列、Worker 和真正 SSE 的工程化方案讲清楚。

## 调试与排查

### 场景一：`stream()` 只输出最终结果

**现象**：for 循环只跑了一次，或者 chunk 格式是完整状态。

**原因**：`stream_mode` 用错了。`values` 模式每步输出完整状态，`updates` 模式每步输出节点更新。

**排查**：确认 `stream_mode="updates"`；打印 chunk 观察格式是否符合"`{节点名: 更新}`"。

### 场景二：前端收到的事件结构不稳定

**现象**：前端解析经常报错，字段对不上。

**原因**：直接把 `stream()` 原始输出暴露给前端，没有适配层。

**排查**：统一用 `to_frontend_event` 之类适配函数，固定 `task_id/node/status/event_type/payload` 五字段。

### 场景三：`interrupt` 事件没有推送

**现象**：图停在 `human_review`，但前端没有收到审批卡片。

**原因**：流式循环里没有处理 `__interrupt__` 事件，或中断后流被当作正常结束。

**排查**：在 `stream()` 循环里检测 chunk / 状态中的 `__interrupt__` 字段，单独推送 `event_type: "interrupt"`，并保持连接等待恢复后的新事件。

### 场景四：`stream_events` 报版本错误

**现象**：`TypeError` 或 `ValueError` 提示需要指定 version。

**原因**：`stream_events` 必须传 `version="v3"`。

**排查**：`graph.stream_events(input, config, version="v3")`。入门阶段优先用 `stream()`，够用就别上 `stream_events`。

## 常见错误

| 现象 | 原因 | 解决 |
|---|---|---|
| 只给前端最终结果 | 没用流式 | 用 `stream(stream_mode="updates")` |
| 前端解析事件结构不稳定 | 没有统一适配层 | 固定五字段事件结构 |
| 节点状态只有 running/done，缺 error | 状态机不完整 | 每个节点配 waiting/running/done/error |
| 前端不知道 interrupt | 中断事件没单独处理 | 检测 `__interrupt__` 推送 interrupt 事件 |
| 用 `stream_events` 不传版本 | API 用法错误 | `version="v3"`；或直接用 `stream()` |
| 长任务阻塞 HTTP 请求 | 同步执行图 | 后台任务 + 前端订阅事件（第 15 章展开） |

## 本章小结

- 流式输出让长任务可交互：节点进度、模型消息、中断状态都能实时推给前端。
- `stream(stream_mode="updates")` 输出节点级更新，后端调试首选。
- `stream_events(version="v3")` 输出类型化事件，前端/观测系统首选。
- 前端事件要**统一结构**，后端加适配层，别让前端碰 LangGraph 原始输出。
- 最小 API：创建任务 → 查询/订阅事件 → 提交反馈；完整项目再补最终报告查询。
