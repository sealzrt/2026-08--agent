# 05. Node：把业务步骤拆成可测试函数

## 本章目标

- 理解节点本质上是普通 Python 函数。
- 掌握节点输入和输出约定。
- 学会把业务函数和节点函数分开。
- 为贯穿项目拆出多个清晰节点。

## 为什么需要这一章

如果所有逻辑都写在一个节点里，图只是换了一种写法的单体函数。LangGraph 的优势来自清晰的节点边界：每个节点做一件事，读固定状态，返回明确更新。

这和服务端开发中的 service function 很接近。

## 核心概念

### 节点函数

节点函数通常长这样：

```python
def node_name(state: ResearchState) -> dict:
    return {"field": "new value"}
```

### 业务函数

业务函数不需要知道 LangGraph：

```python
def build_questions(topic: str) -> list[str]:
    return [f"{topic} 是什么？"]
```

节点函数调用业务函数：

```python
def analyze_topic(state: ResearchState) -> dict[str, list[str]]:
    return {"questions": build_questions(state["topic"])}
```

这样更容易测试。

## 最小代码示例

```python
from typing import TypedDict


class ResearchState(TypedDict):
    topic: str
    questions: list[str]


def build_questions(topic: str) -> list[str]:
    return [
        f"{topic} 是什么？",
        f"{topic} 的核心概念有哪些？",
        f"{topic} 适合哪些工程场景？",
    ]


def analyze_topic(state: ResearchState) -> dict[str, list[str]]:
    return {"questions": build_questions(state["topic"])}


def test_build_questions() -> None:
    questions = build_questions("LangGraph")
    assert len(questions) == 3
    assert "LangGraph" in questions[0]
```

## 贯穿项目改造

建议把贯穿项目拆成这些节点：

```text
analyze_topic
  -> plan_search
  -> search_documents
  -> summarize_documents
  -> evaluate_summary
  -> generate_report
```

每个节点的职责：

- `analyze_topic`：分析用户主题，生成研究问题。
- `plan_search`：决定要检索哪些方向。
- `search_documents`：调用工具获取资料。
- `summarize_documents`：基于资料生成总结。
- `evaluate_summary`：判断总结是否足够好。
- `generate_report`：生成最终报告。

## 常见错误

- 节点做太多事：一个节点同时检索、总结、评分，会很难测试。
- 节点直接读取环境变量：配置应该集中管理，节点只接收状态或调用业务层。
- 节点返回不可预测结构：后续条件边会依赖状态字段，字段结构必须稳定。
