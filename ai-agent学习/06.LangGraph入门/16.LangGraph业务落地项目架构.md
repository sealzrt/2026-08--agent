## 一句话架构

LangGraph 不负责替代整个后端系统，它负责把一个**有状态、有分支、有循环、可中断恢复的业务流程**编排起来。

```mermaid
flowchart LR
    A["业务需求<br/>用户输入 · 触发条件"] --> B["业务入口<br/>API · Webhook · CLI"]
    B --> C["LangGraph<br/>状态管理 + 图编排"]
    C --> D["外部能力<br/>模型 · 工具 · 数据库 · 人工"]
    D --> E["业务结果<br/>报告 · 状态回写 · 事件通知"]
    D -.->|反馈| C
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    class A,B biz
    class C core
    class D,E cap
```

关键认知：

- API 负责接收请求，不负责写复杂流程。
- LangGraph 负责决定下一步走哪个节点、什么时候循环、什么时候暂停。
- 节点负责把状态交给业务能力处理，再把结果写回状态。
- 工具、模型、数据库、人工审批都是被图调用的能力，不应该反向控制图。

## 业务落地的三层视角

真实项目经常混乱，是因为大家把"业务流程"、"代码结构"、"部署架构"混在一起讲。落地时建议分成三张图：

```mermaid
flowchart TD
    A["业务流程<br/>做什么 → 怎么做 → 何时停"] -->|抽象| B["代码模块<br/>State · Nodes · Tools · Prompts · API"]
    B -->|接入| C["运行部署<br/>队列 · Worker · Checkpoint · 事件"]
    C -->|服务业务| A
    classDef neutral fill:#f8fafc,stroke:#334155,color:#0f172a
    class A,B,C neutral
```

对应到本教程：

| 视角 | 要回答的问题 | 本项目对应内容 |
|---|---|---|
| 业务流程 | 先做什么，后做什么，什么时候返工，什么时候让人确认 | `analyze -> search -> summarize -> evaluate -> review -> report` |
| 代码模块 | 状态、节点、工具、Prompt、API 分别放哪里 | `app/state.py`、`app/nodes/`、`app/tools/`、`app/prompts/`、`app/api/` |
| 运行部署 | 长任务、恢复、事件、失败、成本如何处理 | `thread_id`、checkpointer、API、事件接口、测试和配置 |

## 业务流程架构

"资料检索与总结 Agent"的业务流程不是简单流水线，因为它有两个关键控制点：

1. **质量不达标要回到检索**：这是业务循环。
2. **生成草稿后要人工确认**：这是 Human-in-the-loop。

```mermaid
flowchart TD
    Start(["开始"]) --> Analyze["分析<br/>理解需求，拆解问题"]
    Analyze --> NeedSearch{"需要检索?<br/>分析后判断"}
    NeedSearch -->|是| Plan["规划<br/>生成检索策略"]
    Plan --> Search["检索<br/>调用搜索工具获取资料"]
    Search --> Summarize["总结<br/>整合资料生成摘要"]
    NeedSearch -->|否| Summarize
    Summarize --> Evaluate["评分<br/>质量评估，打分"]
    Evaluate --> Pass{"达标或到上限?<br/>score ≥ 阈值 或 iteration ≥ max"}
    Pass -->|是| Draft["草稿<br/>生成报告初稿"]
    Draft --> Review["审批<br/>人工确认与修改"]
    Review --> Report["报告<br/>最终输出"]
    Report --> End(["结束"])
    Pass -->|否，继续检索| Plan
    classDef neutral fill:#f8fafc,stroke:#334155,color:#0f172a
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    class Start,End neutral
    class Analyze,Plan,Search,Summarize,Evaluate,Draft,Report core
    class NeedSearch,Pass biz
    class Review cap
```

这张图对应 `app/graph.py`：

- `add_node(...)` 定义图上有哪些业务步骤。
- `add_edge(...)` 定义固定顺序。
- `add_conditional_edges(...)` 定义业务分支。
- `compile(checkpointer=...)` 定义图是否可恢复。

## 代码模块架构

一个业务项目不能把所有逻辑都塞进 `graph.py`。推荐把 LangGraph 项目拆成六类模块：

```mermaid
flowchart TD
    subgraph S1["接入层"]
        Front["前端/调用方<br/>Web · CLI · 第三方系统"]
        API["API<br/>app/api/<br/>参数校验 · 任务管理 · 反馈入口"]
    end
    subgraph S2["编排层"]
        Graph["Graph<br/>app/graph.py<br/>注册节点 · 连边 · 路由 · 编译"]
        State["State<br/>app/state.py<br/>共享上下文字段定义"]
        Config["Config<br/>配置 · 模型选择 · 开关"]
    end
    subgraph S3["能力层"]
        Nodes["Nodes<br/>app/nodes/<br/>读状态 → 调能力 → 写状态"]
        Prompts["Prompts<br/>app/prompts/<br/>可独立评审的模型指令"]
        LLM["LLM<br/>app/llm.py<br/>模型调用 · 结构化输出兜底"]
        Tools["Tools<br/>app/tools/<br/>搜索 · 数据库 · 内部系统"]
    end
    subgraph S4["测试"]
        Tests["Tests<br/>tests/<br/>节点单测 · 路由测试 · 图级集成"]
    end
    Front --> API
    API --> Graph
    Graph --> State
    Graph --> Nodes
    Graph --> Prompts
    Graph --> Config
    Nodes --> LLM
    Prompts --> Tools
    Tests -.->|覆盖| Nodes
    Tests -.->|覆盖| Graph
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    classDef neutral fill:#f8fafc,stroke:#334155,color:#0f172a
    class Front,API biz
    class Graph,State,Config core
    class Nodes,Prompts,LLM,Tools cap
    class Tests neutral
```

| 模块 | 职责 | 不应该做 |
|---|---|---|
| `app/api/` | 参数校验、任务创建、状态查询、人工反馈入口 | 不写 Prompt，不决定图路线 |
| `app/graph.py` | 注册节点、连边、路由、编译图 | 不写具体业务处理细节 |
| `app/state.py` | 定义共享状态字段和初始状态 | 不调模型，不调工具 |
| `app/nodes/` | 读状态、调业务能力、写状态 | 不直接处理 HTTP，不读写任务表 |
| `app/tools/` | 封装搜索、数据库、内部系统等外部能力 | 不依赖 LangGraph 状态 |
| `app/prompts/` | 存放可独立评审的模型指令 | 不混在 Python 逻辑里 |
| `app/llm.py` | 模型调用、mock/real 切换、结构化输出兜底 | 不决定业务流程 |
| `tests/` | 验证节点输出和图级行为 | 不依赖真实线上服务 |

## State 是业务上下文，不是数据库

LangGraph 的 `State` 是一次任务在图执行过程中的共享上下文。它适合放"后续节点必须继续使用的数据"，不适合当成业务数据库。

```mermaid
flowchart LR
    Input["输入<br/>query<br/>用户原始需求"] --> Analyze["分析<br/>analysis<br/>需求拆解结果"]
    Analyze --> Data["资料<br/>search_results<br/>检索到的材料"]
    Data --> Quality["质量<br/>score · issues<br/>评分和问题列表"]
    Quality --> Control["控制<br/>iteration · status<br/>循环次数和状态"]
    Control --> Review["审批<br/>draft · feedback<br/>草稿和人工反馈"]
    Control -.->|不达标时回到分析/检索| Analyze
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef warn fill:#fee2e2,stroke:#991b1b,color:#0f172a
    class Input core
    class Analyze,Data,Quality cap
    class Control biz
    class Review warn
```

判断一个字段该不该进 `State`，可以问三句话：

1. 后续节点是否需要它？
2. 恢复任务时是否需要它？
3. 审计、调试、展示进度时是否需要它？

三个问题都是否定，就不要放进 `State`。例如临时变量、一次性格式化字符串、局部计算结果，应留在节点函数内部。

## 运行时架构：教程版与生产版

教程项目为了便于理解，API 中同步执行图，任务结果放在内存字典里。这种方式适合学习，不适合生产。

### 教程版运行架构

```mermaid
flowchart LR
    Caller["调用方<br/>HTTP 请求"] --> FastAPI["FastAPI<br/>同步处理，阻塞等待"]
    FastAPI --> Invoke["GRAPH.invoke<br/>图执行入口"]
    Invoke --> Saver["InMemorySaver<br/>进程重启即丢失"]
    Saver --> Result["响应结果<br/>HTTP 同步返回"]
    FastAPI --> Tasks["内存任务表<br/>_TASKS 字典"]
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef warn fill:#fee2e2,stroke:#991b1b,color:#0f172a
    class Caller,Result biz
    class FastAPI,Invoke core
    class Saver,Tasks warn
```

限制很明显：

- HTTP 请求会等待图执行。
- 进程重启后 `_TASKS` 和 `InMemorySaver` 都会丢。
- 并发、重试、取消、告警都很难做。

### 生产版推荐架构

```mermaid
flowchart TD
    subgraph S1["接入层"]
        Front["前端/业务系统<br/>提交任务 · 查看进度 · 审批"]
        API["API<br/>创建任务 → 返回 task_id"]
    end
    subgraph S2["调度层"]
        Queue["任务队列<br/>异步分发，HTTP 不阻塞"]
        Worker["Worker<br/>独立执行图，失败可重试"]
    end
    subgraph S3["编排层"]
        Graph["Graph<br/>节点编排 · 状态管理 · 路由"]
        Checkpoint["Checkpoint<br/>持久化恢复快照"]
    end
    subgraph S4["能力层"]
        Model["模型服务<br/>LLM 调用"]
        Tools["业务工具<br/>搜索 · 数据库 · 内部系统"]
        Human["人工审批<br/>暂停 → 确认 → resume"]
    end
    subgraph S5["支撑"]
        BusinessDB["业务库<br/>任务状态 · 权限 · 审计 · 报告"]
        Events["事件通道<br/>节点进度推送前端"]
    end
    Front --> API
    API --> Queue
    API -->|写任务| BusinessDB
    Queue --> Worker
    Worker --> Graph
    Graph -->|持久化| Checkpoint
    Graph --> Model
    Graph --> Tools
    Graph -->|interrupt| Human
    Worker -->|推送| Events
    Events -.->|进度| Front
    Human -.->|反馈| API
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    classDef neutral fill:#f8fafc,stroke:#334155,color:#0f172a
    class Front,API,Human biz
    class Worker,Graph,Checkpoint core
    class Queue,Events,BusinessDB cap
    class Model,Tools neutral
```

生产版的核心变化：

- API 不等待图跑完，只返回 `task_id`。
- Worker 独立执行图，失败后可重试或标记失败。
- Checkpoint 持久化到数据库，支持恢复和人工继续。
- 任务状态、权限、审计、最终结果进入业务数据库。
- 事件通道负责把节点进度推给前端。

    W->>S: 写 running

    G->>G: 执行节点
    G-->>W: interrupt
    W->>S: 写 interrupted

## 数据边界：Checkpoint 与业务库分工

很多项目会把 checkpointer 当数据库用，这是高风险设计。更稳妥的做法是分工：

```mermaid
flowchart LR
    Runtime["LangGraph 运行时<br/>图执行引擎"] -->|恢复点| Checkpoint["Checkpoint<br/>图恢复快照<br/>thread_id → 状态"]
    Runtime -->|业务记录| Business["业务库<br/>任务 · 状态 · 审计 · 报告"]
    Runtime -->|观测数据| Logs["日志/追踪<br/>耗时 · token · 错误摘要"]
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    class Runtime core
    class Checkpoint,Business cap
    class Logs biz
```

| 数据 | 放哪里 | 原因 |
|---|---|---|
| 图恢复快照 | Checkpoint Store | 给 LangGraph 恢复执行用 |
| 任务列表、状态、创建人 | 业务数据库 | 给业务系统查询、鉴权、统计 |
| 最终报告 | 业务数据库或对象存储 | 用户需要长期查看 |
| 审批人、审批时间、意见 | 业务数据库 | 审计合规需要 |
| 节点耗时、token、错误摘要 | 日志/追踪系统 | 排查和成本分析需要 |
| 临时 Prompt 拼接内容 | 通常不长期保存 | 可能包含敏感信息，且体积大 |

## 关键架构决策

### 1. 图是业务流程，不是工具集合

工具越多，越需要图来管顺序和退出条件。不要让每个工具自己决定下一步，否则流程会分散在很多文件里。

```mermaid
flowchart TD
    subgraph A["工具驱动：每个工具自己决定下一步，流程分散"]
        direction LR
        TD1["工具驱动<br/>无统一编排"] --> TD2["搜索工具<br/>自己决定下一步"]
        TD2 --> TD3["总结工具<br/>自己决定下一步"]
        TD3 --> TD4["评分工具<br/>自己决定下一步"]
        TD4 --> TD5["报告工具<br/>自己决定下一步"]
        TD5 -.->|循环| TD2
    end
    subgraph B["Graph 编排：图路由统一决定下一步，流程集中"]
        direction LR
        GO["Graph 编排<br/>统一路由"] --> GR{"Graph 路由<br/>条件分支"}
        GR --> N1["搜索节点<br/>被图调用"]
        GR --> N2["总结节点<br/>被图调用"]
        GR --> N3["评分节点<br/>被图调用"]
        GR --> N4["报告节点<br/>被图调用"]
    end
    classDef warn fill:#fee2e2,stroke:#991b1b,color:#0f172a
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    class TD1,TD2,TD3,TD4,TD5 warn
    class GO,GR core
    class N1,N2,N3,N4 cap
```

### 2. 节点要薄，业务能力要可测

节点的理想形态是：

```text
读 State -> 调业务函数/工具/模型 -> 返回要更新的字段
```

这样做的好处是节点可以测试，工具可以替换，Prompt 可以评审，图可以单独验证。

### 3. 循环必须有业务上限和运行时上限

本项目有两道闸：

- `max_iterations`：业务层上限，防止一直补充检索。
- `recursion_limit`：LangGraph 运行时上限，防止图无限递归。

```mermaid
flowchart LR
    Eval["evaluate<br/>质量评估节点"] --> Q1{"质量达标?<br/>score ≥ 阈值"}
    Q1 -->|否| Q2{"到达上限?<br/>iteration ≥ max"}
    Q2 -->|否| Retry["重试<br/>补充检索"]
    Q2 -->|是| Done["完成<br/>输出报告"]
    Q1 -->|是| Done
    Retry -.-> Eval
    Limit["运行上限<br/>recursion_limit<br/>LangGraph 运行时保护"] -.->|保护| Q1
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef biz fill:#fef3c7,stroke:#92400e,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    class Eval,Retry,Done core
    class Q1,Q2 biz
    class Limit cap
```

### 4. 人工介入是正式状态，不是弹窗

人工审批不是前端临时弹个框那么简单。后端必须知道任务已经进入 `interrupted`，并持久化草稿、审批问题和恢复所需的 `thread_id`。

## 从教程项目到业务项目的演进路线

不要一上来就做全量平台。一个可控的演进路线更现实：

```mermaid
flowchart LR
    A["本地脚本<br/>单文件可跑完"] --> B["API<br/>创建/查询/反馈"]
    B --> C["持久化<br/>thread_id 恢复"]
    C --> D["Worker<br/>异步执行，不阻塞"]
    D --> E["事件流<br/>节点级进度推送"]
    E --> F["治理<br/>权限/审计/成本/告警"]
    classDef core fill:#e0f2fe,stroke:#075985,color:#0f172a
    classDef cap fill:#dcfce7,stroke:#166534,color:#0f172a
    class A,B,C core
    class D,E,F cap
```

每一阶段的验收标准：

| 阶段 | 验收标准 |
|---|---|
| 本地脚本 | 给定输入能稳定跑完，失败能看见错误 |
| API 包装 | 能创建任务、查询任务、提交人工反馈 |
| 持久化 | 进程重启后能按 `thread_id` 恢复 |
| 队列 + Worker | HTTP 不阻塞，长任务由 Worker 执行 |
| 事件流 | 前端能看到节点级进度和中断事件 |
| 生产治理 | 有权限、审计、成本上限、告警、回放能力 |

## 落地检查清单

| 类别 | 检查项 |
