# 01. LangGraph 是什么

## 本章目标

- 理解 LangGraph 解决的核心问题。
- 区分普通函数调用、链式调用和图工作流。
- 看懂“资料检索与总结 Agent”的第一版流程。
- 判断什么场景适合使用 LangGraph。

## 为什么需要这一章

很多 Agent 示例看起来只是“调用一次大模型”。真实业务通常不是这样：它会有状态、分支、循环、人工审批、失败重试和中间结果展示。LangGraph 的价值就在这里：它把 Agent 当成一个有状态的流程图来编排。

如果你做过服务端，可以把 LangGraph 理解成一个轻量的、有状态的业务流程编排层。节点负责执行业务步骤，边负责决定下一步，状态负责在各步骤之间传递上下文。

## 核心概念

### 普通函数调用

普通函数调用适合确定流程：

```python
result = generate_report(topic)
```

它简单、直接，但一旦流程里出现“如果资料不够就继续检索”“生成前需要人工确认”，代码很快会变成大量 `if`、`while` 和状态变量。

### 链式调用

链式调用适合固定顺序：

```text
输入主题 -> 分析主题 -> 检索资料 -> 生成总结 -> 输出报告
```

它比单个函数清晰，但仍然不擅长表达复杂分支和循环。

### 图工作流

图工作流适合有条件、有循环、有状态的流程：

```text
开始
  -> 分析主题
  -> 是否需要检索？
      -> 否：直接总结
      -> 是：检索资料 -> 总结资料 -> 评估质量
  -> 质量是否达标？
      -> 否：补充检索
      -> 是：人工确认 -> 最终报告
结束
```

这就是 LangGraph 的典型使用场景。

## 最小代码示例

这一章先不写 LangGraph 代码，只用普通 Python 描述流程：

```python
def run_research_agent(topic: str) -> str:
    if len(topic) < 10:
        return f"主题较简单，直接生成总结：{topic}"

    documents = ["模拟资料 A", "模拟资料 B"]
    summary = f"基于 {len(documents)} 份资料生成总结：{topic}"
    return summary


if __name__ == "__main__":
    print(run_research_agent("LangGraph 适合做什么"))
```

这段代码能跑，但它没有显式表达流程结构。后续章节会把它逐步改成 LangGraph。

## 贯穿项目改造

本教程贯穿项目是“资料检索与总结 Agent”。

第一版流程：

```text
用户输入主题
  -> 分析主题
  -> 制定检索计划
  -> 检索资料
  -> 总结资料
  -> 评估总结质量
  -> 必要时补充检索
  -> 人工确认
  -> 生成最终报告
```

先记住三个问题：

- 哪些步骤是明确顺序？
- 哪些步骤需要条件判断？
- 哪些步骤可能循环？

后面 LangGraph 的 `State`、`Node`、`Edge` 都会围绕这三个问题展开。

## 常见错误

- 把 LangGraph 当成“大模型调用库”。它更像有状态流程编排库。
- 过早引入多 Agent。入门阶段先掌握单个图的状态、节点、边。
- 用 LangGraph 替代所有业务系统。数据库、权限、队列、日志仍然要按普通工程方式设计。
