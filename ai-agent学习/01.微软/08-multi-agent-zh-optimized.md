# 多 Agent 设计模式：何时用、为什么用、怎么用

来源：Microsoft Learn 开源课程 [AI Agents for Beginners - Multi-Agent Design Patterns](https://github.com/microsoft/ai-agents-for-beginners/blob/main/08-multi-agent/README.md)

> 本文是对原英文课程的中文整理版，不是逐字翻译。目标是帮助中文读者判断何时切换到多 Agent 架构、掌握实现多 Agent 系统的组成要素和常见模式。

## 1. 这节课要解决什么问题

一旦项目涉及多个 Agent，就需要考虑多 Agent 设计模式。但"什么时候该切换到多 Agent""它有什么优势"往往并不直观。这节课回答四个问题：

- 多 Agent 适用于哪些场景？
- 相比一个 Agent 干所有事，多 Agent 有什么优势？
- 实现多 Agent 设计模式需要哪些组成要素？
- 如何对多个 Agent 之间的交互保持可见性？

一句话定义：**多 Agent 是一种让多个 Agent 协同工作以达成共同目标的设计模式**。它在机器人、自动驾驶系统、分布式计算等领域被广泛使用。

## 2. 适用场景

以下几类场景特别适合多 Agent：

- **大工作量**：把大任务切分成小任务分给不同 Agent，并行处理、更快完成。典型例子：大规模数据处理。
- **复杂任务**：把复杂任务拆解成子任务，每个 Agent 专精一个方面。典型例子：自动驾驶中分别由不同 Agent 负责导航、障碍检测、车际通信。
- **多样化专长**：不同 Agent 拥有不同领域的专长，比单个 Agent 更有效地处理任务的不同侧面。典型例子：医疗领域中分别负责诊断、治疗方案、患者监测的 Agent。

## 3. 多 Agent 相比单 Agent 的优势

简单任务用单 Agent 就够了；复杂任务用多 Agent 有三大优势：

- **专业化**：每个 Agent 专注一个任务。单个"全能" Agent 面对复杂任务时容易迷失，甚至去做它并不擅长的事。
- **可扩展性**：通过增加 Agent 来扩展系统，比不断给单个 Agent 加担子更容易。
- **容错性**：一个 Agent 失效时其他 Agent 仍可继续工作，保证系统可靠性。

以订行程为例：单 Agent 系统要包办从查航班到订酒店、租车的所有环节，需要为所有任务配备工具，最终形成一个复杂的、难以维护和扩展的单体系统。多 Agent 系统则可以分别有专门查航班、订酒店、租车的 Agent，系统更模块化、更好维护、易于扩展。

打个比方：这就是"夫妻店旅行社"和"连锁旅行社"的区别——前者一个人包办所有事，后者不同岗位各司其职。

## 4. 实现多 Agent 模式的组成要素

仍以订行程为例，实现多 Agent 设计模式需要考虑以下要素：

- **Agent 间通信**：查航班的 Agent 需要与订酒店的 Agent 通信，确保酒店与航班日期一致。你需要决定*哪些 Agent 之间共享信息、如何共享*（协议和方式）。
- **协调机制**：用户偏好"酒店离机场近"、约束"租车只能在机场取"——订酒店的 Agent 需要与租车 Agent 协调，同时满足偏好和约束。你需要决定 *Agent 之间如何协调行动*。
- **Agent 架构**：每个 Agent 需要有做决策、从交互中学习的内部结构。例如查航班的 Agent 可以用机器学习模型基于用户历史偏好推荐航班。你需要决定 *Agent 如何决策、如何从用户交互中学习*。
- **交互可见性**：需要有跟踪 Agent 活动与交互的工具和手段——日志与监控、可视化工具、性能指标。
- **多 Agent 模式选型**：集中式、去中心化、混合式架构，需要选择最适合业务场景的模式。
- **人工介入**：多数场景下需要人在环中，要明确指示 Agent 何时请求人工干预。例如用户点名要某个 Agent 未推荐的酒店/航班，或者在订票前要求人工确认。

## 5. 多 Agent 交互的可见性

可见性对调试、优化、保证系统整体有效性至关重要。例如订行程场景，可以做一个仪表盘展示：每个 Agent 的状态、用户的偏好与约束、Agent 之间的交互。具体手段：

- **日志与监控**：记录每个 Agent 的每次动作——哪个 Agent、什么动作、什么时间、结果如何。这些信息用于调试和优化。
- **可视化工具**：用图形直观展示 Agent 之间的信息流，帮助发现瓶颈、低效环节和其他问题。
- **性能指标**：任务完成时长、单位时间完成任务数、推荐准确率等，用于定位改进空间、优化系统。

## 6. 常见的多 Agent 模式

### 6.1 群聊（Group Chat）

适合多个 Agent 相互对话的应用。典型场景：团队协作、客户支持、社交网络。

每个 Agent 相当于群聊中的一个用户，通过消息协议交换消息：向群里发消息、接收群消息、回复其他 Agent。可以用集中式架构（所有消息经中央服务器路由）或去中心化架构（消息直接交换）实现。

### 6.2 交接（Hand-off）

适合多个 Agent 之间移交任务的应用。典型场景：客户支持、任务管理、工作流自动化。

每个 Agent 代表工作流中的一个任务或环节，按照预定义规则把任务交接给下一个 Agent。

### 6.3 协同过滤（Collaborative Filtering）

适合多个 Agent 协作为用户提供推荐的应用。多 Agent 协作的价值在于各自专长不同、以不同方式贡献于推荐过程。

例如用户想要股票买入建议：

- **行业专家 Agent**：精通某个特定行业。
- **技术分析 Agent**：擅长技术面分析。
- **基本面分析 Agent**：擅长基本面分析。

三者协作可以给出更全面的建议。

## 7. 实例场景：退款流程

以客户申请退款为例，参与的 Agent 可以分为两类：

**退款流程专属 Agent**：

- **客户 Agent**：代表客户，负责发起退款流程。
- **卖家 Agent**：代表卖家，负责处理退款。
- **支付 Agent**：代表支付环节，负责把款项退还给客户。
- **纠纷处理 Agent**：负责解决退款过程中出现的问题。
- **合规 Agent**：确保退款流程符合法规和政策。

**可复用的通用 Agent**（业务其他环节也能使用）：

- **物流 Agent**：负责把商品寄回卖家（购物正向流程同样可用）。
- **反馈 Agent**：收集客户反馈（不限于退款过程）。
- **升级 Agent**：把问题升级到更高级别的支持。
- **通知 Agent**：在退款各阶段向客户发送通知。
- **分析 Agent**：分析退款流程相关数据。
- **审计 Agent**：审计退款流程执行是否正确。
- **报表 Agent**：生成退款流程报表。
- **知识 Agent**：维护退款及其他业务相关的知识库。
- **安全 Agent**：保障退款流程的安全。
- **质量 Agent**：保障退款流程的质量。

这个清单展示了如何为多 Agent 系统划分"流程专属"与"通用可复用"两类 Agent。

## 8. 练习与自测

**练习**：为客户支持流程设计一个多 Agent 系统。识别流程涉及的 Agent、各自的角色职责、相互如何交互。既要考虑客服流程专属的 Agent，也要考虑业务通用的 Agent。（提示：想想客服流程的不同阶段，可能需要的 Agent 比你以为的更多。参考答案见[原仓库 solution](https://github.com/microsoft/ai-agents-for-beginners/blob/main/08-multi-agent/solution/solution.md)。）

**自测 1**：以下哪个场景最适合多 Agent 系统？

- A1：一个支持机器人用单一知识库和少量工具回答常见问题。
- A2：退款工作流需要独立的反欺诈、支付、合规角色，各有各的工具，且结果必须协调。✅
- A3：同一个简单分类请求每小时到达数千次。

**自测 2**：什么时候单 Agent 通常是更好的选择？

- A1：任务用一套指令和工具就能处理，不需要专家间交接。✅
- A2：Agent 能访问多个工具。
- A3：工作流需要有不同权限、独立审计轨迹的多个角色。
