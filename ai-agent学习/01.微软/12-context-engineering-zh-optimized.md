# 上下文工程：让 Agent 始终拿到"对的信息"

来源：Microsoft Learn 开源课程 [AI Agents for Beginners - Context Engineering for AI Agents](https://github.com/microsoft/ai-agents-for-beginners/blob/main/12-context-engineering/README.md)

> 本文是对原英文课程的中文整理版，不是逐字翻译。目标是帮助中文读者理解上下文工程与提示工程的区别、掌握"写入/选取/压缩/隔离"等管理策略，以及识别和修复四类常见的上下文故障。

## 1. 这节课要解决什么问题

要构建可靠的 Agent，仅靠提示工程（Prompt Engineering）不够，还需要让 Agent 有效地管理信息。本课回答：

- 什么是上下文工程（Context Engineering）？它和提示工程有何不同？
- 有效上下文工程的策略：如何写入、选取、压缩、隔离信息。
- 会让 Agent 脱轨的常见上下文故障（中毒/分心/混乱/冲突）及修复方法。

## 2. 什么是上下文工程

对 Agent 而言，**上下文驱动着 Agent 的规划和行动**。上下文工程就是确保 Agent 在任务的每一步都拿到"对的信息"的实践。由于上下文窗口大小有限，Agent 构建者需要建立系统和流程来管理上下文窗口中信息的**添加、移除和浓缩**。

### 2.1 提示工程 vs 上下文工程

- **提示工程**：聚焦一组**静态**指令，用一套规则有效引导 Agent。
- **上下文工程**：管理一组**动态**信息（包括初始 prompt 在内），确保 Agent 随时间推移始终拥有所需信息。核心理念是让这个过程**可重复、可靠**。

### 2.2 上下文的类型

上下文不是单一事物，Agent 需要的信息来自多种来源：

- **指令（Instructions）**：Agent 的"规则"——prompt、系统消息、few-shot 示例、可用工具的描述。这是提示工程与上下文工程的交汇处。
- **知识（Knowledge)**：事实、从数据库检索的信息、Agent 积累的长期记忆。需要访问不同知识库时就要集成 RAG 系统。
- **工具（Tools）**：Agent 可调用的外部函数、API、MCP Server 的定义，以及调用后得到的反馈结果。
- **对话历史（Conversation History）**：与用户的持续对话。时间越长对话越复杂，占用的上下文窗口越多。
- **用户偏好（User Preferences）**：随时间学到的用户喜好，可存储起来在关键决策时调用。

## 3. 有效上下文工程的策略

### 3.1 规划策略（三步法）

1. **定义清晰的结果**：明确回答——"Agent 完成任务后，世界应该变成什么样？"即用户与 Agent 交互后应得到什么变化、信息或响应。
2. **绘制上下文地图**：回答——"Agent 完成这个任务需要哪些信息？"由此梳理出这些信息分布在哪里。
3. **建设上下文管道**：回答——"Agent 如何获取这些信息？"手段包括 RAG、MCP Server 及其他工具。

### 3.2 实操策略：管理上下文

信息开始流入上下文窗口后，需要主动管理：

1. **Agent 便签板（Scratchpad）**：让 Agent 在单次会话中记录与当前任务和用户交互相关的笔记。便签板存在于上下文窗口**之外**（文件或运行时对象），本次会话中需要时再取回。
2. **记忆（Memories）**：便签板管理单次会话，记忆则让 Agent 能**跨会话**存取相关信息——摘要、用户偏好、用于未来改进的反馈等。
3. **压缩上下文**：上下文窗口接近上限时，用摘要（summarization）和裁剪（trimming）——只保留最相关的信息，或删除较旧的消息。
4. **多 Agent 系统**：本身就是一种上下文工程——每个 Agent 有自己的上下文窗口。上下文如何在 Agent 之间共享和传递，是设计时要规划的事。
5. **沙箱环境**：Agent 要运行代码或处理大文档时，结果可能消耗大量 token。与其全塞进上下文窗口，不如放到沙箱里执行，Agent 只读取结果和相关信息。
6. **运行时状态对象**：创建信息容器，按需给 Agent 提供特定信息。对复杂任务，Agent 可以逐步存储每个子任务的结果，让上下文只与当前子任务关联。

### 3.3 检查上下文（Inspecting Context）

应用上述策略后，值得检查下一次模型调用**实际收到了什么**。一个有用的调试问题：

> Agent 是加载了太多上下文、加载了错误的上下文，还是漏掉了它需要的上下文？

回答这个问题不需要记录原始 prompt、工具输出或记忆内容。生产环境中，优先记录小型的"上下文检查记录"——计数、ID、哈希、策略标签：

- **选取（Selection）**：考虑了多少候选分块/工具/记忆、选中了多少、其余被哪条规则或分数过滤掉。
- **压缩（Compression）**：来源范围或 trace id、摘要 id、压缩前后的估算 token 数、原始内容是否被排除出下次调用。
- **隔离（Isolation）**：哪个子任务在独立的 Agent/会话/沙箱中运行、返回了什么有界摘要、大体量工具输出是否留在父 Agent 上下文之外。
- **记忆与 RAG**：存检索文档 id、记忆 id、分数、选中 id、脱敏状态，而不是全文。
- **安全与隐私**：优先用哈希、id、token 分桶、策略标签，而不是敏感的 prompt 文本、工具参数/结果或用户记忆正文。

目标不是保留更多上下文，而是留下足够的证据，让开发者能判断哪个上下文策略生效了、它是否按预期改变了下一次模型调用。

## 4. 一个直观的对比示例

用户说："帮我订一趟去巴黎的行程。"

- **只用提示工程的简单 Agent**：只处理了用户当下的问题，回复"好的，你想什么时候去巴黎？"
- **用了上下文工程的 Agent**：在回复之前，系统可能已经——
  - 查了你的日历，找到可用日期（实时数据检索）；
  - 从长期记忆调出你的出行偏好（常坐的航空公司、预算、是否偏好直飞）；
  - 识别出可用的订机票/订酒店工具。

  然后回复："嗨 [名字]！我看到你十月第一周有空。要不要我在你常用的 [预算] 内，帮你找 [偏好航司] 直飞巴黎的航班？"——这种更丰富的、上下文感知的响应就是上下文工程的威力。

## 5. 四类常见上下文故障与修复

### 5.1 上下文中毒（Context Poisoning）

- **是什么**：幻觉（LLM 生成的虚假信息）或错误进入上下文后被反复引用，导致 Agent 追逐不可能的目标或发展出荒谬的策略。
- **怎么办**：实施上下文校验与隔离检疫（quarantine）。信息加入长期记忆前先校验；发现疑似中毒就开启全新的上下文线程，防止坏信息扩散。
- **旅行示例**：Agent 幻觉出一条"本地小机场直飞远程国际城市"的航线（实际不存在），这个虚假航班信息被存入上下文。之后用户要求订票时，Agent 反复尝试搜索这条不可能的航线，不断报错。
- **解法**：在航班信息加入工作上下文之前，先用实时 API 校验航班和航线是否存在；校验失败的信息被"检疫隔离"，不再使用。

### 5.2 上下文分心（Context Distraction）

- **是什么**：上下文太大，模型过度关注累积的历史而不是运用训练中学到的能力，导致重复或无用的动作。上下文窗口没满时就可能开始出错。
- **怎么办**：上下文摘要。定期把累积信息压缩成较短的摘要——保留重要细节、去掉冗余历史，帮模型"重置"注意力。
- **旅行示例**：用户和 Agent 聊了很久各种梦想目的地，还详细回忆了两年前的背包旅行。当用户终于说"帮我找下个月的便宜机票"时，Agent 却陷在陈旧无关的细节里，反复追问背包装备和过去的行程，忽略了当前请求。
- **解法**：达到一定轮数或上下文过大时，Agent 应摘要对话中最新最相关的部分（聚焦当前的出行日期和目的地），用浓缩摘要进行下一次 LLM 调用，丢弃不相关的历史闲聊。

### 5.3 上下文混乱（Context Confusion）

- **是什么**：不必要的上下文（常见的是可用工具太多）导致模型生成糟糕的响应或调用不相关的工具。小模型尤其容易中招。
- **怎么办**：用 RAG 技术做"工具装载管理"（tool loadout）——把工具描述存入向量库，每次任务只选取最相关的工具。研究表明工具数量应控制在 30 个以内。
- **旅行示例**：Agent 有几十个工具：book_flight、book_hotel、rent_car、find_tours、currency_converter、weather_forecast、restaurant_reservations……用户问"在巴黎市内怎么出行最好？"，工具太多导致 Agent 混乱，居然尝试调用 book_flight 订巴黎市内航班，或明明用户偏好公共交通却调用 rent_car——因为工具描述有重叠，模型分辨不出哪个最合适。
- **解法**：对工具描述做 RAG。用户问巴黎出行时，系统按查询动态检索出最相关的工具（如 rent_car、public_transport_info），只把聚焦后的工具集呈现给 LLM。

### 5.4 上下文冲突（Context Clash）

- **是什么**：上下文中存在相互矛盾的信息，导致推理不一致或最终响应糟糕。常发生在信息分阶段到达、早期的错误假设残留在上下文中的情况。
- **怎么办**：上下文修剪（pruning）与卸载（offloading）。修剪：新信息到达时移除过时或冲突的信息；卸载：给模型一个独立的"便签板"工作区处理信息，不污染主上下文。
- **旅行示例**：用户先说"我要订经济舱"，聊着聊着改主意："这趟还是坐商务舱吧。"如果两条指令都留在上下文里，Agent 可能搜出互相矛盾的结果，或不知道该优先哪个偏好。
- **解法**：实施上下文修剪——新指令与旧指令矛盾时，删除旧指令或在上下文中显式覆盖。也可以让 Agent 用便签板先调和冲突的偏好再决策，确保只有最终一致的指令指导行动。

## 6. 小结

| 概念 | 一句话 |
|------|--------|
| 上下文工程 | 确保 Agent 每一步都拿到"对的信息"的可重复流程 |
| 与提示工程的区别 | 静态指令 vs 动态信息管理 |
| 五类上下文 | 指令、知识、工具、对话历史、用户偏好 |
| 管理手段 | 便签板、记忆、压缩、多 Agent、沙箱、运行时状态对象 |
| 四类故障 | 中毒（校验+检疫）、分心（摘要）、混乱（工具 RAG）、冲突（修剪+卸载） |
