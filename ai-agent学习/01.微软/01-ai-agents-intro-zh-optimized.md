# AI Agent 入门：概念、类型与适用场景

来源：Microsoft Learn 开源课程 [AI Agents for Beginners - Introduction to AI Agents and Agent Use Cases](https://github.com/microsoft/ai-agents-for-beginners/blob/main/01-intro-to-ai-agents/README.md)

> 本文是对原英文课程的中文整理版，不是逐字翻译。目标是帮助中文读者更自然地理解 AI Agent 的基本概念、常见类型、适用边界和开发思路。

## 1. 这节课要解决什么问题

在真正开始构建 AI Agent 之前，需要先弄清楚三个基础问题：

- AI Agent 到底是什么？
- AI Agent 和普通的 AI 应用有什么区别？
- 什么场景适合用 Agent，什么场景不值得用？

学完这一节后，你应该能够：

- 用自己的话解释 AI Agent 的定义。
- 区分 AI Agent 与普通 LLM 应用的差异。
- 判断一个业务问题是否适合用 Agent 方案。
- 初步画出一个 Agentic Solution 的设计思路。

## 2. 什么是 AI Agent

可以先用一句话理解：

> AI Agent 是一种让大语言模型不只是“回答问题”，而是能够结合工具、知识和环境去完成任务的系统。

普通的大语言模型主要负责生成文本。例如回答问题、写总结、改写文案、生成代码片段等。而 AI Agent 在此基础上多了一层“行动能力”：它可以读取环境状态、调用工具、执行步骤，并根据结果继续调整下一步。

举个旅行预订助手的例子：

- 用户说：“帮我订下周去上海的行程，预算不要太高，尽量少转机。”
- 普通 LLM 可能只能给出建议。
- AI Agent 则可能会查询航班、比较酒店、检查预算、调用预订 API，并给出可执行方案。

所以，Agent 的关键不只是“聪明”，而是“能在受控范围内行动”。

## 3. AI Agent 的核心组成

一个 Agent 通常不是单一模型，而是一组组件协同工作的系统。可以从以下几个部分理解。

### 3.1 环境

环境是 Agent 所处和操作的空间。

例如旅行 Agent 的环境可能是：

- 航班查询系统
- 酒店预订平台
- 用户账户数据
- 支付或订单系统

Agent 能看到什么、能操作什么，取决于它被接入了哪些环境。

### 3.2 感知能力

感知能力指 Agent 如何读取当前环境状态。

例如：

- 查询某个日期的航班价格。
- 检查酒店是否还有空房。
- 读取用户过去的偏好。
- 判断订单是否已经确认。

这部分相当于 Agent 的“观察能力”。

### 3.3 行动能力

行动能力指 Agent 可以对环境做什么。

例如：

- 预订酒店。
- 取消订单。
- 发送确认邮件。
- 调用外部 API。
- 写入数据库。

没有行动能力的系统通常只是聊天机器人；具备行动能力后，才更接近 Agent。

### 3.4 大语言模型

LLM 是现代 Agent 的核心推理组件。它负责理解用户意图、处理自然语言、拆解任务，并决定下一步该调用什么工具。

Agent 并不是 LLM 的同义词。更准确地说，LLM 是 Agent 系统中的“大脑”之一，而 Agent 还需要工具、记忆、权限、流程控制和运行环境。

### 3.5 工具

工具决定了 Agent 能做哪些事。

例如旅行 Agent 可以接入：

- 航班搜索工具
- 酒店查询工具
- 价格比较工具
- 用户偏好数据库
- 邮件发送接口

工具范围需要由开发者明确配置。一个设计良好的 Agent 应该只拥有完成任务所需的最小权限，而不是无限制地访问所有系统。

### 3.6 记忆与知识

Agent 可以使用短期记忆和长期记忆。

短期记忆通常是当前对话上下文，例如用户刚刚说过的预算和目的地。

长期记忆可能来自数据库、历史订单、知识库或用户画像。例如系统记住某个用户偏好靠窗座位、常住某类酒店、对价格更敏感。

记忆能让 Agent 的表现更连贯，但也会带来隐私、安全和数据治理问题，因此需要谨慎设计。

## 4. 常见 AI Agent 类型

不同 Agent 的复杂度和能力不同。下面用“旅行助手”作为统一例子说明。

| 类型 | 特点 | 旅行助手示例 |
| --- | --- | --- |
| 简单反射型 Agent | 基于固定规则行动，不考虑历史状态，也不做复杂规划。 | 收到投诉邮件后，直接转发给客服团队。 |
| 基于模型的反射型 Agent | 内部维护一个“世界状态”模型，会根据新信息更新判断。 | 跟踪历史机票价格，当某条路线价格异常升高时提醒用户。 |
| 目标导向型 Agent | 先明确目标，再规划实现路径。 | 根据用户所在地和目的地，安排机票、酒店和租车。 |
| 效用导向型 Agent | 不只找可行解，还会在多个方案中权衡优劣。 | 在价格、耗时、舒适度之间做比较，推荐综合评分最高的行程。 |
| 学习型 Agent | 根据反馈持续改进。 | 根据用户旅行后的评价，优化后续推荐策略。 |
| 分层型 Agent | 高层 Agent 拆解任务，低层 Agent 分别执行子任务。 | “取消行程”被拆成取消航班、取消酒店、取消租车三个子任务。 |
| 多 Agent 系统 | 多个 Agent 协同或竞争完成任务。 | 航班 Agent、酒店 Agent、娱乐活动 Agent 分别负责不同部分，再汇总方案。 |

这些类型不是互斥的。真实系统中，一个 Agent 可能同时具备目标导向、工具调用、记忆和多 Agent 协作能力。

## 5. 什么时候适合使用 AI Agent

不是所有 AI 应用都需要 Agent。Agent 更适合以下场景。

### 5.1 问题开放，无法提前写死流程

如果任务路径无法完全预定义，需要模型根据上下文动态判断下一步，就适合考虑 Agent。

例如：“帮我规划一次适合家庭出行、预算有限、尽量轻松的云南旅行。”  
这类任务涉及偏好理解、信息查询、方案比较和多轮调整，单次问答很难处理完整。

### 5.2 任务需要多步骤执行

Agent 适合处理需要连续行动的任务。

例如：

- 查询信息。
- 比较候选方案。
- 调用工具执行操作。
- 根据工具返回结果调整计划。
- 最终向用户确认。

如果任务只是一次简单检索或一次文本生成，普通 LLM 应用通常更合适。

### 5.3 系统需要随着反馈持续改进

当业务希望系统根据用户反馈、历史行为或环境变化不断优化表现时，Agent 的记忆和学习机制会更有价值。

例如，旅行 Agent 可以逐渐知道用户更在意价格、时间、酒店位置，还是舒适度。

## 6. 什么时候不应该急着使用 AI Agent

Agent 能力更强，但也更复杂。以下情况不一定适合上 Agent：

- 任务流程非常固定，用规则或普通程序就能稳定完成。
- 只需要一次性生成文本，不需要调用工具或持续执行。
- 业务对错误容忍度极低，但又没有设计好权限、审计和回滚机制。
- 数据权限、隐私边界和安全策略还不清晰。
- 成本和延迟要求很严格，而 Agent 的多步推理和工具调用会带来额外开销。

简单说：能用普通工作流解决的问题，不必强行做成 Agent。Agent 适合处理“动态、多步、有工具、有反馈”的问题。

## 7. Agentic Solution 的基础设计思路

构建 Agentic Solution 时，首先要定义 Agent 能做什么，以及它不能做什么。

通常需要明确：

- Agent 的目标是什么。
- 可以访问哪些数据。
- 可以调用哪些工具。
- 哪些操作必须先让用户确认。
- 出错时如何回退或转人工。
- 如何记录执行过程，便于调试和审计。

原课程使用 Microsoft Foundry Agent Service 作为主要平台。它支持接入不同模型和数据源，也支持通过标准化工具定义来构建 Agent 能力。

## 8. Agentic Patterns：Agent 的常见设计模式

普通 LLM 应用通常依赖提示词来完成任务。但 Agent 需要跨多轮、跨工具、跨步骤地完成工作，不能只靠人工写死每一次提示词。

Agentic Patterns 可以理解为一组可复用的设计方法，用来指导 Agent 如何思考、如何规划、如何调用工具，以及如何处理结果。

常见方向包括：

- 任务拆解
- 工具调用
- 反思与自我检查
- 多 Agent 协作
- 人类确认与干预
- 记忆管理

这些模式可以让 Agent 系统更稳定，也更容易扩展。

## 9. Agentic Frameworks：为什么需要框架

Agentic Framework 是帮助开发者构建 Agent 的工具箱和基础设施。

它通常会提供：

- 工具接入方式
- Agent 编排能力
- 多 Agent 协作机制
- 调试与观测能力
- 模板和最佳实践
- 与模型、数据源和外部服务的集成

课程中重点使用 Microsoft Agent Framework 来构建更接近生产环境的 Agent。

## 11. 本节核心结论

AI Agent 的重点不是“会聊天”，而是“能在工具和权限约束下完成任务”。

它与普通 LLM 应用的主要区别在于：

- 能读取环境状态。
- 能调用工具。
- 能执行多步骤任务。
- 能利用记忆和知识。
- 能根据反馈调整行为。

判断是否需要 Agent，可以用一个简单标准：

> 如果任务需要动态规划、多步执行、工具调用和持续反馈，Agent 可能是合适选择；如果只是一次性问答或固定流程，普通 LLM 应用往往更简单、更可靠。
