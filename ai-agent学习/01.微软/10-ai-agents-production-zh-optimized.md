# AI Agent 生产化：可观测性与评估

来源：Microsoft Learn 开源课程 [AI Agents for Beginners - AI Agents in Production: Observability & Evaluation](https://github.com/microsoft/ai-agents-for-beginners/blob/main/10-ai-agents-production/README.md)

> 本文是对原英文课程的中文整理版，不是逐字翻译。目标是帮助中文读者掌握 Agent 从原型走向生产所需的可观测性建设、评估方法和成本控制策略。

## 1. 这节课要解决什么问题

当 AI Agent 从实验原型走向真实应用，理解其行为、监控其性能、系统性地评估其输出就变得至关重要。学完本课你将掌握：

- Agent 可观测性与评估的核心概念
- 提升 Agent 性能、成本、有效性的技巧
- 系统性评估 Agent 时"评什么、怎么评"
- 部署到生产时如何控制成本
- 如何为 Microsoft Agent Framework（MAF）构建的 Agent 做插桩

目标：把"黑盒" Agent 变成透明、可管理、可信赖的系统。

> 注意：部署安全可信的 Agent 同样重要，请结合[第 6 课：构建可信 Agent](06-trustworthy-agents-zh-optimized.md)一起阅读。

## 2. Trace 与 Span

Langfuse、Microsoft Foundry 等可观测性工具通常把 Agent 的运行表示为 Trace 和 Span：

- **Trace（追踪）**：一次完整的 Agent 任务，从开始到结束（如处理一次用户查询）。
- **Span（跨度）**：Trace 内部的单个步骤（如一次 LLM 调用、一次数据检索）。

没有可观测性，Agent 就是"黑盒"——内部状态和推理过程不透明，难以定位问题或优化性能。有了可观测性，Agent 变成"玻璃盒"，这种透明性是建立信任、确保 Agent 按预期运行的基础。

## 3. 生产环境为什么必须有可观测性

进入生产环境后，可观测性不再是"锦上添花"，而是关键能力：

- **调试与根因分析**：Agent 失败或输出异常时，Trace 能精确定位错误来源。对涉及多次 LLM 调用、工具交互和条件逻辑的复杂 Agent 尤为重要。
- **延迟与成本管理**：Agent 依赖按 token/按调用计费的 LLM 和外部 API。可观测性能精确跟踪这些调用，找出过慢或过贵的操作，进而优化 prompt、换更高效的模型或重新设计工作流。
- **信任、安全与合规**：可观测性提供 Agent 行为和决策的审计轨迹，可用于发现和缓解提示注入、有害内容生成、个人身份信息（PII）处理不当等问题。例如通过回看 Trace 理解 Agent 为什么给出某个回答、为什么用了某个工具。
- **持续改进闭环**：可观测性数据是迭代开发的基础。监控真实表现 → 找出改进点 → 收集微调数据 → 验证变更效果，形成"线上评估洞察反哺线下实验优化"的反馈循环。

## 4. 需要跟踪的关键指标

具体指标因 Agent 用途而异，但以下几项是普遍重要的：

| 指标 | 说明 |
|------|------|
| **延迟（Latency）** | Agent 响应多快？要按任务和单步分别测量。例如所有模型调用共花 20 秒，可以换更快的模型或并行调用。 |
| **成本（Costs）** | 每次运行花多少钱？频繁的工具调用和多轮 prompt 会快速推高成本。例如为边际质量提升调用 5 次 LLM 是否值得？实时监控还能发现异常尖峰（如 bug 导致的 API 死循环）。 |
| **请求错误（Request Errors）** | 失败了多少请求（API 错误、工具调用失败）？可据此设置降级和重试，如 LLM 供应商 A 挂了自动切到 B。 |
| **显式用户反馈** | 点赞/点踩、1-5 星评分、文字评论。持续的负面反馈是 Agent 未按预期工作的信号。 |
| **隐式用户反馈** | 用户行为暗含的反馈：立即改写问题、重复提问、点击重试按钮。用户反复问同一个问题就说明有问题。 |
| **准确性（Accuracy）** | Agent 多大比例产出正确/理想的结果？先定义"成功"对你的 Agent 意味着什么，再通过自动化检查、评估打分或任务完成标注（如把 Trace 标记为成功/失败）来跟踪。 |
| **自动化评估指标** | 用 LLM 给 Agent 输出打分（是否有帮助、是否准确）；开源库如 RAGAS（评 RAG）、LLM Guard（检测有害语言/提示注入）。 |

实践中，组合使用这些指标才能全面覆盖 Agent 的健康状况。

## 5. 为 Agent 插桩（Instrumentation）

要收集追踪数据，需要给代码插桩——让 Agent 代码发出可被观测平台捕获、处理、可视化的 trace 和指标。

**OpenTelemetry（OTel）** 已成为 LLM 可观测性的行业标准，提供生成、收集、导出遥测数据的 API、SDK 和工具。很多插桩库封装了现有 Agent 框架，可轻松把 OTel Span 导出到观测工具。

MAF 原生集成 OpenTelemetry：

```python
from agent_framework.observability import get_tracer, get_meter

tracer = get_tracer()
meter = get_meter()

with tracer.start_as_current_span("agent_run"):
    # Agent 的执行会被自动追踪
    pass
```

**手工创建 Span**：插桩库提供了基线，但常常需要更细或自定义的信息。可以手工创建 Span 来覆盖自定义应用逻辑，更重要的是给 Span 补充自定义属性（tags/metadata），如 user_id、session_id、model_version 等业务数据、中间计算结果或任何有助于调试分析的上下文。

Langfuse Python SDK 手工创建 Span 的例子：

```python
from langfuse import get_client

langfuse = get_client()
span = langfuse.start_span(name="my-span")
span.end()
```

## 6. Agent 评估

可观测性给我们指标，**评估**则是分析这些数据（并执行测试）来判断 Agent 表现如何、如何改进的过程。

定期评估非常重要：Agent 通常是非确定性的，而且会演化（版本更新、模型行为漂移）——不评估，你就不知道你的"智能 Agent"是真的在干活，还是已经退化了。

评估分两类，互为补充。通常从离线评估开始——这是部署任何 Agent 前的最低必要步骤。

### 6.1 离线评估（Offline Evaluation）

在受控环境中用测试数据集（而非真实用户查询）评估。使用已知期望输出/正确行为的精选数据集来跑 Agent。

例如数学应用题 Agent，可以准备 100 道已知答案的题目。离线评估常在开发期进行（也可纳入 CI/CD 流水线），用于验证改进、防止回归。优点是可重复、有 ground truth，能得到清晰的准确率指标。

**关键挑战**：测试集要全面且保持时效——Agent 在固定测试集上表现好，但生产中可能遇到完全不同的查询。所以要持续用新的边界案例和贴近真实场景的样例更新测试集。建议"小冒烟测试集 + 大评估集"搭配：小集合快速检查，大集合看整体指标。

### 6.2 在线评估（Online Evaluation）

在真实生产环境中、真实用户使用过程中评估：持续监控 Agent 在真实交互中的表现并分析结果，如跟踪真实流量的成功率、用户满意度等。

优点是能捕捉实验室中预料不到的东西：观察模型随时间的漂移（输入模式变化导致效果退化）、发现测试数据里没有的意外查询——它反映 Agent 在真实世界的表现。

在线评估通常包括收集显式/隐式用户反馈，也可能做影子测试或 A/B 测试（新版本 Agent 并行运行与旧版对比）。挑战在于真实交互难以获得可靠的标签或评分，可能要依赖用户反馈或下游指标（如用户是否点击了结果）。

### 6.3 两者结合

线上监控的洞察（如 Agent 表现差的新型用户查询）可以用来扩充和改进离线测试集；离线测试表现好的 Agent 才能更有信心地部署上线。很多团队采用这样的循环：

**离线评估 → 部署 → 在线监控 → 收集新失败案例 → 补入离线数据集 → 精化 Agent → 重复**

## 7. 常见问题与对策

| 问题 | 可行方案 |
|------|---------|
| Agent 执行任务不稳定 | 精化 prompt，明确目标；考虑把任务拆成子任务交给多个 Agent 处理 |
| Agent 陷入死循环 | 设定清晰的终止条件，让 Agent 知道何时停止；复杂的推理规划任务改用专精推理的大模型 |
| Agent 工具调用效果差 | 在 Agent 系统之外单独测试和验证工具输出；优化工具的参数定义、prompt 和命名 |
| 多 Agent 系统表现不稳定 | 精化每个 Agent 的 prompt，确保各自明确且彼此有区分度；引入"路由"/控制器 Agent 构建层级体系，判断请求该给哪个 Agent |

这些问题在有可观测性的情况下更容易被发现——Trace 和指标能精确定位问题发生在工作流的哪个环节。

## 8. 成本管理策略

- **用更小的模型**：小语言模型（SLM）在某些 Agent 场景下表现不俗，能显著降低成本。用评估体系对比 SLM 与大模型的表现是判断是否适用的最佳方式。可以让 SLM 处理意图分类、参数提取等简单任务，把大模型留给复杂推理。
- **用路由模型**：混用不同大小的模型，由一个 LLM/SLM 或无服务器函数按复杂度把请求路由给最合适的模型——简单查询走小而快的模型，复杂推理才用昂贵的大模型。
- **缓存响应**：识别高频请求和任务，在进入 Agent 系统之前直接返回缓存结果；还可以用轻量模型判断新请求与已缓存请求的相似度。对高频 FAQ 和常见工作流能显著省钱。

## 9. 小结

生产化的核心是把 Agent 从"黑盒"变成"玻璃盒"：用 OpenTelemetry 插桩收集 Trace/Span，跟踪延迟、成本、错误、反馈、准确性等关键指标，用"离线评估 → 部署 → 在线监控 → 反哺离线数据集"的闭环持续改进，并通过小模型、路由、缓存三板斧控制成本。
