# 第 1 章：为什么需要 Harness

## 学习目标

完成本章后，你应该能够：

- 说明手动测试 Agent 的主要问题
- 解释 Harness 在 Agent 开发流程中的位置
- 理解为什么需要固定任务集、运行记录和评估规则
- 说清楚最小 Harness 闭环包含哪些模块

## 核心概念

### Agent

Agent 是执行任务的主体。它通常包含模型、系统提示词、上下文、工具列表和决策逻辑。

### Harness

Harness 是 Agent 外部的运行框架。它不替代 Agent，而是负责准备输入、执行任务、记录过程、评估结果和生成报告。

### 可复现性

可复现性指同一个任务、同一个配置、同一套评估规则可以被重复运行和比较。没有可复现性，就很难判断 Prompt 修改或工具修改是否真的带来了改进。

### 可观测性

可观测性指你能看到一次 Agent 运行过程中发生了什么，包括输入、工具调用、错误、耗时和最终输出。

## 为什么手动测试不够

手动测试一个 Agent 通常是这样：

1. 打开对话窗口或脚本
2. 输入一个任务
3. 查看答案是否看起来正确
4. 修改 Prompt 后再试一次
5. 凭印象判断是否变好

这种方式有几个问题：

- 任务输入不固定，无法稳定回归
- 判断标准不固定，结果容易受主观影响
- 工具调用过程不可见，失败时很难定位
- 修改 Prompt 后缺少批量验证
- 没有统一报告，无法对比版本效果

Harness 的价值就是把这些临时动作变成稳定流程。

## 最小 Harness 闭环

第一版教程只关注一个最小闭环：

```text
Task -> Agent -> Trace -> Evaluate -> Report
```

各环节含义如下：

- `Task`：要交给 Agent 完成的任务
- `Agent`：执行任务并生成输出
- `Trace`：记录运行过程
- `Evaluate`：判断输出是否满足要求
- `Report`：汇总运行结果

## 操作步骤

### 步骤 1：准备 3 个手动任务

先不要写 Harness。手动准备 3 个任务，用来感受问题。

示例任务：

```text
任务 1：总结一段短文本，要求不超过 120 字。
任务 2：从一段文本中提取 3 个关键词。
任务 3：判断一段回答是否包含指定结论。
```

### 步骤 2：手动运行任务

把这 3 个任务交给同一个 Agent 或模型执行，并记录最终答案。

建议记录：

- 任务编号
- 输入内容
- 输出内容
- 是否看起来正确
- 判断理由

### 步骤 3：观察手动验证的问题

检查以下问题是否出现：

- 判断标准是否模糊
- 每次输入是否完全一致
- 是否记录了工具调用过程
- 是否记录了错误信息
- 是否能快速看出 3 个任务的通过率

如果这些问题存在，就说明需要 Harness。

## 示例

手动记录可以先写成表格：

| 任务 | 输入 | 输出摘要 | 人工判断 | 问题 |
| --- | --- | --- | --- | --- |
| task-001 | 总结短文本 | 输出了总结 | 通过 | 没有记录字数 |
| task-002 | 提取关键词 | 返回 4 个关键词 | 失败 | 缺少固定规则 |
| task-003 | 判断结论 | 结论不明确 | 失败 | 没有失败原因 |

这张表已经接近 Harness 的雏形。后续章节会把它变成结构化任务、运行记录、评估结果和报告。
