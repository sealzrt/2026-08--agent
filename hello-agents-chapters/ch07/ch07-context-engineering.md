## 7.1 什么是上下文工程？

### 一个现实问题

你的智能体有：
- 5 条用户偏好（来自记忆系统）
- 3 段相关文档（来自 RAG）
- 10 轮对话历史
- 5 个可用工具的描述

全塞进 prompt？可能超出窗口。只塞一部分？该选哪些？

**上下文工程就是解决"在有限窗口中放入最有价值信息"的系统性方法。**

---

## 7.2 GSSC 流水线

GSSC 是四个阶段的缩写，描述了从"信息收集"到"组装 prompt"的完整流程：

```
Gather（收集）→ Select（选择）→ Structure（组织）→ Compress（压缩）
```

### Gather：收集所有可能相关的信息

```
来源：
├── 对话历史（最近 N 轮）
├── 长期记忆（用户偏好）
├── RAG 检索结果
├── 工具描述
└── 系统指令
```

### Select：筛选最有价值的信息

不是所有信息都同等重要。选择策略：
- **相关性排序**：和当前问题最相关的优先
- **时效性优先**：最近的信息优先
- **去重**：去掉重复信息

### Structure：组织信息的顺序

信息的排列顺序影响 LLM 的理解：

```
推荐结构：
1. 系统指令（始终在最前面）
2. 关键上下文（用户偏好、当前任务目标）
3. 对话历史（最近几轮）
4. 检索结果（RAG 返回的文档）
5. 工具描述（如果需要工具调用）
```

### Compress：压缩以节省 Token

当信息总量超过窗口时，需要压缩：
- **对话摘要**：把 20 轮对话压缩成一段摘要
- **文档摘要**：把长文档压缩成关键段落
- **工具精简**：只保留当前可能用到的工具

## 7.3-7.4 上下文管理的工程实践

### 实用策略：滑动窗口 + 摘要

```python
from helpers import count_tokens, summarize  # 共享辅助函数：Token 计数 + 对话摘要

def build_context(history, memories, rag_results, max_tokens=4000):
    """构建上下文：将多种信息源组装到有限 Token 窗口内"""
    context_parts = []

    # 1. 系统指令（固定部分）：包含角色设定 + 用户偏好记忆
    context_parts.append("你是旅行助手。用户偏好：" + memories)

    # 2. RAG 结果：按相关性排序，取最相关的前 3 条
    for doc in rag_results[:3]:
        context_parts.append(f"参考资料：{doc}")

    # 3. 对话历史：滑动窗口，只保留最近 5 轮（每轮 2 条消息）
    recent = history[-10:]               # 最近 10 条消息 = 5 轮对话

    # 4. Token 管理：如果总 Token 超出窗口限制，压缩旧对话
    total_tokens = count_tokens(context_parts + recent)
    if total_tokens > max_tokens:
        old_summary = summarize(history[:-10])  # 将旧对话压缩为摘要
        context_parts.append(f"之前的对话摘要：{old_summary}")  # 用摘要代替旧对话
        context_parts.extend(recent)     # 保留最近的对话不压缩
    else:
        context_parts.extend(recent)     # Token 充足时，直接拼接全部历史

    # 将各部分用双换行拼接，形成完整的上下文
    return "\n\n".join(context_parts)
```

### 🚧 常见坑

**坑 #1：重要信息被压缩丢失**
- 现象：智能体"忘记"了用户之前提到的关键约束
- 原因：压缩时把关键信息也删了
- 解决：标记"不可压缩"的关键信息（如用户明确要求）

实现"动态工具选择"：根据当前对话内容，只注入可能用到的工具描述，减少 Token 浪费。
