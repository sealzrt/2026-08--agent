# 第 6 章：记忆系统 - Agent 的长期记忆

原课程对应：`第二部分-核心系统篇/06-记忆系统-Agent的长期记忆.md`

> 上下文窗口只能保存当前会话的工作记忆。记忆系统解决的是另一个问题：哪些信息值得跨会话保存，并在未来任务中成为 Agent 的可靠线索。

## 学习目标

读完本章后，你应该能够：

- 区分短期记忆、长期记忆、外部记忆这三种常见 Agent 记忆视角。
- 区分 Claude Code 长期记忆里的 `user`、`feedback`、`project`、`reference` 四种内容类型。
- 说明“三类记忆”是通用视角，“四种类型”是长期记忆内部的内容分类。
- 理解为什么记忆系统只保存不可从代码仓库实时推导的信息。
- 掌握记忆 Markdown 文件、Frontmatter 和 `MEMORY.md` 索引的作用。
- 说明后台自动记忆提取为什么基于 Fork 模式运行。
- 理解工具列表一致性和提示缓存共享之间的关系。
- 能设计一套不过度保存、可验证、可维护的 Agent 记忆策略。

## 6.0 先看全景：短期记忆、长期记忆、外部记忆

很多资料会把 Agent 记忆分成短期记忆、长期记忆、外部记忆。它们不是三块神秘能力，而是三种不同的信息来源、保存位置和使用方式。

这里先使用一个便于学习的通用视角。后面的 6.1 节再把其中的“长期记忆”映射到本课程讨论的 `user`、`feedback`、`project`、`reference` 四种类型。不要把两套名称理解成两套互相竞争的系统。

```text
短期记忆：当前任务正在用的信息。
长期记忆：跨会话仍然有用的协作线索。
外部记忆：不适合塞进模型窗口、需要随用随查的外部事实源。
```

先看三类记忆如何一起进入当前上下文：

```mermaid
flowchart TD
  U["用户输入 / 当前任务"] --> ST["短期记忆池<br/>messages / tool_result / plan"]
  ST --> Ctx["上下文管理<br/>选择 / 压缩 / 裁剪"]
  Ctx --> M["本轮 context<br/>模型实际可见"]
  M --> A["模型推理 / 回复 / 工具调用"]

  ST --> Extract{"是否有长期价值?"}
  Extract -->|"否"| Drop["任务结束后丢弃或压缩"]
  Extract -->|"是"| LT["长期记忆<br/>user / feedback / project / reference"]

  EXT["外部记忆<br/>代码仓库 / 文档 / 数据库 / MCP / 搜索"] --> Retrieve["工具读取或检索"]
  Retrieve --> ST

  LT --> Recall["按相关性召回"]
  Recall --> ST

  ST --> Verify{"涉及当前事实?"}
  Verify -->|"是"| EXT
  Verify -->|"否"| A

  classDef short fill:#E8F3FF,stroke:#2563EB,color:#111827
  classDef long fill:#F5F3FF,stroke:#7C3AED,color:#111827
  classDef external fill:#ECFDF3,stroke:#16A34A,color:#111827

```

读图结论：

- 短期记忆是“当前工作台”，模型本轮主要依赖它。
- 长期记忆是“下次少从零开始的线索”，需要被召回后才会进入上下文。
- 外部记忆是“仓库、文档、数据库、搜索、MCP 等外部事实源”，需要工具读取后才会进入上下文。
- 三者最终都要变成当前上下文的一部分，模型才能使用。

### 三类记忆的对比

| 维度 | 短期记忆 | 长期记忆 | 外部记忆 |
|------|----------|----------|----------|
| 保存位置 | 当前会话的 `messages`、工具结果、计划和暂存工作材料 | 记忆文件、记忆库、用户画像 | 仓库、文档、数据库、搜索、MCP |
| 生命周期 | 当前任务或会话 | 跨会话 | 由外部系统决定 |
| 进入模型方式 | 经上下文管理后进入本轮 `context` | 召回后进入本轮 `context` | 工具读取后进入本轮 `context` |
| 主要价值 | 当前任务连续性 | 下次少从零开始 | 当前事实和大规模知识 |
| 主要风险 | 上下文爆炸 | 过期、污染、过度保存 | 检索错误、权限、来源不可靠 |
| 管理重点 | 压缩、裁剪、优先级 | 提炼、分类、更新、删除 | 检索、验证、引用、权限 |

一句话区分：

```text
短期记忆：我现在正在处理什么。
长期记忆：以后遇到类似事情，我应该记得什么。
外部记忆：当前事实在哪里，需要时去查。
```

### 短期记忆：当前任务的工作台

短期记忆可以理解成 Agent 当前正在处理任务时的工作材料。它通常包括：

- 当前 `messages`。
- 工具结果 `tool_result`。
- 当前计划、待办列表、scratchpad。
- 刚读过的文件片段、命令输出、错误信息。

短期记忆的核心问题不是“存不存”，而是“当前任务的工作材料暂时保留什么”。其中一部分会经过选择、排序、压缩和裁剪，形成本轮的 `context`。这就是第 7 章上下文管理要解决的问题。

#### 短期记忆和上下文的关系

短期记忆和上下文关系很近，但不是同一个东西。

```text
短期记忆 = 当前任务过程中暂时保留的工作材料池
上下文 = 本轮真正送进模型、模型这一次能看到的材料
```

换句话说，上下文是短期记忆经过选择、排序、压缩、裁剪之后得到的“本轮可见切片”。

```mermaid
flowchart TD
  subgraph Pool["短期记忆池"]
    U["用户需求"]
    Msg["最近 messages"]
    Plan["当前计划 / 待办列表"]
    Tool["tool_result"]
    Files["刚读过的文件片段"]
    Logs["测试日志 / 命令输出"]
    Summary["历史摘要"]
  end

  Pool --> CM["上下文管理<br/>选择 / 排序 / 压缩 / 裁剪"]
  CM --> Ctx["本轮 context<br/>模型这一次实际可见"]
  Ctx --> Model["模型推理"]

  classDef pool fill:#E8F3FF,stroke:#2563EB,color:#111827
  classDef manage fill:#FFF7ED,stroke:#EA580C,color:#111827
  classDef context fill:#F5F3FF,stroke:#7C3AED,color:#111827

  class U,Msg,Plan,Tool,Files,Logs,Summary pool
  class CM manage
  class Ctx,Model context
```

这也是为什么第 6 章和第 7 章容易混在一起：

| 概念 | 关注点 | 类比 |
|------|--------|------|
| 短期记忆 | 当前任务暂时保留了哪些材料 | 桌面上堆着的资料 |
| 上下文 | 这一次拿给模型看的材料 | 此刻摊开在眼前的几页纸 |
| 上下文管理 | 从短期记忆中挑选、压缩、排序 | 从桌面资料里挑出要看的几页 |

一句话：短期记忆是当前任务的工作材料池；上下文是本轮模型可见的工作材料切片。

#### 记忆还需要和哪些概念区分

理解记忆时，不要只在“短期 / 长期 / 外部”三类里打转。Agent 运行过程中还有很多相邻概念，它们都会和记忆发生关系，但职责不同。

先看一条信息在 Agent Harness 中怎么流动：

```mermaid
flowchart TD
  User["用户对话"] --> Msg["messages<br/>对话历史"]
  Tool["工具执行"] --> Result["tool_result<br/>观察结果"]
  Repo["代码仓库 / 文档 / 数据库 / MCP"] --> External["外部事实源"]

  Msg --> Short["短期记忆池"]
  Result --> Short
  External --> Read["工具读取 / 检索"]
  Read --> Short

  Short --> CM["上下文管理<br/>选择 / 压缩 / 裁剪 / 排序"]
  CM --> Context["本轮 context"]
  Context --> Model["模型推理"]

  Short --> Compact["compact summary<br/>压缩摘要"]
  Compact --> Short

  Short --> Candidate{"是否有长期价值?"}
  Candidate -->|"是"| Long["长期记忆<br/>user / feedback / project / reference"]
  Candidate -->|"否"| Trace["trace / log<br/>执行证据或调试记录"]

  Long --> Recall["未来召回"]
  Recall --> Context

  Context -.稳定前缀可复用.-> Cache["prompt cache<br/>性能优化"]

  classDef data fill:#E8F3FF,stroke:#2563EB,color:#111827
  classDef memory fill:#F5F3FF,stroke:#7C3AED,color:#111827
  classDef external fill:#ECFDF3,stroke:#16A34A,color:#111827
  classDef ops fill:#FFF7ED,stroke:#EA580C,color:#111827

  class Msg,Result,Short,Context,Model data
  class Long,Recall memory
  class Repo,External,Read external
  class CM,Compact,Candidate,Trace,Cache ops
```

读图结论：记忆不是单独存在的仓库。它和 `messages`、`context`、工具结果、压缩摘要、外部事实源、trace、prompt cache 都会发生关系，但每个概念解决的问题不同。

| 概念 | 和记忆的关系 | 核心区别 |
|------|--------------|----------|
| `context` 上下文 | 记忆要进入 `context` 后模型才能用 | `context` 是本轮可见内容，记忆是可被召回的材料 |
| `messages` 对话历史 | 短期记忆的重要来源 | `messages` 是聊天和工具回填记录，不等于长期记忆 |
| `tool_result` | 当前任务观察结果 | 通常是短期材料，除非能提炼出长期规则 |
| `scratchpad` / plan / 待办列表 | 当前任务工作状态 | 服务当前任务，不一定跨会话保存 |
| `compact summary` 压缩摘要 | 把短期历史压缩后继续任务 | 压缩是为了续航，不一定是长期记忆 |
| 项目目录中的 `CLAUDE.md` / `AGENTS.md` | 项目级显式规则载体 | 写在项目文件中，属于项目规则/外部知识源，不是用户侧长期记忆 |
| 代码仓库 | 当前事实来源 | 不该把当前代码结构记成长期记忆，需要时实时读取 |
| 外部记忆 / RAG / 向量库 | 大规模外部知识源 | 通过检索进入 `context`，不是模型天然记住 |
| `trace` / log | 执行证据 | 用于复盘和调试，不一定用于模型推理 |
| `prompt cache` | 性能优化 | 缓存稳定请求前缀，不是语义记忆 |
| `state` / session | 运行时状态 | 当前会话状态，不等于长期可复用知识 |
| 用户画像 | 长期记忆的一类 | 描述用户偏好、背景、理解方式 |
| `feedback` | 长期记忆的一类 | 描述 Agent 以后应该怎么做或避免什么 |

可以用这组判断公式：

```text
当前这轮要用的信息
  -> 短期记忆 / context

以后还会影响协作的信息
  -> 长期记忆

当前真实情况在哪里
  -> 外部记忆 / 仓库 / 文档 / 数据库

执行过程证据
  -> trace / log

为了省 token 或提速
  -> compact summary / prompt cache
```

特别要记住：记忆不是事实本身，记忆是未来构造上下文时可用的线索。如果涉及当前代码、版本、路径、配置、负责人、日期，就算记忆里提到了，也应该回到外部事实源验证。

以“修复一个测试失败”为例：

```text
短期记忆：
  用户目标：修复测试失败
  测试命令：npm test
  失败输出：某个断言不通过
  读取文件：相关 test 文件和实现文件
  当前计划：先定位断言，再修改实现，再重跑测试
  工具结果：Grep / Read / Bash 的输出
```

这些信息对当前任务很有用，但不一定值得长期保存。比如这次失败日志、某次命令输出、临时调试过程，通常任务结束后就不该进入长期记忆。

如果这次任务中发现一个稳定规则，例如“这个项目所有日期比较都必须使用 UTC，不能用本地时区”，它才可能从短期记忆中被提炼成长期记忆或项目文档。

### 长期记忆：未来协作的线索

长期记忆保存的是跨会话仍然有用的信息。它不是当前上下文本身，而是未来构造上下文时可以召回的材料。

典型长期记忆包括：

- 用户偏好：喜欢图解、喜欢先看全景、不想死记 API。
- 用户背景：熟悉后端，不熟 TypeScript。
- 行为反馈：后续公开内容抓取类 `curl -L` 命令不要反复确认。
- 项目决策背景：为什么当初选择某个架构方案。
- 外部入口线索：监控、工单、文档、团队频道的位置。

记忆系统做的不是“把聊天记录永久塞进模型脑子里”。模型本身不会因为一次对话就自动改变。记忆系统真正做的是：把未来仍然有用的线索保存下来，下一次遇到相关任务时，再把这些线索放回当前上下文，让 Agent 少从零开始。

可以用这条闭环理解长期记忆：

```mermaid
flowchart TD
  A["当前对话中出现信息"] --> B{"以后还会影响 Agent 行为吗?"}
  B -->|"否"| X["不保存"]
  B -->|"是"| C{"能从代码/文档/Git 实时查到吗?"}
  C -->|"能"| X
  C -->|"不能或成本高"| D["写入长期记忆"]
  D --> E["更新 MEMORY.md 索引"]
  E --> F["未来任务开始时读取索引"]
  F --> G{"和当前任务相关吗?"}
  G -->|"否"| H["不放进本轮上下文"]
  G -->|"是"| I["打开具体记忆"]
  I --> J["放入本轮上下文"]
  J --> K["影响 Agent 的解释、选择和执行策略"]
  K --> L{"涉及当前事实吗?"}
  L -->|"是"| M["回到仓库/外部系统验证"]
  L -->|"否"| N["直接作为协作偏好或背景使用"]

  classDef save fill:#F5F3FF,stroke:#7C3AED,color:#111827
  classDef context fill:#E8F3FF,stroke:#2563EB,color:#111827
  classDef drop fill:#FEF2F2,stroke:#DC2626,color:#111827
  classDef verify fill:#FFF7ED,stroke:#EA580C,color:#111827

  class D,E,F,I,J,K save
  class A,B,C,G,L context
  class X,H drop
  class M,N verify
```

读图结论：长期记忆负责“下次如何更好地开始”，不是负责“替代当前事实判断”。真正行动前，只要记忆涉及当前代码、配置、版本、路径、负责人、日期，就要重新验证。

### 外部记忆：随用随查的外部事实源

“外部记忆”是很多 Agent 教程对一类架构的统称。严格来说，代码仓库、项目文档、数据库、MCP 和搜索结果是外部知识源，不一定都实现成一个叫“记忆”的模块。本章为了便于理解，把这些“模型窗口之外、需要随用随查”的来源统一称为外部记忆。

它不是模型内部的记忆，也不等于 Agent 自己的长期记忆文件。它更像外部世界里的知识源，需要工具访问。

常见外部记忆：

| 外部知识源 | 例子 | 作为当前事实源提供什么 |
|----------|------|--------------|
| 代码仓库 | 当前源码、配置、测试、Git 历史 | 当前实现事实 |
| 项目文档 | `README.md`、`AGENTS.md`、`CLAUDE.md`、架构文档 | 团队正式规则和说明 |
| 数据库 | 用户数据、业务状态、任务记录 | 运行时事实 |
| 向量库 | 文档切片、知识库、历史案例 | 大规模可检索知识 |
| MCP Server | GitHub、监控、工单、内部服务 | 外部系统能力和资源 |
| 网络搜索 | 官方文档、公开资料 | 当前或外部更新信息 |

外部记忆进入上下文的路径是：

```mermaid
flowchart LR
  Need["当前任务需要信息"] --> Source{"信息在哪里?"}
  Source -->|"当前会话已有"| ST["短期记忆"]
  Source -->|"长期偏好/线索"| LT["长期记忆召回"]
  Source -->|"当前事实/大规模资料"| EXT["外部记忆"]

  EXT --> Tool["工具读取<br/>Read / Grep / Bash / MCP / Search"]
  Tool --> Result["结构化结果"]
  Result --> Context["放入当前上下文"]
  LT --> Context
  ST --> Context
  Context --> Model["模型使用"]
```

外部记忆的价值在于：不把所有东西都塞进长期记忆，也不把整个世界塞进上下文。需要什么，查什么；查到后，把必要片段放进当前上下文。

例如项目根目录的 `AGENTS.md`：

```text
运行测试用 npm test
不要修改 generated/ 目录
提交前运行 npm run lint
```

它属于项目规则载体，也是外部知识源的一部分。Agent 进入项目时可以读取它，并把相关规则放进当前上下文。它不应被复制成用户侧长期记忆。

两者边界是：

```text
项目目录中的 CLAUDE.md / AGENTS.md
  -> 团队共享的显式规则
  -> 当前进入项目时读取
  -> 规则变化时以文件内容为准

用户或 Agent 记忆目录中的长期记忆
  -> 跨项目或跨会话的协作线索
  -> 主要保存 user / feedback 等内容
  -> 不复制项目文档已经明确写出的规则
```

如果长期记忆只保存“项目规范在某个文件里”，它最多是一个导航线索；真正执行时仍应读取项目文件。

### 生活类比：餐馆多放辣椒

可以把记忆理解成常去一家餐馆时，服务员逐渐记住你的长期口味偏好。

```text
第一次吃饭
  -> 你说：这道菜帮我多放辣椒
  -> 服务员记住：这个客人点类似菜时喜欢偏辣

下次再来
  -> 你点了同类菜
  -> 服务员主动参考这个偏好
  -> 可能直接提醒后厨多放辣椒
  -> 或者问你：还是多放辣椒吗？
```

这里保存的不是“那天中午 12:30 吃了什么”，也不是“那盘菜具体放了几勺辣椒”。真正值得保存的是：

```text
这个用户以后点类似菜时，可能更喜欢偏辣。
```

对应到 Agent 记忆：

| 餐馆场景 | Agent 记忆 |
|----------|------------|
| 用户说多放辣椒 | 用户表达了长期偏好或行为规则 |
| 服务员记住口味 | Agent 把高价值信息写入长期记忆 |
| 下次点类似菜时参考 | 未来任务读取相关记忆并放入上下文 |
| 服务员必要时再确认 | 涉及当前事实或风险时仍然验证 |

这个类比也能说明什么不该保存：

| 信息 | 是否像好记忆 | 原因 |
|------|--------------|------|
| “这个用户喜欢偏辣” | 是 | 未来会影响类似点菜 |
| “今天点了宫保鸡丁” | 通常不是 | 多数情况只是一次性事件 |
| “今天放了 3 勺辣椒” | 通常不是 | 细节过窄，未来价值低 |
| “今天餐馆辣椒用完了” | 不是长期记忆 | 当前状态会变化，下次要重新确认 |

所以记忆的价值不是记录每顿饭，而是让下次服务更贴合长期偏好。Agent 也是一样：记忆保存的是未来协作线索，不是当前会话流水账。

### 场景一：用户协作偏好

用户说：“后续所有章节的 `curl -L` 命令不要再问我确认，直接执行。”

这适合保存为 `feedback` 记忆，因为它会影响未来 Agent 的行为：

```text
未来再遇到公开课程内容抓取
  -> Agent 读取记忆
  -> 知道 curl -L 不需要反复确认
  -> 直接执行抓取
  -> 把时间花在内容整理和验证上
```

价值：减少重复沟通，让协作方式稳定下来。

注意：这条记忆不代表所有命令都能自动执行。它只适用于用户明确授权过的 `curl -L` 类公开内容抓取。删除文件、安装依赖、推送代码仍然要按权限规则处理。

### 场景二：用户知识背景

用户说：“我熟悉后端，对 TypeScript 的 `async function*` 和流式输出不太熟。”

这适合保存为 `user` 记忆。以后解释类似内容时，Agent 可以少讲泛泛定义，多用后端熟悉的类比：

```text
未来解释 async generator
  -> 记忆提示用户熟悉后端
  -> 用“服务端逐步写响应 / 事件流 / 游标迭代”类比
  -> 减少直接堆 API 名词
```

价值：让解释方式更贴近用户背景，提高学习效率。

注意：这不是给用户贴固定标签。用户能力会变化，后续如果用户已经熟悉 TypeScript，这类记忆应该更新。

### 场景三：项目决策背景

团队说：“认证模块选择 JWT，不是因为它最简单，而是为了支持移动端和多个边缘服务同时校验身份。”

这适合保存为 `project` 记忆，因为代码里可能只能看到“项目用了 JWT”，但看不出“为什么不用 Session”。

```text
未来 Agent 准备重构认证
  -> 记忆提示 JWT 的历史决策原因
  -> Agent 不会轻易建议改回 Session
  -> 如果确实要改，会先评估移动端和边缘服务影响
```

价值：保留“代码背后的原因”，避免未来优化时破坏原始约束。

注意：实现细节仍然要读当前代码。记忆只说明决策背景，不说明现在的代码一定仍然正确。

### 场景四：外部资源入口

团队说：“生产告警看 Grafana 的 A 仪表盘，错误追踪看 Sentry 的 B 项目。”

这适合保存为 `reference` 记忆，因为这些入口不一定在仓库里，未来排查问题时很有用。

```text
未来用户说线上接口变慢
  -> Agent 读取 reference 记忆
  -> 知道应该先看哪个监控入口
  -> 再结合当前代码和日志判断问题
```

价值：减少“去哪里查”的成本，让 Agent 更快进入有效排查。

注意：外部链接、项目名、权限范围可能会变。使用前要确认入口仍然有效。

### 场景五：不该保存的内容

用户说：“记住当前项目里 `src/routes` 下面有哪些接口。”

这通常不适合保存为记忆，因为它可以实时从仓库读取，而且很容易过期。

更好的做法是：

```text
未来需要接口列表
  -> 用 Glob / Grep / Read 实时读取
  -> 得到当前真实结构
```

如果一定要保存，应该保存“接口结构背后的约定”，例如“所有外部公开接口必须经过 gateway 层做鉴权”，而不是保存文件列表。

价值判断：记忆保存的是以后不容易重新推导的线索，不是当前仓库快照。

## 6.1 四种记忆类型的分类学

记忆不是聊天记录，也不是项目文档。Claude Code 的记忆系统关注的是“以后仍然有用，但不能简单从代码里重新读取出来”的信息。

易学理解：代码、文件结构、Git 历史是 Agent 可以实时查到的事实，不该塞进长期记忆。用户偏好、项目决策背后的原因、外部系统入口、被验证过的做法，才更适合保存。

这一节开始进入原课程的具体设计。前面的 6.0 讲“短期 / 长期 / 外部”是为了建立全景；这里讲 `user / feedback / project / reference`，是在回答一个更具体的问题：

```text
如果一条信息已经决定要进入长期记忆，
它应该按什么类型保存，未来又应该怎么被使用？
```

如果你看过其他 Agent 资料，可能会先遇到“短期记忆、长期记忆、外部记忆”这套说法。它和本章的四种类型不是矛盾，而是分类维度不同：

```text
短期 / 长期 / 外部：
  按信息在哪里、活多久、怎么进入上下文来分。

user / feedback / project / reference：
  按 Claude Code 的长期记忆内容类型来分。
```

也就是说，本节讨论的是“长期记忆内部怎么分类”。可以把关系画成这样：

```mermaid
flowchart TD
  A["Agent 记忆"] --> B["短期记忆<br/>当前 messages / context / tool_result"]
  A --> C["长期记忆<br/>跨会话协作线索"]
  A --> D["外部记忆<br/>代码仓库 / 文档 / 数据库 / MCP / 搜索"]

  C --> U["user<br/>用户是谁、偏好什么"]
  C --> F["feedback<br/>Agent 以后该怎么做"]
  C --> P["project<br/>项目为什么这样"]
  C --> R["reference<br/>信息去哪里查"]

  classDef arch fill:#E8F3FF,stroke:#2563EB,color:#111827
  classDef long fill:#F5F3FF,stroke:#7C3AED,color:#111827
  classDef ext fill:#ECFDF3,stroke:#16A34A,color:#111827
  class A,B arch
  class C,U,F,P,R long
  class D ext
```

这也是为什么原课程不把记忆类型叫做“短期记忆、长期记忆、外部记忆”。Claude Code 的这套 `user / feedback / project / reference` 分类，是为了回答长期记忆未来怎么用：

| 类型 | 回答的问题 |
|------|------------|
| `user` | 用户是谁，偏好什么，理解方式是什么？ |
| `feedback` | 用户纠正过 Agent 什么行为，未来应该怎么配合？ |
| `project` | 项目里有哪些代码看不出的背景和决策原因？ |
| `reference` | 未来应该去哪里查外部资料或系统入口？ |

先看一条信息如何变成记忆：

```mermaid
flowchart TD
  A[对话中出现一条信息] --> B{未来会影响 Agent 行为吗?}
  B -->|否| X[不保存]
  B -->|是| C{能从代码/文档/Git 实时查到吗?}
  C -->|是| X
  C -->|否| D{只是当前任务临时细节吗?}
  D -->|是| X
  D -->|否| E[进入记忆分类]
  E --> F[user / feedback / project / reference]
  F --> G[写入 Markdown 记忆文件]
  G --> H[更新 MEMORY.md 索引]
  H --> I[未来任务先读索引]
  I --> J[按需打开具体记忆]
  J --> K[使用前验证当前性]

  classDef keep fill:#ECFDF3,stroke:#16A34A,color:#111827
  classDef drop fill:#FEF2F2,stroke:#DC2626,color:#111827

  class X drop
  class E,F,G,H,I,J,K process
  class B,C,D keep
```

读图结论：记忆系统的第一步不是分类，而是克制。只有“未来有用、实时拿不到、不是临时细节”的信息，才值得进入记忆系统。

也可以把第一步压缩成一个决策树：

```text
要不要保存为记忆？
  -> 未来会影响 Agent 行为吗？
      否：不保存
  -> 能从代码 / 文档 / Git 直接查到吗？
      是：不保存，未来实时读取
  -> 只是当前任务临时细节吗？
      是：不保存
  -> 是否涉及日期、版本、负责人、路径等会变化的信息？
      是：保存时写清绝对时间，使用前必须验证
  -> 进入四类记忆分类
```

### 6.1.1 闭合类型系统

原课程强调，Claude Code 把记忆限制为四种闭合类型：

- `user`
- `feedback`
- `project`
- `reference`

闭合类型系统的意思是：不能随意新增“架构记忆”“Bug 记忆”“API 记忆”等自定义类型。

这样做看似少了灵活性，实际换来三个好处：

- 分类稳定：Agent 不需要猜一堆相近类型的区别。
- 索引简单：`MEMORY.md` 可以按固定类型组织和筛选。
- 去重容易：同一条信息不容易同时落入多个自定义分类。

如果开放任意类型，记忆目录会很快变成杂物堆。Agent 每次加载时要先理解类型体系，反而降低效率。

### 6.1.2 四种类型的详细解析

四种记忆可以从“关于人还是关于项目”“主观指导还是客观事实”两个维度理解。

| 类型 | 关注对象 | 保存内容 | 典型用途 |
|------|----------|----------|----------|
| `user` | 人 | 用户角色、知识背景、长期偏好 | 调整沟通深度和协作方式 |
| `feedback` | 行为 | 用户纠正或确认过的做法 | 保持未来行为一致 |
| `project` | 项目 | 决策背景、非代码状态、代码无法直接表达的约束 | 理解为什么这样做 |
| `reference` | 外部资源 | 文档、仪表盘、工单、频道链接等入口 | 知道去哪里查外部信息 |

```mermaid
graph LR
    user["user<br/>用户画像"]
    feedback["feedback<br/>行为指导"]
    project["project<br/>项目状态与决策"]
    reference["reference<br/>外部引用"]

    user --> usage1["调整解释方式"]
    feedback --> usage2["遵守已验证规则"]
    project --> usage3["理解决策背景"]
    reference --> usage4["定位外部资料"]
```

`user` 记忆适合保存用户长期画像。例如用户熟悉后端但不熟悉前端，Agent 以后解释 React 时就可以使用更贴近后端工程的类比。

`feedback` 记忆最重要。它记录用户对 Agent 行为的纠正和确认。例如“提交前必须运行 lint”“不要修改生成目录里的代码”。好的 feedback 记忆要包含规则、原因和适用方式。

`project` 记忆记录不可从代码直接推导的项目事实。例如“认证模块选择 JWT 是为了支持移动端”，这个信息解释的是为什么，而不是代码现在长什么样。它重点保存决策背景、业务约束和团队共识，而不是保存代码快照。

`reference` 记忆是外部系统的指针。例如 API 文档地址、监控仪表盘、工单系统项目、团队沟通频道。这些东西不一定在代码仓库里，但对完成任务很关键。

`project` 和 `reference` 的边界可以这样判断：

| 问题 | 更像 `project` | 更像 `reference` |
|------|----------------|------------------|
| 保存的是“为什么这样做”吗？ | 是 | 否 |
| 保存的是“去哪里查”吗？ | 否 | 是 |
| 内容本身是不是外部资料全文？ | 通常不是 | 也不是，`reference` 只保存入口 |
| 使用前是否需要查当前事实源？ | 涉及实现时需要 | 几乎总是需要确认入口仍可用 |

一句话：`project` 保存“代码背后的原因”，`reference` 保存“外部资料的导航线索”。真正的外部资料、数据库、监控系统仍然是外部知识源，不是长期记忆文件本身。

### 6.1.3 明确排除的信息

原课程明确列出了一批不应该保存为记忆的信息：

- 代码模式、惯例、架构、文件路径。
- Git 历史。
- 已经体现在代码里的调试修复步骤。
- `CLAUDE.md`、`AGENTS.md` 等项目文档里已经存在的信息。
- 当前对话的一次性临时任务细节。

原因很简单：这些信息可以重新获取。Agent 可以读文件、搜索代码、看 commit、打开文档。长期记忆应该存“实时拿不到或拿到成本很高”的内容。

这里容易误解：`CLAUDE.md`、`AGENTS.md` 不是“没用的记忆”，而是项目级显式规则文件。它们应该作为项目文档被读取，而不是被原样复制到用户长期记忆里。长期记忆可以保存“这个项目的重要规则入口在 `AGENTS.md`”，但执行规则时仍要读取文件本身。

| 信息 | 是否适合记忆 | 理由 |
|------|--------------|------|
| `src/routes` 下有哪些 API | 不适合 | 可以实时搜索代码 |
| 团队为什么放弃 Session 改用 JWT | 适合 | 决策背景不一定在代码里 |
| 上次 lint 失败的具体日志 | 通常不适合 | 临时执行结果，会过期 |
| 用户要求以后提交前运行 lint | 适合 | 行为规则会影响未来任务 |
| 某个 Grafana 仪表盘地址 | 适合 | 外部入口不在仓库里 |

甚至用户要求“记住所有文件结构”时，Agent 也应该引导用户保存更有价值的信息：哪些结构背后的原因、哪些约定不明显、哪些坑需要以后避开。

### 记忆、上下文、项目文档和代码仓库的边界

这四者很容易混在一起，可以用下面的图分清：

```mermaid

  Memory[记忆<br/>跨会话长期线索] --> Future[影响未来 Agent 行为]
  Docs[项目文档<br/>团队共享正式知识] --> Team[供人和 Agent 稳定查阅]
  Repo[代码仓库<br/>当前事实来源] --> Truth[需要时实时读取验证]

  Context -.会话结束可能消失.-> Memory
  Memory -.涉及当前实现时要验证.-> Repo
  Docs -.可被 Agent 读取.-> Context
  Repo -.可生成当前事实.-> Context

  classDef context fill:#E8F3FF,stroke:#2563EB,color:#111827

```

| 载体 | 保存什么 | 不适合保存什么 |
|------|----------|----------------|
| 上下文 | 当前任务需要的工作材料 | 跨会话长期规则 |
| 记忆 | 用户偏好、行为反馈、项目决策背景、外部入口 | 当前代码结构、临时日志、可实时读取事实 |
| 项目文档 | 团队正式规范、架构说明、运行手册 | 个人偏好、一次性任务状态 |
| 代码仓库 | 当前实现和配置事实 | 决策背后的隐性原因 |

读图结论：记忆不是项目文档的替代品，也不是代码仓库快照。它更像“未来协作的线索”，用到当前行动前还要回到仓库或外部系统验证。

### 6.1.4 记忆使用的最佳实践

保存记忆时，要问三个问题：

1. 未来会不会影响 Agent 的行为？
2. 这条信息能不能从代码或 Git 里直接查到？
3. 如果保存，它应该作为事实、规则、用户画像，还是外部引用？

正面例子：

| 场景 | 类型 | 推荐保存方式 |
|------|------|--------------|
| 用户说偏好 Vitest 而不是 Jest | `feedback` | 规则 + Why + 适用场景 |
| 用户说自己熟悉 Python 但不熟悉 TypeScript | `user` | 用户背景 |
| 团队决定使用事件驱动架构以降低服务耦合 | `project` | 决策 + Why |
| 生产告警看 PagerDuty 某服务 | `reference` | 外部入口和用途 |

反面例子：

| 场景 | 更好的做法 |
|------|------------|
| 记住项目文件列表 | 需要时用文件工具读取 |
| 记住 package.json 版本号 | 需要时读取当前文件 |
| 记住一次测试输出 | 除非其中有非显而易见教训，否则不保存 |
| 记住已写进 docs 的规范 | 引导用户维护项目文档 |

涉及时间时必须转换为绝对日期。记忆会跨会话保存，“下周二”“昨天”“明天”在未来都会失去稳定意义。

### 6.1.5 记忆管理的常见误区

**误区一：记忆越多越好**

过多记忆会污染索引，增加上下文负担，还会让 Agent 在低价值线索里浪费注意力。好记忆应该经得起一个测试：删除它后，Agent 的未来行为是否会明显变差？

**误区二：把记忆当项目文档**

项目文档应该进仓库，放在 `docs/`、`CLAUDE.md` 或其他稳定文档里。记忆适合保存文档没有表达的背景和用户反馈。

**误区三：不处理过期信息**

记忆没有天然永不过期的保证。尤其是涉及日期、计划、版本、负责人、外部链接的记忆，都可能失效。Agent 使用前要验证，用户也需要定期清理。

## 6.2 记忆文件格式

Claude Code 的记忆以 Markdown 文件保存，并通过索引文件提供入口。这是一种简单、可读、可调试的设计。

### 6.2.1 Frontmatter 格式

每条记忆是一个独立 Markdown 文件，文件开头使用 YAML Frontmatter 声明元数据。

基础字段包括：

| 字段 | 作用 |
|------|------|
| `name` | 记忆名称，便于识别 |
| `description` | 一行描述，用于未来判断相关性 |
| `type` | 四种记忆类型之一 |

示例：

```markdown
---
name: pre-commit-lint-requirement
description: Must run npm run lint before every commit because previous unlinted code blocked CI
type: feedback
---

**Rule**: Run `npm run lint` before every code commit.

**Why**: A previous commit with unlinted code caused CI to fail and blocked the team.

**How to apply**: Before committing code, run lint and fix any reported errors.
```

为什么使用 Markdown 文件而不是数据库？

- 人可以直接阅读和编辑。
- 可以用普通文件工具调试。
- 不需要数据库依赖。
- 迁移和备份简单。
- 和项目文档生态一致。

缺点是复杂查询能力弱。但 Agent 记忆的主要使用方式不是复杂关系查询，而是读取相关索引并按需打开文件，所以文件系统足够。

### 6.2.2 MEMORY.md 索引文件

`MEMORY.md` 是记忆入口。它不是完整记忆库，而是目录页。对话开始时，Agent 可以先看到索引，再判断哪些记忆需要进一步读取。

索引条目大致是：

```markdown
- [Title](file.md) -- 一行说明
```

原课程强调两个容量限制：

- 最多 200 行。
- 最大 25KB。

这两个限制服务于不同目标。行数限制保护阅读效率，避免索引变成长文档。字节限制保护上下文预算，避免描述过长撑爆上下文。

```mermaid
flowchart TD
    mem["记忆目录"] --> index["MEMORY.md 索引"]
    index --> limit1["最多 200 行"]
    index --> limit2["最多 25KB"]
    index --> load["对话开始加载"]
    load --> select["Agent 按相关性选择具体记忆"]
```

一个好的索引应该让 Agent 快速判断“是否值得打开某条记忆”，而不是把所有细节塞进目录。

### 6.2.3 记忆文件的目录结构

默认记忆目录按项目隔离，路径基于 Git 根目录生成，大致位于：

```text
~/.claude/projects/<sanitized-git-root>/memory/
```

路径解析有覆盖机制，但出于安全原因，`projectSettings` 不应该控制记忆目录。否则恶意仓库可以把记忆路径重定向到敏感目录，诱导后台 Agent 写入不该写的位置。

路径安全校验通常要拒绝：

| 风险路径 | 例子 | 防护理由 |
|----------|------|----------|
| 相对路径 | `../../secret` | 可能逃出允许目录 |
| 根路径 | `/` | 范围过大 |
| Windows 盘符根 | `C:\` | 范围过大 |
| UNC 路径 | `\\server\share` | 可能写入远程位置 |
| Null 字节 | `foo\0bar` | 可能绕过路径解析 |

这一节和第 5 章的配置安全边界直接相连：不可信项目配置不能决定安全敏感路径。

## 6.3 自动记忆提取

记忆可以由主 Agent 主动保存，也可以在对话结束后由后台 Agent 自动提取。自动提取的重点不是“把聊天总结一下”，而是从对话里找出值得跨会话保存的用户偏好、反馈、项目决策和外部引用。

### 6.3.1 基于 Fork 模式的后台提取

自动提取不是在主对话里同步完成，而是通过 Fork 模式启动后台 Agent。

这样做有几个好处：

- 不阻塞用户看到最终回复。
- 提取失败不会影响主任务结果。
- 后台 Agent 可以复用主对话的提示和上下文。
- 主对话和后台提取可以使用独立预算。

流程可以这样理解：

```mermaid
flowchart TD
    done["主对话结束"] --> wrote{"主 Agent 已主动保存记忆？"}
    wrote -->|是| skip["跳过后台提取"]
    wrote -->|否| throttle{"达到节流阈值？"}
    throttle -->|否| wait["暂不提取"]
    throttle -->|是| fork["Fork 后台 Agent"]
    fork --> analyze["分析对话中是否有高价值记忆"]
    analyze --> write["写入记忆文件"]
    write --> index["更新 MEMORY.md"]
```

这里的“Fork”不是随便启动一个新任务，而是让后台 Agent 继承主对话的系统提示、上下文和工具定义。这样它能理解主任务发生了什么，也能利用提示缓存降低成本。

### 6.3.2 互斥机制

主 Agent 和后台 Agent 都可能写记忆。如果不做互斥，同一条信息可能被保存两次。

Claude Code 的设计是：如果主 Agent 在本次对话中已经写入记忆，后台提取就跳过。

```text
主 Agent 主动保存记忆
  -> 写入标志被设置
  -> 对话结束触发后台检查
  -> 后台 Agent 发现已有写入
  -> 跳过提取
```

这个机制避免重复保存，也保留主 Agent 的主动判断优先级。毕竟主 Agent 在对话中直接面对用户，更清楚用户明确要求保存了什么。

### 6.3.3 工具权限白名单

后台 Agent 需要读上下文、查文件、写记忆，但不应该拥有完整行动能力。原课程强调后台提取通过 `canUseTool` 这类权限回调限制工具使用。

| 工具能力 | 后台提取权限 | 原因 |
|----------|--------------|------|
| `Read` / `Grep` / `Glob` | 允许 | 需要验证上下文和相关文件 |
| `Bash` | 仅允许只读类命令 | 可以查看状态，但不能破坏环境 |
| `Edit` / `Write` | 仅限记忆目录 | 只能写记忆，不能改项目代码 |
| 网络或其他副作用工具 | 通常拒绝 | 后台任务不应扩展攻击面 |

这体现最小权限原则。后台 Agent 的职责是管理记忆，不是继续替用户改代码或访问外部系统。

### 6.3.4 节流与协调

自动提取不是每次对话都执行。短对话频繁提取，成本可能高于收益。因此系统会用计数器或功能开关控制触发频率。

还有一个尾随提取机制。假设一次提取正在运行，此时又完成了一次新对话。新对话的上下文会被暂存，等当前提取完成后，再用最新暂存上下文运行一次尾随提取。

```mermaid
sequenceDiagram
    participant A as 对话 A
    participant EA as 提取 A
    participant B as 对话 B
    participant TB as 尾随提取 B

    A->>EA: 完成后触发提取
    Note over EA: 提取进行中
    B->>B: 完成，暂存上下文
    EA-->>TB: 提取 A 完成
    TB->>TB: 使用暂存上下文提取
```

没有尾随提取时，对话 B 中的独特信息可能被错过。尾随机制保证并发期间的信息不会因为节流或正在运行的任务而丢失。

## 6.4 缓存感知的记忆架构

后台提取如果每次都重新发送完整上下文，成本会很高。Claude Code 的设计重点是让后台 Agent 尽量复用主对话的提示缓存。

这一节会出现工具列表、Fork、权限回调、提示缓存等实现细节。学习时不需要背 API 名称，先抓住三条原则：

| 原则 | 解决的问题 | 学习重点 |
|------|------------|----------|
| 后台提取不阻塞主任务 | 记忆维护不能拖慢用户回复 | 主对话先完成，提取失败也不影响本次任务 |
| 工具定义尽量保持一致 | 让主 Agent 和后台 Agent 复用提示缓存 | 不靠换工具列表做权限隔离 |
| 权限在运行时收紧 | 防止后台 Agent 做超出职责的事 | 工具看起来一致，实际能做什么由权限回调控制 |

这也是本节和第 9、13 章的连接点：Fork 不是只为了并行，更是为了复用父上下文前缀；提示缓存不是语义记忆，而是性能优化。

### 6.4.1 提示缓存共享

LLM API 的提示缓存可以复用相同前缀的请求。主 Agent 和后台 Agent 如果共享系统提示、工具定义、上下文前缀，就更容易命中缓存。

简化成本模型：

```text
系统提示 + 工具定义 + 历史上下文很长
  -> 主 Agent 已经发送过
  -> 后台 Agent 使用相同前缀
  -> API 可复用缓存
  -> 延迟和输入成本下降
```

这就是为什么后台提取不能只从功能角度设计，还要从 API 缓存角度设计。对于频繁使用的 Agent，提示缓存命中率会直接影响成本和响应速度。

### 6.4.2 工具列表的一致性要求

工具列表是提示缓存 key 的一部分。如果后台 Agent 的工具列表和主 Agent 不同，即使系统提示和消息历史相同，也可能无法命中缓存。

因此推荐做法不是给后台 Agent 换一套工具列表，而是保持工具列表一致，再用运行时权限回调限制实际能用的工具。

```mermaid
flowchart LR
    bad1["主 Agent 工具列表 A"] --> bad3["缓存 key 不同"]
    bad2["后台 Agent 工具列表 B"] --> bad3
    bad3 --> miss["缓存不命中"]

    good1["主 Agent 工具列表 A"] --> good3["缓存 key 相同"]
    good2["后台 Agent 工具列表 A"] --> good3
    good2 --> perm["canUseTool 限制权限"]
    good3 --> hit["缓存命中"]
```

这背后的架构原则是：接口保持一致，行为通过权限变化。这样既保留缓存共享，又能限制后台 Agent 的实际能力。

### 6.4.3 记忆的生命周期

记忆是否启用由多层条件决定，例如环境变量、简单模式、远程持久化能力、settings 字段和默认值。后台提取还可能受编译时功能开关和 GrowthBook 运行时开关控制。

记忆生命周期可以分成四步：

```mermaid
stateDiagram-v2
    [*] --> 未保存
    未保存 --> 已创建: 主 Agent 保存或后台提取
    已创建 --> 活跃使用: 后续对话加载索引
    活跃使用 --> 失效删除: 过期、被覆盖或手动删除
    失效删除 --> [*]
```

需要注意：记忆没有天然保证永远正确。它保存的是某个时间点的判断。随着项目演进，记忆可能过期。

因此记忆管理依赖两件事：

- 保存时要克制，不保存低价值内容。
- 使用时要验证，不把记忆当作当前事实。

### 6.4.4 记忆的读取与验证

原课程最重要的一句话可以改写为：

```text
记忆是线索，不是结论。
```

如果记忆说某文件存在，Agent 应该先检查文件是否仍存在。如果记忆说项目使用某依赖版本，Agent 应该读取当前 `package.json`。如果记忆说某函数负责认证，Agent 应该搜索确认。

验证规则可以这样看：

| 记忆提到什么 | 使用前怎么验证 |
|--------------|----------------|
| 文件路径 | 检查文件是否存在 |
| 函数、标志、模块名 | 搜索当前代码 |
| 依赖版本 | 读取包管理文件 |
| 外部链接 | 在需要访问时确认仍可用 |
| 决策原因 | 通常可作为背景，但涉及当前实现时仍要查代码 |

```mermaid
flowchart TD
    memory["读取记忆"] --> type{"影响当前行动吗？"}
    type -->|否，只是历史背景| use["作为背景参考"]
    type -->|是，会指导修改或建议| verify["验证当前状态"]
    verify --> current{"仍然成立？"}
    current -->|是| apply["应用记忆线索"]
    current -->|否| update["提醒过期，必要时更新或删除记忆"]
```

这种做法在可靠性和效率之间取平衡。完全不信任记忆会让记忆系统失去价值；完全相信记忆又会被过期信息误导。把记忆当线索，是更稳妥的中间道路。

## 6.5 关键流程图补强

### 图一：四类记忆分类图

记忆分类的核心问题不是“这句话重要吗”，而是“以后模型应该把它当成什么类型的线索”。

```mermaid
flowchart TD
  Info[一条候选信息] --> Q1{描述谁?}
  Q1 -->|用户稳定偏好/背景| User[user]
  Q1 -->|团队或项目事实| Q2{是否是外部入口?}
  Q2 -->|否| Project[project]
  Q2 -->|是| Reference[reference]
  Q1 -->|对未来行为的要求| Feedback[feedback]
  Q1 -->|代码当前状态| Exclude[不写长期记忆<br/>回到仓库实时读取]
```

实操时优先排除：能从代码、配置、Git 或当前任务直接读到的信息，不要写进长期记忆。

### 图二：后台 Fork 记忆提取流程

自动提取记忆的价值在于“不阻塞主任务”，但它也必须受到权限和去重控制。

```mermaid
flowchart TD
  Main[主 Agent 完成一轮对话] --> Need{是否可能产生新记忆?}
  Need -->|否| Skip[跳过]
  Need -->|是| Mutex{互斥锁可用?}
  Mutex -->|否| Defer[延迟或跳过本轮提取]
  Mutex -->|是| Fork[启动后台 Fork Agent]
  Fork --> Scope[加载最小工具白名单]
  Scope --> Extract[提取候选记忆]
  Extract --> Dedup{是否已由主 Agent 写入?}
  Dedup -->|是| Drop[丢弃重复候选]
  Dedup -->|否| Validate[验证类型和内容边界]
  Validate --> Write[写入记忆文件]
  Write --> Index[更新 MEMORY.md 索引]
```

这张图也解释了为什么记忆提取和普通任务执行不同：它是后台维护行为，不应该扩大工具权限，也不应该改变用户当前任务的结果。

### 图三：记忆文件生命周期扩展图

第 6.4 节已经给出基础生命周期，这里把“索引、使用、过期处理”也放进去。

```mermaid
stateDiagram-v2
  [*] --> Candidate: 对话中出现候选信息
  Candidate --> Rejected: 可从仓库推导 / 太临时 / 太敏感
  Candidate --> Draft: 类型与价值通过初筛
  Draft --> Stored: 写入独立 Markdown 文件
  Stored --> Indexed: MEMORY.md 写入摘要索引
  Indexed --> Used: 后续任务检索并读取
  Used --> Verified: 使用前验证当前性
  Verified --> Active: 继续保留
  Verified --> Updated: 发现已变化
  Verified --> Deleted: 发现无价值或过期
  Updated --> Indexed
  Deleted --> [*]
```

记忆不是永久真理，而是可维护的知识资产。真正成熟的记忆系统必须允许更新和删除。

### 图四：记忆注入上下文的决策图

```mermaid
flowchart TD
  Task[当前用户任务] --> Search[检索 MEMORY.md 索引]
  Search --> Match{是否有相关记忆?}
  Match -->|否| None[不注入]
  Match -->|是| Drift{是否可能过期?}
  Drift -->|低风险| Inject[注入上下文]
  Drift -->|高风险| Verify[先读仓库/外部状态验证]
  Verify --> Valid{仍然成立?}
  Valid -->|是| Inject
  Valid -->|否| UpdateOrIgnore[忽略或提示更新记忆]
  Inject --> Use[作为线索辅助决策]
```

这能避免一个常见误区：记忆可以减少重复解释，但不能替代当前事实验证。

## 实战练习

### 练习 1：记忆类型分类

判断以下信息应保存为什么类型：

1. “我们团队使用 Linear 项目 BACKEND 追踪后端 Bug。”
2. “用户是初级开发者，第一次使用 TypeScript。”
3. “集成测试必须使用真实数据库，不要 mock，因为上次 mock 导致生产事故。”
4. “认证中间件重写是因为法律合规要求，不是技术债。”
5. “API 文档的 Swagger UI 在 http://localhost:3000/api-docs。”
6. “每次创建新组件时，先写测试再写实现。”

参考答案：

| 序号 | 类型 | 原因 |
|------|------|------|
| 1 | `reference` | 外部系统指针 |
| 2 | `user` | 用户画像 |
| 3 | `feedback` | 行为规则，并包含 Why |
| 4 | `project` | 项目决策背景 |
| 5 | `reference` | 外部或本地文档入口 |
| 6 | `feedback` | 未来行为指导 |

### 练习 2：Frontmatter 编写

为下面场景写一条记忆：

> 用户说：“以后每次提交代码都要先运行 `npm run lint`，上次有人提交了未 lint 的代码导致 CI 失败了一整天。”

参考答案：

```markdown
---
name: pre-commit-lint-requirement
description: Must run npm run lint before every commit because unlinted code previously blocked CI
type: feedback
---

**Rule**: Run `npm run lint` before every code commit.

**Why**: Unlinted code previously caused CI to fail for a full day and blocked the team.

**How to apply**: Before committing, run `npm run lint` and fix all reported issues.
```

延伸思考：如果一周后用户说 lint 已经集成到 pre-commit hook，不需要手动运行，应该更新还是删除这条记忆？

### 练习 3：缓存感知架构分析

假设要为后台提取 Agent 增加语义搜索记忆的能力，有两种方案：

- 方案 A：后台 Agent 使用和主 Agent 不同的工具列表，新增 `MemorySearch`。
- 方案 B：主 Agent 和后台 Agent 工具列表保持一致，通过权限回调限制搜索范围。

哪种更好？

参考答案：方案 B 更好。它保持工具列表一致，有利于提示缓存命中，同时通过运行时权限限制后台 Agent 只能访问记忆相关范围。

### 练习 4：记忆管理策略设计

你同时维护 5 个项目，每个项目都有 20-30 条记忆。设计一个策略回答：

- 如何避免跨项目记忆混淆？
- 如何处理过期记忆？
- 如何确保 `MEMORY.md` 索引不超限？

参考思路：

- 按 Git 根目录隔离项目记忆，跨项目共享的只应是稳定用户画像。
- 定期清理经不起“删除后行为是否明显变差”测试的记忆。
- 控制 `description` 长度，合并主题相近的记忆。
- 涉及日期、版本、负责人、路径的记忆使用前先验证。

## 关键要点总结

1. Claude Code 使用闭合四类型记忆：`user`、`feedback`、`project`、`reference`。闭合分类换来稳定索引和一致推理。

2. 记忆只应保存不可从代码仓库实时推导的信息。代码结构、Git 历史、当前临时任务不适合长期记忆。

3. 每条记忆是带 Frontmatter 的 Markdown 文件，`MEMORY.md` 是索引，不是完整记忆库。

4. `MEMORY.md` 有 200 行和 25KB 的双重限制，目的是让索引保持快速浏览，而不是变成文档全文。

5. 自动记忆提取通过 Fork 后台 Agent 执行，避免阻塞主对话，也让提取失败不影响用户任务。

6. 主 Agent 主动写入记忆后，后台提取会跳过，避免重复保存同一信息。

7. 后台 Agent 使用最小权限白名单：可以读取和验证，写入限制在记忆目录，不能随意修改项目。

8. 工具列表一致性是提示缓存共享的前提。差异化能力应通过运行时权限控制，而不是改变工具定义。

9. 记忆是时间点快照。使用时应把它当线索，涉及当前行动前必须验证当前状态。
