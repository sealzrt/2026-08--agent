# 第 11 章：技能系统与插件架构

原课程对应：`第三部分-高级模式篇/11-技能系统与插件架构.md`

> 本章讨论 Claude Code 如何把“某类任务的做法”封装成可复用能力。重点不是背技能字段，而是理解 Skill、插件、动态发现、权限来源之间如何组成一个可扩展的能力层。

## 学习目标

读完本章后，你应该能够：

- 理解 Claude Code 技能系统的整体架构，知道内置技能、文件技能、插件技能、MCP 技能分别来自哪里。
- 说清 `SKILL.md` 的 frontmatter 字段、正文、参数替换和附属文件如何共同定义一个技能。
- 理解技能为什么要分层加载、按需发现和条件激活。
- 掌握插件系统如何把技能、智能体和 Hook 打包成一个扩展单元。
- 能够设计一个小而专注的自定义技能，并判断它应该放在用户级、项目级还是插件级。
- 识别技能系统中的安全边界：来源可信度、Shell 内联、文件提取、符号链接和 gitignore 过滤。

## 11.1 技能系统架构

技能系统解决的问题是：Agent 不能把所有任务知识都塞进基础系统提示里。

如果每次启动都把“代码审查流程”“API 生成规范”“调试套路”“部署检查清单”“某项目专用约定”全部放进上下文，模型会更慢、更贵，也更容易在无关指令之间摇摆。Skill 的思路是：把某类任务的知识、流程、模板和辅助资源做成一个能力包，只有在需要时才加载。

可以把技能理解成 Agent 的“专业操作手册”：

```text
基础系统提示：告诉 Agent 怎么工作
工具系统：告诉 Agent 能做哪些动作
技能系统：告诉 Agent 某类任务应该怎么做
插件系统：把一组技能、智能体、Hook 打包分发
```

这套设计的核心目标是“默认可用，按需增强”。普通用户不用配置也能使用内置技能；团队可以在项目中添加项目级技能；企业可以通过管理策略下发统一技能；插件和 MCP 还可以把外部能力接进来。

### 11.1.1 内置技能清单

内置技能是随 Claude Code 一起打包的技能。它们不依赖用户本地目录，启动后就可以被注册，适合承载通用、稳定、面向所有用户的能力。

原课程把内置技能分成两类：

| 类型 | 易学理解 | 例子 | 设计意义 |
|------|----------|------|----------|
| 核心技能 | 所有人都可能需要的基础能力 | 验证、调试、简化、记忆、批处理、走出卡住状态 | 开箱即用，不需要用户先搭建技能目录 |
| 功能门控技能 | 只有特定功能开启时才可用 | 循环任务、Claude API 应用开发、远程计划任务 | 避免实验功能或平台能力提前暴露 |

常见内置技能可以按用途理解：

| 技能方向 | 主要用途 | 典型场景 |
|----------|----------|----------|
| 代码质量 | 验证变更、调试问题、简化代码 | 提交前检查、测试失败分析、重构建议 |
| 工作流辅助 | 批量处理、把 prompt 转成技能、处理卡住状态 | 批量改文件、沉淀复用流程、打破循环推理 |
| 配置与记忆 | 更新配置、记录项目约定、查看快捷键帮助 | 写入 CLAUDE.md、修改 settings、学习按键绑定 |
| 功能门控 | 只在对应功能可用时注册 | 避免无效命令进入模型可见范围 |

这里有一个关键设计点：内置不等于全部加载到模型上下文。

注册技能只是让 Harness 知道“有这个能力”。真正进入上下文，通常要等到技能被用户调用、被模型选择，或满足某些激活条件。否则内置技能越多，基础 prompt 越臃肿。

### 11.1.2 内置技能注册机制

每个内置技能都通过注册函数加入技能系统。注册时不是只给一个 prompt 字符串，而是给一份结构化定义。

一个成熟的技能定义通常包含：

| 字段方向 | 作用 |
|----------|------|
| 名称、描述、别名 | 让用户和模型能识别技能 |
| 使用场景提示 | 帮助模型判断什么时候该用 |
| 参数提示 | 告诉用户 slash 命令需要什么参数 |
| 允许工具 | 限制技能执行时能调用的工具集合 |
| 模型与推理强度 | 针对任务复杂度选择合适模型或继承当前模型 |
| 是否可由用户调用 | 区分内部技能和 slash 命令技能 |
| 运行时门控 | 每次调用前再判断功能是否启用 |
| 执行上下文 | 决定技能在当前会话内执行，还是 fork 到独立上下文 |
| 引用文件 | 提供额外文档、模板或示例 |
| prompt 生成器 | 在真正调用时生成最终提示内容 |

这里最值得关注的是“延迟生成”。技能的 prompt 不一定在启动时就完整生成，而是在技能被调用时再构造。这有几个好处：

- 可以读取当前会话参数。
- 可以结合最新配置和功能开关。
- 可以在需要时才展开附属文件。
- 可以减少启动时的 I/O 和上下文开销。

#### 文件提取的安全设计

有些内置技能会附带参考文件，例如检查清单、示例模板或额外说明。这些资源可以被打包进程序，直到首次使用技能时才提取到磁盘。

这看起来像普通文件写入，但安全要求更高。因为一旦技能会把文件写到磁盘，就要防止符号链接攻击、并发竞态和权限泄露。

原课程强调了几类防护：

| 安全措施 | 防什么 | 易学解释 |
|----------|--------|----------|
| 不跟随符号链接 | 符号链接劫持 | 如果目标路径被替换成指向敏感文件的链接，写入应失败 |
| 独占创建 | 竞态覆盖 | 文件必须是新建，不能悄悄覆盖已有文件 |
| 私有目录权限 | 目录被别人读取或遍历 | 技能临时文件只让当前用户访问 |
| 私有文件权限 | 内容泄露 | 附属文件不应被其他系统用户读取 |
| 单例 Promise | 并发重复提取 | 多个调用同时发生时，只执行一次提取流程 |

可以把这套设计理解为：技能附属文件虽然是“说明书”，但仍然经过真实文件系统，不能按普通字符串处理。只要触碰磁盘，就要把它当成安全边界。

### 11.1.3 技能加载引擎

文件系统上的技能由统一加载引擎处理。加载引擎负责从多个来源读取技能，解析 `SKILL.md`，去重，区分无条件技能和条件技能，然后返回当前会话可见的技能集合。

整体流程可以这样看：

```text
启动或刷新技能
  -> 判断是否 bare mode
  -> 读取管理级、用户级、项目级、额外目录、旧版命令目录
  -> 解析每个技能目录中的 SKILL.md
  -> 使用真实路径去重
  -> 带 paths 的技能进入条件池
  -> 无条件技能直接可用
```

`bare mode` 是一个特殊模式：它减少默认加载，只加载显式加入的目录。这个模式适合需要强隔离或可重复执行的环境，例如测试、SDK 嵌入或受控自动化。

去重也不是细节。项目中可能通过符号链接、嵌套目录或额外目录把同一个技能暴露成多个路径。如果不按真实路径去重，同一个技能可能被加载两次，造成命令重复、优先级混乱或行为不稳定。

## 11.2 技能定义格式

技能定义格式决定了“一个技能到底是什么”。在 Claude Code 中，文件型技能不是随便放一个 Markdown 文件，而是一个目录加一个固定入口文件：

```text
my-skill/
  SKILL.md
  optional-reference.md
  examples/
  scripts/
```

`SKILL.md` 的 frontmatter 负责结构化配置，正文负责给模型看的任务说明。附属文件、示例和脚本则在需要时作为额外资源使用。

### 11.2.1 Markdown Frontmatter 配置

`SKILL.md` 顶部可以写 YAML frontmatter。它描述技能元数据、触发条件、参数、权限和执行上下文。

一个简化示例：

```yaml
---
name: api-endpoint
description: 生成 REST API 端点骨架
when_to_use: 用户需要新增 API 路由、控制器和测试时使用
arguments: method resource
argument-hint: "[GET|POST|PUT|DELETE] [resource]"
allowed-tools:
  - Read
  - Write
  - Grep
  - Glob
model: inherit
context: fork
paths:
  - "src/api/**/*.ts"
---

# API 端点生成

请根据项目现有模式，为 $resource 生成 $method 接口。
```

常用字段可以这样记：

| 字段 | 是否常用 | 作用 | 建议 |
|------|----------|------|------|
| `name` | 常用 | 技能显示名或命令名 | 不写时通常可用目录名推导，建议保持短小 |
| `description` | 必须重视 | 说明技能做什么 | 一句话说清，不要写成泛泛口号 |
| `when_to_use` | 常用 | 给模型看的触发说明 | 写具体场景，不要写“任何时候” |
| `arguments` | 常用 | 声明命名参数 | 参数少时很好用，提升可读性 |
| `argument-hint` | 常用 | 给用户看的参数提示 | 适合 slash 命令 |
| `allowed-tools` | 重要 | 限制技能能用的工具 | 遵循最小权限 |
| `model` | 可选 | 指定或继承模型 | 默认继承通常最稳 |
| `effort` | 可选 | 控制推理强度倾向 | 复杂审查、设计任务可提高 |
| `user-invocable` | 可选 | 是否允许用户直接调用 | 内部辅助技能可以关闭 |
| `disable-model-invocation` | 少见 | 是否不再发起模型调用 | 适合纯脚本或特殊流程 |
| `context` | 重要 | inline 或 fork | 长任务、隔离任务适合 fork |
| `agent` | 可选 | 关联特定子智能体 | 适合把任务交给专门 Agent |
| `paths` | 重要 | 条件激活路径 | 适合按目录或文件类型自动启用 |
| `hooks` | 可选 | 技能前后执行命令 | 用于 lint、测试、生成后校验 |
| `version` | 可选 | 标记技能版本 | 团队分发时有价值 |

易学理解：frontmatter 是“技能说明卡”，正文是“技能操作手册”。模型看到说明卡后知道是否该用，真正执行时再读操作手册。

#### 字段详解与最佳实践

写技能时最常见的问题是太贪心。一个技能如果试图覆盖“前端开发”“后端开发”“测试”“部署”所有事情，它的 prompt 会变长，约束会互相干扰，模型也难以判断重点。

更好的设计原则：

| 原则 | 做法 |
|------|------|
| 小而专注 | 一个技能解决一类任务，例如“生成 API 端点”而不是“写整个后端” |
| 描述具体 | `description` 写清产物和边界 |
| 权限最小 | 只给必要工具，不要默认允许 Bash、Write、Edit |
| 参数清楚 | 能命名就命名，例如 `method resource` 比 `$1 $2` 更容易维护 |
| 依赖显式 | 需要模板、规范、示例时放到技能目录，正文说明何时读取 |
| 可验证 | 技能末尾写清生成后应如何检查 |

### 11.2.2 参数替换机制

技能正文支持参数替换。这样一个技能可以根据用户输入变成不同任务，而不需要为每个资源写一个新技能。

常见替换方式：

| 写法 | 含义 | 示例 |
|------|------|------|
| `$ARGUMENTS` | 完整参数字符串 | `/gen-api GET users` -> `GET users` |
| `$ARGUMENTS[0]` | 第一个参数 | `GET` |
| `$ARGUMENTS[1]` | 第二个参数 | `users` |
| `$1`、`$2` | 位置参数简写 | `$1` 是第一个用户参数 |
| `$method`、`$resource` | 命名参数 | 来自 `arguments: method resource` |
| `${CLAUDE_SKILL_DIR}` | 当前技能目录 | 用来引用附属文件 |
| `${CLAUDE_SESSION_ID}` | 当前会话 ID | 用于日志、临时文件或追踪 |

替换顺序可以理解为：

```text
用户输入 slash 命令
  -> 根据 arguments 绑定命名参数
  -> 替换位置参数
  -> 替换完整参数 $ARGUMENTS
  -> 替换技能目录和会话环境变量
  -> 如果正文完全没用参数，则把参数追加到末尾
```

为什么“没用参数时追加到末尾”？因为很多简单技能不想显式写 `$ARGUMENTS`，但用户输入的补充说明仍然有价值。追加机制让技能更容错。

技能正文还可能支持 Shell 命令内联展开，但这必须受来源限制。来自本地、管理策略或内置的技能相对可信，可以按规则处理；来自 MCP 的技能属于外部来源，不能让它在本地随意执行 Shell 展开。否则远端服务器只要返回恶意技能内容，就可能把 prompt 展开变成本地命令执行。

### 11.2.3 LoadedFrom 类型

`LoadedFrom` 用来标记技能从哪里来。它不是单纯的调试字段，而会影响安全策略和行为。

| 来源 | 易学解释 | 信任倾向 | 关键影响 |
|------|----------|----------|----------|
| `bundled` | 内置打包技能 | 最高 | 可使用内置资源提取机制 |
| `managed` | 企业或管理员下发 | 高 | 用于组织级标准流程 |
| `skills` | 用户或项目 `.claude/skills/` | 中 | 本地可控，但仍要受权限约束 |
| `plugin` | 插件提供 | 中 | 需要考虑插件来源和版本 |
| `commands_DEPRECATED` | 旧版命令目录 | 中偏低 | 兼容历史格式，不建议新增依赖 |
| `mcp` | MCP 服务器提供 | 低 | 不应执行本地 Shell 内联 |

这体现了一个通用原则：能力来源越远，默认信任越低。安全策略不能只看技能内容写得像不像正常文档，而要看它来自哪里、谁能更新它、是否经过本地审查。

## 11.3 技能加载路径

技能加载路径回答两个问题：

1. Claude Code 到哪些地方找技能？
2. 多个地方都有技能时，谁优先？

### 11.3.1 分层加载策略

技能来源按层级组织。不同层级适合不同治理场景：

| 层级 | 路径或来源 | 适合放什么 | 注意点 |
|------|------------|------------|--------|
| 管理策略级 | 管理员配置路径下的 `.claude/skills/` | 企业统一规范、安全流程、审计要求 | 优先级高，适合强约束 |
| 用户级 | `~/.claude/skills/` | 个人常用流程、跨项目习惯 | 不应写项目专属规则 |
| 项目级 | 项目内 `.claude/skills/` | 当前仓库的代码规范、生成模板 | 适合随项目共享 |
| 额外目录 | `--add-dir` 指定目录 | 临时加载或多根工作区 | 要注意来源可信度 |
| 旧版命令目录 | `.claude/commands/` | 历史兼容 | 新能力优先用技能目录 |
| 插件级 | 插件目录中的 commands/agents/hooks | 可分发扩展包 | 需要版本、缓存和错误隔离 |
| 内置级 | 编译进程序 | 通用能力 | 用户不用维护 |

可以用这个流程理解加载：

```text
管理策略
  + 用户级技能
  + 项目级技能
  + 额外目录技能
  + 旧版命令
  + 插件技能
  + 内置技能
  -> 合并
  -> 去重
  -> 按优先级决定最终可见技能
```

不同来源不是简单堆叠。管理策略常常代表企业约束，不能被普通用户配置绕过；项目级技能服务当前仓库；用户级技能服务个人习惯。把三者混在一个目录里，会导致迁移、审计和协作都变困难。

### 11.3.2 动态技能发现

静态加载只能找到已知目录。真实项目，尤其是 monorepo，可能在子项目下放置专用技能。例如：

```text
repo/
  packages/
    web/
      .claude/skills/component-generator/SKILL.md
    api/
      .claude/skills/endpoint-generator/SKILL.md
```

如果 Agent 正在处理 `packages/web/src/Button.tsx`，它更需要前端组件技能，而不是后端 API 技能。动态发现机制就是为这种场景设计的。

流程大致是：

```text
模型读取或编辑某个文件
  -> 从该文件所在目录向上查找
  -> 每一层检查是否存在 .claude/skills/
  -> 跳过被 .gitignore 忽略的目录
  -> 按路径深度合并新技能
  -> 加入动态技能集合
```

跳过 gitignored 目录很重要。否则依赖包、构建产物或临时目录里如果出现 `.claude/skills/`，就可能被误加载。技能是会影响模型行为的输入，不能从不可信目录静默注入。

动态发现的价值：

- Monorepo 中不同子项目可以拥有自己的技能。
- Agent 只有进入相关目录时才看到相关能力。
- 启动时不用扫描整个仓库。
- 项目局部规范可以离代码更近。

### 11.3.3 条件技能

条件技能是带 `paths` 字段的技能。它们不会一开始就直接可用，而是等到模型操作的文件路径匹配规则后才激活。

例子：

```yaml
---
description: React 组件生成和审查规范
paths:
  - "src/components/**/*.tsx"
  - "src/components/**/*.ts"
---
```

激活流程：

```text
加载技能时发现 paths
  -> 放入条件技能池
  -> 模型 Read/Edit/Write 某个文件
  -> 判断文件路径是否匹配 paths
  -> 匹配则激活技能
  -> 本会话后续保持可用
```

“激活后保持可用”是一个细节，但很重要。假设模型读了一个 React 组件，组件技能被激活。后面它可能要改测试文件、样式文件或说明文档，这些文件不一定继续匹配 `paths`。如果技能突然消失，任务行为会不连续。因此，一旦条件技能在会话中被激活，就应该保持可见。

## 11.4 插件系统

技能是能力单元，插件是分发单元。

一个插件可以包含多种扩展：

```text
my-plugin/
  plugin.json
  commands/
    build.md
    deploy.md
  agents/
    reviewer.md
  hooks/
    hooks.json
```

这意味着插件不只是“更多技能”。它可以同时提供 slash 命令、专用子智能体和生命周期 Hook，把一套工作流打包给团队或市场分发。

### 11.4.1 插件目录结构

插件目录通常由清单文件和若干子目录组成：

| 文件或目录 | 作用 |
|------------|------|
| `plugin.json` | 插件元信息，例如名称、版本、描述和组件路径 |
| `commands/` | 插件提供的技能或 slash 命令 |
| `agents/` | 插件提供的自定义智能体 |
| `hooks/` | 插件提供的生命周期钩子配置 |

插件来源主要有两类：

| 来源 | 易学理解 |
|------|----------|
| Marketplace 插件 | 通过配置引用安装或启用，适合可分发能力 |
| Session-only 插件 | 通过命令行参数或 SDK 临时加入，只影响当前会话 |

插件提供的智能体和第 9 章的自定义智能体格式相近；插件提供的技能和本章的文件技能类似。差别在于来源和优先级：插件是一个独立包，适合集中安装、禁用、缓存和诊断。

### 11.4.2 缓存优先加载策略

插件加载会触发较多文件系统操作：读取清单、扫描命令目录、加载智能体、解析 Hook 配置。如果每次需要技能列表都重新扫描插件，性能和稳定性都会受影响。

因此插件采用缓存优先策略：

```text
收集插件来源
  -> 对每个插件目录检查缓存
  -> 命中缓存则直接返回
  -> 未命中则解析 plugin.json
  -> 加载 commands、agents、hooks
  -> 收集错误但尽量不中断其他插件
  -> 写入缓存
  -> 返回插件加载结果
```

“收集错误但不中断”是插件系统常见的韧性设计。一个插件中的某个命令写错了，不应该导致整个 Claude Code 启动失败，也不应该让其他插件全部不可用。更好的做法是：能加载的先加载，错误进入诊断结果，让用户后续修复。

这也解释了为什么插件需要清单和缓存。插件系统面向第三方扩展，质量不可控，必须默认考虑格式错误、缺文件、版本不兼容和部分加载失败。

### 11.4.3 MCP 技能的间接注册

MCP 服务器也可以提供技能。但 MCP 模块和技能模块之间容易产生循环依赖：

```text
技能模块需要知道 MCP 技能如何构造
MCP 模块也需要把远端技能变成技能对象
如果互相直接 import，就会形成依赖环
```

原课程提到的解决思路是“发布-查找”模式：引入一个很小的中间注册模块。

```text
技能模块启动时
  -> 向中间注册模块发布 buildMcpSkill 函数

MCP 模块需要构造技能时
  -> 从中间注册模块查找构造函数
  -> 调用构造函数生成技能
```

这个中间模块本身不依赖复杂业务，因此可以作为依赖图中的叶子节点，打断循环。

为什么不简单用动态 import？因为 Claude Code 需要打包成可执行程序。打包器通常需要在编译期知道模块依赖，如果运行时用变量路径动态加载，打包后可能找不到目标模块。发布-查找模式把依赖关系留在编译期可见范围内，同时避免模块互相引用。

## 11.5 创建自定义技能完整教程

本节目标是把前面的结构落到一个具体技能上。我们以“生成 API 端点”为例。

### 案例：创建一个 API 端点生成技能

目标：用户输入 `/gen-api GET users` 后，Agent 能按项目已有模式生成 API 路由、类型、控制器和测试。

这个技能适合放在项目级还是用户级？

- 如果不同项目的 API 框架差异很大，应放在项目级 `.claude/skills/`。
- 如果你个人所有项目都遵循同一套框架，可以放在用户级 `~/.claude/skills/`。
- 如果要给团队或多个仓库复用，并且附带 agents/hooks，可以做成插件。

#### Step 1: 创建技能目录

项目级技能示例：

```bash
mkdir -p .claude/skills/gen-api
```

用户级技能示例：

```bash
mkdir -p ~/.claude/skills/gen-api
```

#### Step 2: 编写 SKILL.md

示例结构：

```yaml
---
name: gen-api
description: 根据项目现有模式生成 REST API 端点
when_to_use: 用户需要新增接口、CRUD 端点、路由和相关测试时使用
arguments: method resource
argument-hint: "[GET|POST|PUT|DELETE] [resource-name]"
allowed-tools:
  - Read
  - Write
  - Edit
  - Grep
  - Glob
model: inherit
context: fork
user-invocable: true
---

# API 端点生成器

为资源 $resource 创建 $method 接口。

## 上下文收集

先查找项目已有模式：

1. 用 Glob 找路由、控制器、测试和类型目录。
2. 用 Grep 搜索已有的相似资源。
3. 用 Read 阅读一个最接近的现有接口。
4. 总结项目的命名、错误处理、认证和响应格式。

## 生成规范

根据调查结果生成或修改必要文件：

1. 路由定义：遵循现有路由注册方式。
2. 类型定义：补齐请求、响应、查询参数类型。
3. 控制器逻辑：包含输入校验、业务调用、错误处理。
4. 测试文件：覆盖正常路径、错误路径和边界条件。

## 注意事项

- 不要引入项目未使用的新框架。
- 优先复用现有工具函数和错误类型。
- 生成后运行相关测试或说明无法运行的原因。
```

这个示例的重点不是模板本身，而是技能写法：先要求模型调查现有模式，再生成代码。不要让技能直接凭空输出文件，否则它很容易违背项目风格。

#### Step 3: 测试技能

启动 Claude Code 后调用：

```text
/gen-api GET users
```

检查四件事：

| 检查项 | 期望结果 |
|--------|----------|
| 技能是否可见 | slash 命令能被识别 |
| 参数是否替换正确 | `$method` 变成 `GET`，`$resource` 变成 `users` |
| 上下文调查是否发生 | 模型先读现有代码，而不是直接写 |
| 权限是否合理 | 只请求 Read/Grep/Glob/Edit/Write 等必要工具 |

如果技能没有被加载，优先检查目录结构是否是 `技能目录/SKILL.md`，再检查 frontmatter 是否有效。

#### Step 4: 迭代优化

技能很少一次写完就完美。真实迭代通常围绕三个问题：

| 问题 | 优化方式 |
|------|----------|
| 模型漏步骤 | 在正文中把步骤拆得更明确 |
| 生成风格不一致 | 添加“先读取相似文件并总结模式”的要求 |
| 参数不够 | 扩展 `arguments` 或要求用户补充缺失信息 |
| 权限过宽 | 收窄 `allowed-tools` |
| 技能太长 | 拆成多个小技能，或把详细规范放附属文件 |

### 技能组合使用的最佳实践

技能可以单独用，也可以和其他机制组合。

#### 模式一：技能链

技能链适合把一个完整工作流拆成多个独立阶段。

```text
/gen-api POST orders
  -> 生成接口骨架
/verify
  -> 验证类型、测试和运行结果
/remember "订单 API 使用统一错误码"
  -> 把新发现的项目约定沉淀到记忆
```

好处是每个技能保持专注，组合时又能覆盖完整流程。

#### 模式二：条件技能 + 智能体

条件技能适合和专用智能体配合。

```text
条件技能：paths: ["src/api/**/*.ts"]
  -> 只在 API 文件相关任务中激活

API 子智能体：
  -> 专门处理接口设计、控制器、测试

技能附属文件：
  -> 保存项目 API 规范、错误码规则、示例接口
```

这样主 Agent 不需要长期携带 API 细节；只有进入 API 目录并派出相关智能体时，才加载对应知识。

#### 模式三：技能 + Hook

Hook 可以给技能加上自动检查。

```yaml
---
description: 修改接口并运行相关验证
hooks:
  pre:
    - command: npm run typecheck
  post:
    - command: npm test -- --related
---
```

这种组合适合把“执行前检查”和“执行后验证”制度化。不过 Hook 失败时如何处理要写清楚：是立即停止、提示用户，还是继续但标记风险。

## 实战练习

### 练习 1：创建一个自定义项目级技能

在当前项目创建 `.claude/skills/code-review/SKILL.md`，让它只关注 TypeScript 代码审查。

建议包含：

- `description`：说明它输出结构化审查报告。
- `arguments`：接收 `file_path`。
- `allowed-tools`：只允许 `Read`、`Grep`、`Glob`。
- `paths`：匹配 `src/**/*.ts` 和 `src/**/*.tsx`。
- 正文：要求检查安全、性能、可维护性、错误处理和测试缺口。

扩展挑战：在技能目录加入 `review-checklist.md`，正文中要求模型必要时读取该文件。

### 练习 2：创建一个带命名参数的用户级技能

创建 `~/.claude/skills/generate-api/SKILL.md`，声明：

```yaml
---
description: 生成 REST API 端点样板
arguments: method resource_name
allowed-tools:
  - Read
  - Write
  - Grep
  - Glob
---
```

正文中使用 `$method` 和 `$resource_name`。

思考：如果用户只输入 `/generate-api`，技能应该怎么提示缺少参数？更好的做法是在正文第一步要求模型检查参数是否完整，不完整时先向用户确认。

### 练习 3：探索技能加载的调试日志

开启调试日志后观察技能加载过程，重点看：

- 内置技能是否注册。
- 用户级、项目级和旧版命令目录是否被扫描。
- 条件技能是否先进入条件池。
- 符号链接或重复路径是否被去重。
- gitignored 目录中的技能是否被跳过。

这个练习的目的不是记住日志格式，而是建立“技能是从多个来源合并而来”的直觉。

### 练习 4：创建一个带生命周期钩子的技能

设计一个技能，在执行前运行类型检查，在执行后运行相关测试。

思考：

- pre hook 失败时是否应该阻止技能继续？
- post hook 失败时输出应该进入最终报告吗？
- Hook 是否需要读取技能参数？
- 这个技能是否应该允许 `Bash`，还是把验证交给已有工具或项目脚本？

### 练习 5：设计一个条件技能系统

为 React + TypeScript 项目设计四个条件技能：

| 条件 | 技能 |
|------|------|
| `src/components/**` | 组件生成和审查 |
| `src/hooks/**` | 自定义 Hook 设计 |
| `src/api/**` | API 集成 |
| `*.test.*` | 测试辅助 |

思考这些技能可能如何重叠。例如 `src/components/Button.test.tsx` 同时匹配组件和测试。你需要决定是允许两者同时激活，还是让测试技能只关注断言和覆盖率，组件技能只关注组件结构。

## 关键要点

1. Skill 是按需加载的任务能力包，不是普通 prompt 文本，也不是工具本身。
2. 内置技能解决开箱即用问题，文件技能解决用户和项目定制问题，插件技能解决打包分发问题，MCP 技能解决外部能力接入问题。
3. `SKILL.md` 由 frontmatter 和正文组成：frontmatter 描述元数据、权限、参数和触发条件；正文描述具体执行流程。
4. 参数替换让一个技能可以服务多种输入，但参数缺失和歧义要在技能正文中处理。
5. `LoadedFrom` 会影响安全策略。来自 MCP 的技能默认更不可信，不应执行本地 Shell 内联。
6. 分层加载让企业、用户、项目和插件各自管理自己的能力边界。
7. 动态发现和条件技能让技能靠近代码，只在相关路径被操作时激活。
8. 插件是更高层的扩展包，可以同时包含技能、智能体和 Hook。
9. 缓存优先和错误收集让插件系统在第三方扩展质量不稳定时仍能保持可用。
10. 好技能应该小而专注。复杂工作流应通过技能链、条件技能、智能体和 Hook 组合完成。
