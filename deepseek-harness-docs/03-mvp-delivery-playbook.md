# dsh 业务 Agent MVP 交付手册

> 目标：把一个业务 Agent 从想法推进到可试点的 MVP。重点是交付节奏、产出物、验收标准和风险控制。

前面几篇已经回答：

- dsh 适合什么业务场景。
- 业务需求如何映射成 dsh 组件。
- 第一个业务 Agent 可以怎么拆。

这一篇回答：

```text
如果真的要做一个 MVP，项目应该怎么推进？
每个阶段交付什么？
怎么判断可以进入下一阶段？
哪些坑要提前避开？
```

---

## 1. MVP 的正确目标

dsh 业务 Agent 的 MVP 不是“做一个完整 AI 平台”。

MVP 的目标只有一个：

```text
用一个真实业务场景证明：
Agent 能在明确边界内完成动作，
高风险动作能停住，
过程能追溯，
结果能被业务人员接受。
```

所以 MVP 要小：

- 一个业务场景。
- 一个入口。
- 2-3 个核心工具。
- 一个确认点。
- 一份审计日志。
- 一组样例数据。

不要一开始就追求：

- 全流程自动化。
- 全业务线覆盖。
- 完整管理后台。
- 全量系统集成。
- 复杂权限体系。
- 复杂多 Agent 编排。

---

## 2. 推荐 4 周交付节奏

可以按 4 周推进一个业务 Agent MVP。

| 周次 | 目标 | 交付物 | 通过标准 |
|------|------|--------|----------|
| 第 1 周 | 业务边界清楚 | 场景说明、流程图、工具清单、样例数据 | 业务方认可“先做这一个场景” |
| 第 2 周 | 跑通工具动作 | 2-3 个工具、模拟数据、基础 Agent 提示 | Agent 能调用工具处理样例 |
| 第 3 周 | 跑通闭环流程 | 人工确认、审计日志、错误处理 | 高风险能停住，结果能追溯 |
| 第 4 周 | 小范围试点 | 真实接口或测试系统、验收报告、问题清单 | 10-30 条样例完成验收 |

如果团队刚接触 dsh，第一轮 MVP 可以放宽到 6 周，但不要拖成 3 个月。时间太长，说明范围太大。

---

## 3. 第 1 周：把业务边界问清楚

第 1 周不要急着写代码。

目标是把业务问题固定下来。

### 3.1 需要产出的文档

| 文档 | 内容 |
|------|------|
| 场景说明 | 这个 Agent 到底处理什么业务 |
| 输入输出 | 输入数据是什么，最终输出是什么 |
| 流程图 | 从触发到结束有哪几步 |
| 工具清单 | Agent 需要调用哪些动作 |
| 风险清单 | 哪些动作需要确认或禁止自动执行 |
| 样例数据 | 用于测试的 10-30 条真实或脱敏样例 |

### 3.2 场景说明模板

```text
业务场景：

当前痛点：

希望 Agent 完成的任务：

本次 MVP 只覆盖：

本次 MVP 不覆盖：

业务成功标准：
```

### 3.3 常见错误

| 错误 | 后果 |
|------|------|
| 一上来做完整平台 | 迟迟看不到效果 |
| 没有样例数据 | 后面无法验收 |
| 没有定义高风险动作 | Agent 容易越界 |
| 没有业务负责人确认 | 做完发现不是业务想要的 |

第 1 周通过标准：

```text
业务方能接受：
先做这个小场景，
用这些样例验证，
这些动作必须人工确认。
```

---

## 4. 第 2 周：跑通工具动作

第 2 周的目标不是流程完整，而是证明 Agent 能调用业务动作。

### 4.1 工具优先级

先做三类工具：

| 类型 | 例子 | 优先级 |
|------|------|--------|
| 查询工具 | 查规则、查客户、查档案、查订单 | 高 |
| 写入工具 | 创建记录、更新状态、写入结果 | 高 |
| 审计工具 | 写日志、保存处理记录 | 高 |

暂时不急着做：

- 复杂统计工具。
- 批量工具。
- 多系统联动工具。
- 自动通知工具。

### 4.2 工具设计模板

每个工具都写清楚：

```text
工具名：

用途：

输入字段：

输出字段：

是否只读：

是否会修改业务状态：

失败时返回什么：

是否需要人工确认：
```

### 4.3 先用模拟实现

MVP 早期可以先用模拟数据。

比如：

```text
query_customer -> 先查 JSON 文件
save_ticket -> 先写 SQLite
notify_oa -> 先打印模拟回执
```

这样做不是偷懒，而是降低集成噪音。先证明 Agent 的流程能走通，再换真实系统。

第 2 周通过标准：

```text
Agent 能在样例任务中正确调用工具，
工具输入输出能被业务方看懂，
失败时不会静默吞掉错误。
```

## 5. 第 3 周：跑通闭环流程

第 3 周要把“动作”变成“业务闭环”。

### 5.1 加入人工确认

先只加一个确认点。

常见确认点：

| 确认点 | 触发条件 |
|--------|----------|
| 写入确认 | 即将写生产或测试业务库 |
| 高风险确认 | 涉及投诉、退款、删除、涉密、隐私 |
| 低置信度确认 | Agent 无法确定分类或部门 |
| 对外通知确认 | 即将发短信、邮件、OA 通知 |

确认信息要短：

```text
是否允许执行这个动作？

动作：将工单分派给售后支持部
原因：命中退款和投诉规则
影响：会创建一条正式分派记录
```

### 5.2 加入审计日志

审计日志至少记录：

| 字段 | 说明 |
|------|------|
| `request_id` | 业务请求 ID |
| `session_id` | dsh 会话 ID |
| `tool_name` | 调用的工具 |
| `decision` | 自动执行、人工通过、人工拒绝、失败 |
| `reason` | 判断原因 |
| `operator_id` | 发起人或确认人 |
| `output_ref` | 写入结果或报告地址 |
| `created_at` | 时间 |

### 5.3 加入失败处理

第一版至少定义三种失败：

| 失败类型 | 处理方式 |
|----------|----------|
| 输入信息不完整 | 转人工补充 |
| 工具调用失败 | 返回错误并写审计 |
| 高风险未确认 | 不执行写入 |

第 3 周通过标准：

```text
Agent 能完成完整业务路径；
高风险动作不会自动越过确认；
每次处理都有日志；
失败能被看见。
```

---

## 6. 第 4 周：小范围试点

第 4 周目标是验证真实可用性。

### 6.1 试点范围

建议只选一个窄范围：

```text
只处理一个部门
只处理一种业务类型
只处理低风险数据
只接测试环境
只让 2-3 个业务人员试用
```

### 6.2 试点数据

准备 10-30 条样例。

| 类型 | 数量 |
|------|------|
| 正常样例 | 50% |
| 高风险样例 | 20% |
| 信息不完整样例 | 20% |
| 异常格式样例 | 10% |

不要只准备“漂亮数据”。真实业务一定有脏数据。

### 6.3 验收报告

试点结束后输出一份报告：

| 项目 | 内容 |
|------|------|
| 样例数量 | 共处理多少条 |
| 自动完成数量 | 自动通过多少条 |
| 转人工数量 | 因为什么转人工 |
| 错误数量 | 错误类型是什么 |
| 业务反馈 | 哪些判断不符合预期 |
| 修正计划 | 下一轮改什么 |

第 4 周通过标准：

```text
业务方能基于试点结果判断：
这个方向值得继续投入，
下一轮应该扩大哪里，
哪些规则需要修正。
```

## 7. 角色分工

一个 dsh 业务 Agent MVP 通常需要这些角色：

| 角色 | 负责什么 |
|------|----------|
| 业务负责人 | 定义场景、规则、验收标准 |
| 技术负责人 | 拆工具、插件、流程、系统集成 |
| Agent 设计者 | 设计提示、工具边界、人工确认策略 |
| 后端开发 | 实现工具和系统对接 |
| 测试 / 业务试用者 | 准备样例、跑验收、反馈结果 |

最容易缺的是业务负责人。

如果没有业务负责人，Agent 很容易变成“技术演示”，而不是业务能力。

---

## 8. 交付物清单

一个合格 MVP 至少应该有这些交付物。

| 交付物 | 是否必须 | 说明 |
|--------|----------|------|
| 场景说明 | 必须 | 说明本次只解决什么问题 |
| 流程图 | 必须 | 让业务方和技术方对齐 |
| 工具清单 | 必须 | 明确 Agent 可以做什么 |
| 风险清单 | 必须 | 明确哪些动作要确认 |
| 样例数据 | 必须 | 没有样例就无法验收 |
| 审计日志 | 必须 | 证明过程可追溯 |
| 验收报告 | 必须 | 决定是否进入下一轮 |
| 源码实现 | 必须 | 工具、插件或配置 |
| 完整 UI | 非必须 | MVP 阶段可简化 |
| 复杂权限 | 非必须 | 先控制范围，再逐步补 |

## 9. MVP 风险清单

### 风险 1：业务规则不清楚

表现：

- 业务方经常改口。
- 不同人给出不同判断。
- 样例没有标准答案。

处理：

```text
先整理规则和样例，不急着写 Agent。
```

### 风险 2：工具太大

表现：

- 一个工具做了查询、判断、写入、通知。
- Agent 看不到中间过程。
- 出错无法定位。

处理：

```text
把工具拆小：
query -> decide -> confirm -> write -> audit
```

### 风险 3：过早接生产系统

表现：

- 调试困难。
- 错误影响真实数据。
- 业务方不敢试。

处理：

```text
先用模拟数据和测试库，闭环稳定后再接生产。
```

### 风险 4：没有人工确认

表现：

- Agent 直接写入业务系统。
- 高风险动作无法拦截。
- 业务方不信任系统。

处理：

```text
第一版至少保留一个确认点。
```

### 风险 5：只看自动化率

表现：

- 追求所有任务都自动完成。
- 不愿意转人工。
- 错误被隐藏。

处理：

```text
MVP 的核心指标是安全闭环，不是自动化率。
```

## 10. 什么时候可以进入下一阶段

满足这些条件，再进入下一阶段：

| 条件 | 说明 |
|------|------|
| 业务方认可场景 | 没有场景争议 |
| 样例有标准答案 | 能判断 Agent 对不对 |
| 工具边界稳定 | 输入输出不频繁变化 |
| 高风险能停住 | 不越过确认 |
| 日志能复盘 | 能解释每次处理 |
| 错误能看见 | 不静默失败 |
| 业务愿意试用 | 有真实反馈来源 |

如果这些条件不满足，不要扩大范围。

## 11. 复盘模板

每轮 MVP 结束后，做一次复盘。

```text
本轮试点场景：

处理样例数量：

自动完成数量：

转人工数量：

失败数量：

最常见失败原因：

业务方最不满意的点：

下轮保留什么：

下轮删除什么：

下轮新增什么：
```

复盘时要特别关注：

```text
哪些地方 Agent 不该自动化？
哪些工具边界太模糊？
哪些规则应该从提示词移到规则表？
哪些日志字段不足以解释结果？
```

---

## 12. 学习重点

这篇文档的重点不是让你记住 dsh 的所有机制，而是建立交付判断：

```text
业务边界先于技术实现
工具边界先于插件开发
确认机制先于自动化率
审计日志先于规模扩展
MVP 验收先于生产上线
```

如果你能按这套方式推进一个小场景，就已经具备把 dsh 用到业务里的基本能力。
