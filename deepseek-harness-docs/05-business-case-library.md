# 业务 Agent 案例库

> 目标：通过具体业务案例，快速理解 dsh 可以落到哪些场景、第一版 MVP 怎么切、需要哪些工具、哪里要人工确认、怎么验收。

如果 [04-business-agent-patterns.md](04-business-agent-patterns.md) 是“模式库”，这一篇就是“案例库”。

建议读法：

```text
先找一个和你业务相似的案例
  -> 看它的 MVP 边界
  -> 抄它的工具清单和确认点
  -> 换成自己的业务字段
```

## 1. 案例选择表

先用这张表快速找相似场景。

| 案例 | 适合部门 | 主要价值 | 推荐模式 |
|------|----------|----------|----------|
| 客服工单分派 | 客服、运营 | 减少人工判断和分派时间 | 写入前确认 + 转人工兜底 |
| 档案自动归档 | 档案、政务、办公室 | 提升整理、分类、入库效率 | 流程编排 + 审计优先 |
| 运维巡检报告 | 运维、平台 | 自动检查系统状态并生成报告 | headless 批处理 + 审计优先 |
| 合同初审助手 | 法务、采购 | 标出风险条款，辅助人工审查 | 只读辅助 + 转人工兜底 |
| 报销单初审 | 财务、人事 | 初步校验票据和制度规则 | 写入前确认 + 流程编排 |
| 知识库问答升级 | 客服、IT 支持 | 从问答升级到可行动助手 | 只读辅助 -> 写入前确认 |
| 数据质量巡检 | 数据、运营 | 自动发现异常数据并生成处理建议 | headless 批处理 |
| OA 公文流转助手 | 办公室、行政 | 辅助拟办、分发、催办和归档 | 流程编排 + 系统集成 |

## 3. 案例一：客服工单分派

### 3.1 业务痛点

客服工单进入系统后，需要人工判断：

- 属于哪个问题类型。
- 是否紧急。
- 应该分派给哪个部门。
- 是否需要升级处理。

高峰期工单多时，人工分派容易慢，也容易标准不一致。

### 3.2 第一版 MVP

第一版只做：

```text
输入一条工单文本
Agent 判断类型、紧急程度、责任部门
高风险或低置信度时人工确认
确认后创建分派记录
记录审计日志
```

第一版不做：

- 多渠道接入。
- 自动回复客户。
- 复杂 SLA 计算。
- 全量工单系统重构。

### 3.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `query_routing_rules` | 查询 | 查询工单分类和部门规则 |
| `query_customer_profile` | 查询 | 查询客户等级和历史投诉 |
| `create_ticket_assignment` | 写入 | 创建分派记录 |
| `write_audit_log` | 审计 | 记录判断、确认和写入结果 |

### 3.4 人工确认点

需要人工确认的情况：

- 投诉、退款、舆情类工单。
- Agent 判断置信度低。
- 命中多个部门规则。
- 客户等级高或历史投诉多。

### 3.5 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 样例数量 | 10-30 条 |
| 自动分派准确率 | 70%-80% 可接受 |
| 高风险拦截 | 100% 进入确认 |
| 审计完整性 | 每条工单都有判断原因和工具记录 |

## 4. 案例二：档案自动归档

### 4.1 业务痛点

档案整理通常涉及：

- 接收文件。
- 识别文件类型。
- 提取题名、文号、责任者、日期等元数据。
- 判断保管期限和分类。
- 生成档号。
- 入库或转人工审核。

人工处理耗时长，而且规范要求高。

### 4.2 第一版 MVP

第一版只做：

```text
接收 10-30 份脱敏文件
Agent 提取元数据
给出分类和保管期限建议
低置信度进入人工审核
审核通过后写入测试库
```

第一版不做：

- 全量历史档案迁移。
- 复杂 OCR 和版式还原。
- 涉密文件自动处理。
- 生产库直接写入。

### 4.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `read_archive_file` | 查询 | 读取待归档文件内容 |
| `extract_archive_metadata` | 处理 | 提取题名、文号、日期等字段 |
| `query_archive_rules` | 查询 | 查询分类和保管期限规则 |
| `create_archive_record` | 写入 | 写入档案目录记录 |
| `write_audit_log` | 审计 | 记录提取、分类、审核和入库过程 |

### 4.4 流程草图

```text
接收文件
  -> 提取元数据
  -> 查询归档规则
  -> 判断分类和期限
  -> 人工审核
  -> 写入测试库
  -> 生成处理报告
```

### 4.5 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 元数据提取 | 关键字段可被人工快速核对 |
| 分类建议 | 能解释依据 |
| 低置信度处理 | 必须进入人工审核 |
| 审计 | 每份文件都有处理链路 |

档案场景建议从一开始就采用“审计优先模式”，因为后续进入真实业务时，留痕和复盘比自动化率更重要。

## 5. 案例三：运维巡检报告

### 5.1 业务痛点

运维人员每天要检查：

- 服务是否存活。
- 日志是否有异常。
- 磁盘、CPU、内存是否异常。
- 关键接口是否超时。
- 是否需要通知负责人。

这些检查重复性强，适合先做半自动化。

### 5.2 第一版 MVP

第一版只做：

```text
每天手动或定时触发一次巡检
检查 3-5 个关键指标
生成一份 Markdown 报告
异常项给出处理建议
不自动重启服务
```

第一版不做：

- 自动修复生产故障。
- 覆盖全部系统。
- 复杂告警收敛。
- 自动发生产通知。

### 5.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `check_service_health` | 查询 | 检查服务状态 |
| `query_recent_logs` | 查询 | 查询最近错误日志 |
| `query_metric_snapshot` | 查询 | 查询 CPU、内存、磁盘等指标 |
| `write_report` | 写入 | 生成巡检报告 |
| `write_audit_log` | 审计 | 记录巡检批次和异常 |

### 5.4 推荐入口

| 阶段 | 入口 |
|------|------|
| 试验期 | `web` 手动触发 |
| 稳定后 | `headless` 定时执行 |
| 平台集成 | SDK / 调度系统调用 |

### 5.5 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 覆盖系统 | 1 个核心系统 |
| 覆盖指标 | 3-5 个 |
| 报告质量 | 运维人员能直接判断是否异常 |
| 风险边界 | 不自动执行重启、删除、扩容等动作 |

## 6. 案例四：合同初审助手

### 6.1 业务痛点

合同审查需要关注：

- 付款条款。
- 违约责任。
- 自动续约。
- 解除条件。
- 管辖和争议解决。
- 不符合公司模板的条款。

这些工作需要专业判断，不适合第一版就自动审批。

### 6.2 第一版 MVP

第一版只做：

```text
上传一份合同文本
Agent 标出潜在风险条款
给出风险原因和建议
生成初审清单
法务人工确认
```

第一版不做：

- 自动批准合同。
- 自动修改正式合同。
- 替代法务判断。
- 处理所有合同类型。

### 6.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `read_contract` | 查询 | 读取合同文本 |
| `query_contract_rules` | 查询 | 查询公司合同审查规则 |
| `generate_review_checklist` | 处理 | 生成初审清单 |
| `write_review_report` | 写入 | 输出审查报告 |
| `write_audit_log` | 审计 | 记录风险判断依据 |

### 6.4 人工确认点

合同场景建议所有结论都定位为“建议”，不要让 Agent 自动做最终判断。

确认点：

- 风险等级。
- 是否需要修改。
- 是否可进入下一审批环节。

### 6.5 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 漏检风险 | 用历史样例评估 |
| 解释质量 | 能指出条款位置和原因 |
| 人工节省时间 | 法务初审时间下降 |
| 边界 | 明确提示“最终以法务审核为准” |

## 7. 案例五：报销单初审

### 7.1 业务痛点

财务报销初审经常需要检查：

- 发票金额是否匹配。
- 报销类型是否符合制度。
- 附件是否齐全。
- 是否超预算。
- 是否需要上级审批。

规则多、重复性强，但涉及财务风险，需要谨慎。

### 7.2 第一版 MVP

第一版只做：

```text
读取一张报销单和附件信息
根据制度规则生成初审结果
标出缺失材料和异常项
高风险或不确定项转人工
不自动付款
```

### 7.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `query_expense_policy` | 查询 | 查询报销制度 |
| `query_budget_status` | 查询 | 查询预算状态 |
| `check_invoice_fields` | 处理 | 校验发票字段 |
| `create_expense_review` | 写入 | 创建初审记录 |
| `write_audit_log` | 审计 | 记录规则命中和人工确认 |

### 7.4 人工确认点

必须转人工的情况：

- 超预算。
- 发票字段冲突。
- 缺少关键附件。
- 涉及特殊审批。
- 金额超过阈值。

### 7.5 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 规则命中 | 能说明违反哪条制度 |
| 风险拦截 | 高金额和异常票据必须转人工 |
| 处理建议 | 财务能直接看到缺什么材料 |
| 自动边界 | 不自动付款、不自动最终驳回 |

## 8. 案例六：知识库问答升级为可行动助手

### 8.1 业务痛点

很多企业已经有知识库问答，但用户问完后还要自己操作系统：

```text
问：怎么申请账号？
答：请到系统 A 填表，找主管审批，再联系 IT 开通。
```

这类场景可以从“只回答”升级成“帮用户准备动作”。

### 8.2 第一版 MVP

第一版只做：

```text
用户提出常见 IT 支持问题
Agent 查询知识库
如果需要提交申请，生成申请草稿
用户确认后创建工单
```

第一版不做：

- 自动审批。
- 自动开通账号。
- 覆盖全部 IT 流程。

### 8.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `search_knowledge_base` | 查询 | 查询制度或操作文档 |
| `query_user_profile` | 查询 | 查询用户部门和角色 |
| `create_it_ticket_draft` | 写入 | 创建工单草稿 |
| `submit_it_ticket` | 写入 | 用户确认后提交工单 |
| `write_audit_log` | 审计 | 记录问题、依据和提交动作 |

### 8.4 迁移路径

```text
阶段 1：只回答问题
阶段 2：生成可复制的申请内容
阶段 3：确认后创建工单草稿
阶段 4：确认后正式提交
阶段 5：低风险工单自动提交
```

这个案例适合把已有 RAG 系统逐步升级成业务 Agent。

## 9. 案例七：数据质量巡检

### 9.1 业务痛点

运营或数据团队经常要检查：

- 数据是否缺失。
- 指标是否突增突降。
- 业务字段是否异常。
- 上游任务是否延迟。
- 报表口径是否变化。

这些任务很适合先做 headless 批处理。

### 9.2 第一版 MVP

第一版只做：

```text
每天检查一张核心业务表
跑 3-5 条质量规则
生成异常列表和解释
不自动修复数据
```

### 9.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `query_data_snapshot` | 查询 | 查询核心指标快照 |
| `run_quality_rules` | 处理 | 执行质量检查规则 |
| `generate_anomaly_report` | 写入 | 生成异常报告 |
| `create_data_issue` | 写入 | 必要时创建待处理问题 |
| `write_audit_log` | 审计 | 记录批次、规则和异常 |

### 9.4 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 规则数量 | 3-5 条 |
| 巡检对象 | 1 张核心表或 1 个核心指标 |
| 报告可读性 | 业务人员能看懂异常原因 |
| 风险边界 | 不自动改数据 |

## 10. 案例八：OA 公文流转助手

### 10.1 业务痛点

OA 公文处理经常涉及：

- 来文登记。
- 拟办意见。
- 分发部门。
- 催办。
- 办结归档。

流程长、节点多、系统集成多，适合流程编排，但不适合第一版做全流程自动化。

### 10.2 第一版 MVP

第一版只做：

```text
选择一种公文类型
Agent 读取公文摘要
生成拟办建议和分发部门建议
人工确认后生成处理记录
不自动替领导审批
```

### 10.3 工具清单

| 工具 | 类型 | 作用 |
|------|------|------|
| `read_oa_document` | 查询 | 读取公文摘要和元数据 |
| `query_department_rules` | 查询 | 查询分发规则 |
| `create_handling_suggestion` | 写入 | 生成拟办建议 |
| `create_archive_task` | 写入 | 办结后创建归档任务 |
| `write_audit_log` | 审计 | 记录建议、确认和归档任务 |

### 10.4 人工确认点

需要确认：

- 拟办意见。
- 分发部门。
- 是否催办。
- 是否进入归档。

### 10.5 验收标准

| 指标 | 第一版目标 |
|------|------------|
| 场景范围 | 只覆盖一种公文类型 |
| 建议质量 | 办公室人员能快速修改使用 |
| 系统写入 | 只写测试记录或草稿 |
| 审计 | 能看到谁确认了什么 |

## 11. 怎么把案例迁移到自己的业务

不要逐字照搬案例。按下面方式迁移：

```text
1. 把案例里的业务名换成你的业务名。
2. 把输入对象换成你的业务对象。
3. 把工具清单换成你的系统动作。
4. 把确认点换成你的风险动作。
5. 把验收标准换成你的样例数据指标。
```

迁移模板：

```text
我的业务场景：

当前人工怎么做：

Agent 第一版只帮哪一步：

需要查询哪些系统：

需要写入哪些系统：

哪些动作必须确认：

失败后交给谁：

审计日志要记录什么：

准备多少条样例验证：

第一版通过标准：
```

## 12. 学习建议

如果目标是快速落地，建议先选一个“低风险、有真实数据、业务人员愿意配合”的案例。

优先级可以这样排：

```text
1. 只读辅助类
2. 写入前确认类
3. 有固定流程但规模小的场景
4. headless 批处理类
5. 多系统复杂流程
```

一个好的第一版业务 Agent，不是看起来多强，而是满足：

- 场景足够小。
- 输入输出清楚。
- 工具边界清楚。
- 风险能停住。
- 结果能复盘。
- 业务人员愿意继续试。
